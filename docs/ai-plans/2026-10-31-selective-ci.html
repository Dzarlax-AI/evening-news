Evening News · 31 октября 2026 · Редакция 1 · Реализовано и проверено локально

Проверять затронутые модули. Собирать и публиковать изменённые образы.

Полная интеграционная проверка остаётся отдельным обязательным gate перед публикацией. Она проверяет конкретный комплект новых и повторно используемых образов.

1. Результат и границы

Обычный PR получает выборочные тесты с объяснением выбора. Релиз собирает каждый изменённый core-образ один раз, проверяет итоговый комплект и публикует только новые образы. Неизменённые компоненты сохраняют прежние digest и revision.

В область входят выбор проверок во всех Go workflows, сборка трёх core targets, контракт acceptance receipt и публикационный manifest. Триггеры отдельных extractor/browser workflows используют собственные зависимости; их runtime, Dockerfile и поведение не меняются. Бизнес-логика, схемы БД, AI-вызовы, каналы доставки и прод не входят в реализацию этого плана.

Одобрение ниже разрешает локальную реализацию и проверки. Commit, push, PR, merge, публикация и выкладка требуют соответствующего отдельного разрешения. Разрешения на срочный релиз дайджеста не распространяются на CI.

2. Что обнаружено в текущем коде

  • .github/workflows/docker-build-push.yml: 11 модулей × PostgreSQL 16/17, recovery и ARM64; после этого PR собирает все три образа для полного gate. Ручная публикация снова выполняет проверки и сборку всех трёх.
  • После merge автоматически запускается ещё один прогон. При срочном релизе PR #58 дублирующий push-прогон был отменён, чтобы освободить runners для публикации.
  • go-tools/corerelease/release.go всегда публикует web/background/executor и требует одну revision. fixturegate/images.go и receipt.go тоже требуют общую revision. Поэтому одних path filters недостаточно.
  • docker-bake.hcl уже позволяет выбирать targets. Их зависимости заданы в docker/Dockerfile. Изменение теста само по себе не требует нового runtime-образа; встроенные ресурсы и копируемые в финальный слой файлы требуют учёта.

Основа проектирования — origin/main@2ca1726453e49de86e5f5cec72654775267e8850. Локальная ветка диагностики содержит отдельные незакоммиченные изменения; в работу CI они не попадут.

3. Как определяется влияние

Новый Go-инструмент формирует проверяемый план: base/head, изменённые файлы с учётом удаления и переименования, модули для тестов, image targets, обязательные специальные gates и причины каждого выбора. Каталог владельцев файлов хранится в репозитории. Локальные import-зависимости читаются из AST исходников обеих Git-ревизий без сетевого разрешения зависимостей; общие fixtures и не-Go ресурсы имеют явных потребителей.

Для runtime-файла проверяется модуль и обратные зависимости затронутых пакетов; для тестового файла — потребители этого тестового входа. Состав образа вычисляется отдельно: компилируемые зависимости команд, go.mod/go.sum, go:embed, финальные COPY, frontend assets и рецепт сборки. Изменения lockfiles считаются влияющими на соответствующие targets.

PR сравнивается с merge base. Релиз сравнивается с revision последнего доверенного опубликованного каталога компонентов, а не только с HEAD^: так не пропускаются несколько накопленных коммитов. Новый план обязан показывать выбранные проверки и причины пропусков в GitHub summary.

4. Три этапа вместо повторных полных прогонов

  1. PR / быстрые проверки. Только выбранные модули: race tests, vet и проверка зависимостей; PostgreSQL 16/17 сохраняются там, где есть соответствующие проверки. ARM64 — для затронутых runtime targets. Required check имеет стабильное имя и существует даже при пустой матрице. Неожиданно пропущенный выбранный job считается ошибкой.
  2. Кандидат reviewed main. После merge определяется полный накопленный delta, выбранные образы собираются один раз. Результат и точные идентификаторы сохраняются как артефакты этого SHA. Одновременный merge/dispatch не запускает второй кандидат для того же SHA. Проверки PR другого SHA автоматически не засчитываются как проверка main.
  3. Отдельный full integration gate → ручная публикация. Gate получает проверенный комплект из новых candidates и прежних immutable digests. Проверяет весь комплект на PG16/17, recovery, контракты и image identity. Публикация принимает только receipt именно этого комплекта и SHA; повторная сборка после acceptance запрещена. Если gate уже прошёл для тех же входов, второй gate не нужен.

Full gate оформляется отдельным reusable workflow с ручным вызовом. Его можно вызвать до публикации для любого подготовленного комплекта; публикация без успешного gate запрещена. Изменения самого selector/release/gate вызывают расширенную проверку в PR. Пустой выбор образов даёт no-op отчёт и не создаёт новых тегов.

Сохраняются vertical fixture, managed recovery и managed-adoption acceptance на PostgreSQL 16 и 17, включая extractor fixture. Неизменённый вспомогательный extractor fixture переиспользуется как проверенный OCI-артефакт с собственными source fingerprint/platform/image ID; его исходники меняются — он собирается один раз для gate. Первичный fixture-артефакт создаётся явно при переходе. При его утрате требуется явная bootstrap-сборка; скрытой пересборки неизменённых компонентов в full gate нет. Отдельная публикация extractor остаётся в своём workflow.

5. Каталог компонентов и защита публикации

Каталог содержит все три core-компонента. У каждого — собственные revision, repository, platform, registry digest и проверенный config/image ID; новый manifest v2 дополнительно фиксирует source fingerprint, происхождение и признак built/reused. Top-level revision обозначает рассмотренный комплект, а не притворную пересборку каждого компонента. Registry digest и Docker config ID остаются разными полями.

  • Baseline берётся из успешной публикации доверенного workflow этого репозитория на main. Проверяются workflow/event, conclusion, SHA, ancestry, platform, формат manifest и digest. Артефакты fork/PR не становятся baseline публикации.
  • Полный v1 manifest ревизии 2ca1726… уже скачан из успешного publication run 41229321309. Импорт в первый baseline допустим только после проверки доступности всех трёх registry digests, их identities и вычисления source fingerprints по исходникам этой revision; эти проверки ещё не выполнены для всего каталога. Дальше используется v2. Неизвестная версия или недостоверный baseline блокируют публикацию; автоматического выбора latest нет.
  • Неизменённый компонент подтягивается по digest и сохраняет старую revision. Новый компонент обязан иметь labels текущего SHA. Receipt содержит полный комплект и список разрешённых к публикации новых targets.
  • Publisher перед первым push проверяет отсутствие только новых immutable SHA tags и соответствие receipt. Reused targets не retag/push. Чужой, устаревший или подменённый receipt отклоняется.
  • Повторный dispatch использует завершённый кандидат/gate того же SHA и набора входов. При утрате артефакта нельзя незаметно пересобрать другой образ под уже принятым receipt. Повторная сборка создаёт новый кандидат и требует свежего gate.
  • Публикации разных SHA сериализуются общей блокировкой, отдельно от dedup одного SHA. Внутри неё baseline перечитывается перед первым push и перед выпуском полного manifest. Если другой релиз уже продвинул каталог, старый комплект не публикуется: пересчитывается delta/комплект и нужен свежий gate. Более старая revision не может откатить каталог более новой; недоступная или неоднозначная история публикаций блокирует операцию.
  • Полный успешный manifest публикуется только после завершения всех новых push. Если публикация прервалась частично, уже существующие SHA tags не перезаписываются; требуется сверка состояния и продолжение только при доказанном совпадении.

GitHub token получает package write только в публикационном job. Fork PR с недоступным baseline может пройти полный изолированный build/gate без публикации. Изменения mutable base images требуют явного пересмотра/принудительной сборки выбранных targets; reuse не означает автоматическое обновление базового слоя.

Граница acceptance: gate подтверждает указанный каталог компонентов. Произвольный прод-комплект с более старыми digest этим receipt не подтверждается. При последующей частичной выкладке нужно сверить реальные pins с проверенным комплектом или отдельно проверить фактическую комбинацию. Прод-каталог не меняется этим планом.

7. Проверки и критерии приёмки

Критерии приёмки редакции 1; фактические результаты приведены в журнале ниже:

  • Selector: runtime/test/docs-only, shared fixtures, reverse imports, embed/resources, lockfiles, удаление/rename, несколько коммитов после baseline, shallow checkout, несуществующий base, неизвестный путь. PR #57 и #58 становятся реальными регрессионными примерами выбора.
  • Publication: нет baseline, неверные repo/workflow/event/SHA/ancestry/platform, неподходящий source fingerprint, отсутствующий/устаревший receipt, замена локального tag после gate, различающиеся PG receipts, пустой выбор, частичная публикация и повторный запуск.
  • Publisher fake runner доказывает отсутствие build/tag/push для reused targets. Runtime source change не может получить пустой список образов. Контракт gate проверяет все три компонента даже при одной новой сборке.
  • Для изменённых Go-пакетов — race tests и vet в соответствующем модуле. Для YAML — parser/linter, если доступен; затем изолированные прогонки без credentials публикации. Команды новых CLI документируются после реализации.
  • Полный fixture gate PG16/17 на смешанном комплекте; managed recovery, managed-adoption acceptance, extractor fixture и проверка точных image identities сохраняются. Проверяется reuse вспомогательного fixture без лишней сборки. Все данные синтетические, реальные AI и Telegram/Viber не вызываются.
  • Два разных main SHA одновременно используют один baseline: разрешён только актуальный каталог; после продвижения baseline старый receipt не разрешает push или замену полного manifest. Отмена и частичная публикация не превращаются в успех.
  • После отдельного разрешения CI-проверки на GitHub: модульный PR, web-only, tests-only и docs-only; сводка выбора, required check, отсутствие ложных skipped. Публикация не используется для проверки простого trigger.

Успех означает доказанный выбор и отсутствие лишних build/push в проверенных сценариях. Число минут или процент ускорения заранее не обещаются; сравнение выполняется по фактическим GitHub job timings после одобренного пробного прогона.

8. Риски, допущения и восстановление

  • Неполный каталог зависимостей: неизвестный runtime-файл запускает консервативную проверку/останавливает публикацию. Покрытие владельцев файлов проверяется автоматически.
  • Потерянный baseline: блокировка публикации с объяснением. Bootstrap полного каталога — отдельное явное действие, не скрытый fallback публикации.
  • Подтверждённое ограничение хранения: release manifest запрашивает retention 90 дней (политика репозитория может сократить срок); поиск ограничен 2000 артефактами всего репозитория. Утрата baseline или превышение границы блокирует также main impact, а не только publish. Core-baseline recovery/bootstrap пока не реализован; нужен отдельно согласованный проверяемый порядок восстановления. bootstrap_fixture относится только к вспомогательному extractor. Непрерывное хранение каталога требует отдельного решения.
  • Различающиеся версии компонентов: допустимы только при проверке полного комплекта; миграционные и wire-contract изменения не освобождаются от full gate.
  • Изменение build recipe/toolchain: отражается в fingerprints. Экспериментально уточняется полный набор build inputs по Dockerfile и import/asset graph; зависимые блоки не подключаются до прохождения проверки полноты.
  • Required checks / branch protection: текущие правила читаются перед подключением workflows. Их настройки автоматически не меняются; если потребуется переименование защищённого check, это отдельное согласование.
  • Rollback: вернуть workflow и инструменты к предыдущему проверенному коммиту через обычный reviewed change; уже опубликованные immutable digests и версии сохраняются. Исправление CI не требует отката прод-контейнеров или БД.

Выбранные решения для одобрения: доверенный прошлый publication manifest как baseline; per-component revisions; обязательный отдельный full gate; повторное использование exact-SHA артефактов вместо повторных сборок. Пользовательских открытых вопросов к редакции 1 нет. Реализация останавливается и согласует изменение плана, если невозможно подтвердить происхождение baseline или полноту runtime input graph.

9. Одобрение и журнал исполнения

Редакция 1 одобрена пользователем 31 октября 2026. на локальную реализацию описанного CI, работу Terra/Luna и независимый review. Production, commit/push/PR/merge и публикация сюда не входят.

Почему требуется gate: меняется контракт release manifest/receipt и доверие к образам. AGENTS.md и навык html-implementation-plan требуют согласовать такие изменения до реализации.

Реализовано в новой ветке ci/selective-core-images: граф влияния пакетов и build inputs, выборочные module/ARM64 проверки, отдельный integration workflow, каталоги и receipts v2 со смешанными revisions, проверка происхождения GitHub artifacts, exact-SHA reuse и публикация только выбранных образов с повторной проверкой baseline под общей блокировкой.

Terra реализовал selector, release-контракт и доверенный artifact client; Luna — маршрутизацию дополнительных workflows и документацию. Итоговую оркестрацию интегрировал ведущий. Независимый Terra review завершён без оставшихся P1/P2 после исправлений. Summary отражает окончательный выбор, включая PR fallback. При изменении самого алгоритма fingerprints несовпадение с опубликованным каталогом консервативно требует новой сборки.

Подтверждено локально: race tests и vet затронутых Go-пакетов, полный go-tools: go test -race -timeout=15m ./...; go vet ./... на отдельной локальной БД PostgreSQL 17 и DB-тесты scheduler bridge на PostgreSQL 16; 18 синтетических Python-тестов; actionlint v1.7.12 для всех девяти workflows; реальное read-only чтение доверенного v1 baseline через GitHub API. Полный vertical gate прошёл на PostgreSQL 16 и 17 с разными revisions трёх компонентов, canonical receipts совпали; managed-adoption прошёл на обеих версиях. Данные синтетические, внешние AI и каналы не вызывались.

Ограничения: GitHub Actions на новой ветке не запускался, публикация и прод не менялись. Настройки branch protection не менялись; read-only API сообщил, что main не защищён. Полная managed-recovery матрица сохранена в reusable workflow, но локально в этой реализации заново не выполнялась. Начальный переход меняет build recipe и закономерно выбирает все затронутые образы; дальнейшие изменения используют выборочный delta. Symlink/gitlink, неизвестный модуль и непроверенный Docker recipe останавливают selector. Первый вспомогательный OCI fixture требует явного bootstrap.

Сохранность: отдельный worktree не включает незакоммиченную диагностику дайджеста из исходного checkout. Commit/push/PR/merge и публикация остаются за отдельным разрешением.

Локальная приёмка завершена. Тестовые контейнеры и образы удалены; исходные Immich-контейнеры и прежний PostgreSQL 17 сохранены. SHA-256 всех восьми файлов прежней диагностики совпали. Для активации CI нужен отдельно разрешённый commit → PR → CI; измерение времени и живой gate остаются до этого шага непроверенными.
