Проверенное состояние

GitHub main и локальный исходный go-web/go.mod выбирают x/crypto v0.49.0. Локальная ветка fix/digest-failure-diagnostics, исходный HEAD 2ca1726. Несвязанные изменения go-domain сохранены.

Минимальный локальный кандидат уже подготовлен: x/crypto v0.52.0, x/sys v0.45.0, x/text v0.37.0; изменены только go-web/go.mod и go-web/go.sum. go mod tidy, go mod verify, go test -race -count=1 ./..., go vet ./... и git diff --check прошли. DB-интеграция без изолированного TEST_DATABASE_URL не подтверждена.

go-web использует argon2 и blake2b; SSH не входит в дерево импортов. Исходные SSH-advisory, исправленные в v0.52.0, отсутствуют в результатах сканирования кандидата. Однако govulncheck обнаружил более поздние SSH-advisory GO-2026-6303, GO-2026-6354 и GO-2026-6355 на уровне зависимости, исправленные в v0.55–0.56; используемые пакеты их не достигают. Advisory неподдерживаемого openpgp GO-2026-5932 не имеет исправленной версии, и пакет не импортируется.

Общий govulncheck завершился с ошибкой: 23 находки на уровне вызываемых символов в x/text и стандартной библиотеке локального Go 1.26.4. Это результат локального анализа, не проверка production-бинарника и не доказательство практической эксплуатации.

Предлагаемый результат и границы

Выровнять go-web с уже существующим go-domain: Go 1.26.10, x/crypto v0.58.0, x/text v0.43.0 и необходимые транзитивные версии. В кэше подтверждено: x/crypto v0.58.0 требует Go 1.26.0. Сохранить форматы парольных хешей, HTTP/API и поведение аутентификации.

В объём входят локальные исходники сборки и проверки web. Commit, push, PR, merge, публикация образов, production, рассылки и прочие сервисы требуют отдельного разрешения. Dependabot повторно оценивает GitHub-ветку после публикации изменений; сейчас его закрытие не подтверждено.

Файлы и порядок

  1. go-web/go.mod и go-web/go.sum: Go 1.26.10 и согласованный набор зависимостей через go get и go mod tidy.
  2. go-web/Dockerfile: образ компилятора golang:1.26.10-alpine.
  3. docker/Dockerfile: отдельный GO_WEB_BUILD_IMAGE=golang:1.26.10-alpine для стадии go-web-build; общий GO_BUILD_IMAGE используется также background, поэтому его не менять этим шагом.
  4. .github/workflows/web-api.yml уже читает go-web/go.mod; проверить этот контракт и другие web-сборки. Менять только обнаруженные жёсткие web-пины.
  5. Добавить осмысленную проверку совместимости старого Argon2-хеша с новой библиотекой и неверного пароля, если ближайшие тесты без БД этого не покрывают.

Исполнение последовательно одним агентом: файлы тесно связаны, отдельные исполнители не дают независимого объёма. Отдельная проверка кандидата — по workflow fix-finding. Изменений API, схемы БД и настроек production не предполагается.

Приёмка — запланировано

  • Go 1.26.10: go mod verify, go test -race -count=1 ./..., go vet ./... в go-web.
  • govulncheck ./...: ноль находок в достижимом коде; отдельно показать оставшиеся модульные advisory, включая неиспользуемый openpgp.
  • Сборка news-web для linux/amd64 и linux/arm64; временные бинарники удалить после проверки.
  • Проверить обе Docker-стадии web и их выбранный компилятор; при недоступном Docker явно обозначить ограничение.
  • БД-тесты выполнять только на изолированной loopback-базе. Отсутствие такой базы отмечать как пропуск, не как успешную проверку.
  • Финальный diff ограничен указанным объёмом; изменения digest сохранены. Повторная GitHub/Dependabot-проверка отложена до отдельно разрешённого push.

Риски, откат и открытый вопрос

Обновление минимального Go меняет требования к локальным и контейнерным сборкам; локальная версия по умолчанию 1.26.4 останется без изменения глобальной установки. Для проверок использовать отдельный toolchain. Набор транзитивных версий определяется Go MVS и проверяется по фактическому diff.

Откат — только обратный patch собственных изменений в перечисленных файлах после проверки diff. Не применять reset/checkout ко всему дереву; не затрагивать существующие изменения go-domain и пользовательские файлы.

Решение: согласовать локальное расширение с v0.52.0 до v0.58.0, Go 1.26.10 и обновление двух путей сборки web? Расширение согласовано и выполнено локально.
