Подтверждённая диагностика

28 news_processing jobs с 00:00 UTC: все succeeded. Четыре прохода имеют warning с одним source outcome transport_failed: 05:12 snscratchpad.com (source11), 06:52, 08:52, 09:52 hype.replicate.dev (source10), время Europe/Belgrade. Все последующие проходы чистые. Последний 10:12: восемь источников, errors0. Полного провала конвейера не было.

executor.py трактует любой warning/deferred как failure для общей scheduled-task тревоги; OperationalAlertManager сразу закрывает инцидент после одного чистого прохода. Поэтому одиночный сетевой сбой одного источника вызывает общий красный alert и recovery через двадцать минут. transport_failed — общий код: точную сетевую причину по имеющимся receipts установить нельзя.

Отдельно: news_worker имеет 69 Docker restarts, generation24. За сегодня шесть heartbeat failures, затем повторы запуска с lease held, потом новое получение lease. OOMKilled=false, PostgreSQL и browser без рестартов. Сейчас worker healthy, memory PSI0. Эти события не совпадают по времени с указанными source warnings. Store.Heartbeat скрывает исходную ошибку в ErrLeaseLost: корень проблемы пока не доказан.

Предлагаемое поведение алертов

  • Настоящий failed job, недоступность worker и отсутствие обработки — срочная тревога без ожидания двух проходов.
  • Одиночный retryable source transport warning остаётся видимым в receipts/админке, но не объявляет падение всего scheduled task.
  • Тревога об источнике после двух последовательных scheduled-проходов с ошибкой одного и того же source_id. Одиночные ошибки разных источников не складываются в один инцидент.
  • Recovery только после двух успешных наблюдений того же источника. Состояние восстанавливается из durable receipts, не теряется при рестарте executor.
  • Короткое сообщение включает источник, безопасный код причины и X/8 успешных источников. Без URL query, содержимого статей и секретов.
  • Ошибки неизвестного типа и предупреждения AI/delivery не подавлять автоматически; конкретную классификацию сверить с существующими bounded результатами.

Worker lease: сначала доказать причину

Добавить только безопасную диагностическую классификацию heartbeat: стадия begin/update/commit, SQLSTATE либо context timeout/cancel/connection closed. Не выводить DSN, SQL-параметры и тексты драйверных ошибок. В изолированном PostgreSQL воспроизвести задержку/блокировку, разрыв соединения и конкурирующий запуск; проверить время освобождения advisory lock. Исправление выбирать по доказанному сценарию. Запрещено игнорировать потерю lease, продолжать запись после fencing или просто увеличивать таймауты без проверки. Если причина требует изменения контракта владения либо остаётся неизвестной — представить уточнение до такого изменения.

Исполнение и проверка

  1. Сильный lead фиксирует интерфейс bounded source observations и критерии incident/recovery; проверяет очередь и права чтения receipts.
  2. По уточнению пользователя сначала Luna выполняет безопасную диагностику и локальное воспроизведение lease; lead принимает причинный вывод и проверяет fix. Затем Luna реализует alert policy и тесты.
  3. Проверки: один warning→тишина; повтор одного source→одна тревога; разные source→не складывать; один success→ещё не recovery; два success→один recovery; restart→состояние не теряется; failed job→немедленная тревога; скрытые ошибки AI не подавлены; ложные повторы completion не дублируют отправку.
  4. Go tests с PostgreSQL: contender не получает lease; транзакции старого owner отклонены; lock освобождается после потери backend; heartbeat/retention конкуренция не создаёт двух writers. Race/vet по изменённым пакетам. Никаких реальных сайтов или Telegram-send в тестах.
  5. Независимый review реального diff, затем PR/CI. Production acceptance и выкат отдельно после разрешения.

Сейчас выполнены только read-only диагностика и чтение кода. Этап worker lease передан Luna; результаты новых проверок будут записаны ниже.

Риски и восстановление

Два наблюдения увеличивают время до source alert и recovery; это осознанный фильтр шума с сохранением всех warning receipts. Нельзя скрыть полный сбой обработки. Любое исправление lease обязано сохранить fail-closed fencing и защиту от поздней записи. Откат к предыдущим image/config только после отдельного решения; не откатывать данные и не удалять receipts.

Execution checkpoint 1 — worker lease

Luna реализовал безопасный HeartbeatError (begin/update/commit + bounded reason/SQLSTATE) и ожидание только ErrLeaseHeld при старте: до20сек, интервал1сек. До приобретения lease нет claims и recovery вызовов. Heartbeat5сек, ownership generation и fail-closed fencing не изменены.

Локальный PostgreSQL17.11: удерживаемая FOR UPDATE блокировка строки статуса воспроизводит timeout heartbeat и безопасное прекращение владения; затем replacement получает lock. Backend termination и stale generation отклоняют старые записи. Это доказывает локальный сценарий, но НЕ точную причину ночных production событий. Исправлен быстрый цикл повторных стартов при ещё занятом lock; утверждать устранение всех69рестартов пока нельзя.

Go tests/race/vet выполнены Luna; lead независимо повторил go test -race ./... -count=1 и go vet ./... с loopback fixture: pass. Production не использован. Перешли ко второму этапу.

Routine implementation detail — durable source state

Источником наблюдений остаются существующие Go run/source receipts для точного job+attempt. Маркеры отправки и ограниченное состояние source-инцидентов сохраняются во внутренних JSON строках существующей Setting, отдельно для schedule/source/config. Это не требует миграции, нового поля job-result или изменения API. Необработанные/неизвестные предупреждения сохраняют немедленный общий alert; ошибки AI не могут скрываться source-классификацией.

Execution checkpoint 2 — alerts and acceptance

Luna реализовал ScheduledSourceAlertPolicy и интеграцию с legacy completion: 2 последовательных предупреждения одного source/config → source alert; 2 healthy → recovery. Один warning остаётся в job/run receipts без общей тревоги. Неизвестные ошибки, несколько одновременно проблемных источников и AI/delivery warnings сохраняют консервативный немедленный generic путь.

Внутренние bounded Setting JSON строки хранят инцидент и исход отправки отдельно по расписанию. Состояние переживает новый экземпляр executor. Unknown delivery не повторяется вслепую и не вызывает ложного recovery; после двух healthy оно молча закрывается для будущих новых инцидентов. Manual jobs, другие schedules и изменённые конфигурации не смешиваются. Пропущенный callback предыдущего scheduled job разрывает последовательность: поздний replay не создаёт ложный второй сбой. Проверяются предыдущие queue positions; более поздние queued jobs не влияют.

Два дополнительных дефекта исправлены при review: Python errors_count больше не перекрывает добавленную AI-ошибку старым source-счётчиком; SQL exception alert policy откатывает только savepoint и сохраняет общий предупреждающий путь. Публичные API, job-result поля, DB migration, heartbeat timeout и правила владения не изменены.
