Web/API и админка: границы компонентов и перенос реализации

26 октября 2026 · Ревизия 1 · In progress — одобрено пользователем 26 октября 2026

Границы определяются назначением и контрактами. Язык и контейнер — решения о реализации и размещении. Первый этап заменяет существующий web; количество постоянно работающих контейнеров не увеличивается.

1. Цель и границы

Перенести публичный web/API и админку с FastAPI на Go, сохранив URL, авторизацию, данные, интерфейс и пользовательские действия. Сразу разделить HTTP/UI, Auth, Job acceptance, Schedule management и repositories; не создавать единый модуль со всеми обязанностями.

Не переписываем AI, prompts, сводки и доставку. Не меняем алгоритмы worker, collector, ingestion и article processing, настройки браузера, Readeck и production. Не объединяем контейнеры по признаку языка. Изменения retention бэкапов, исправление worker heartbeat timeout и редизайн UI вне этого этапа.

Уже выполненная локальная чистка трёх неиспользуемых Python-модулей сохраняется отдельным изменением; её не смешиваем с переносом web. Незакоммиченные планы и AGENTS.md не сбрасываем.

2. Что проверено в исходниках

  • main.py монтирует static, public, admin, auth и API; при старте выполняет миграции и инициализирует БД.
  • admin.py использует Basic/доверенный ForwardAuth и выдаёт admin_token. security.py поддерживает HS256 JWT, Bearer, cookie, Basic, роли и ограничения входа. Это несколько действующих путей, их нельзя заменить одним новым логином.
  • public.py, api/* содержат read API, CRUD и команды; background_jobs.py — транзакционную идемпотентность, лимиты и advisory locks. scheduled_jobs_router.py принимает приватные occurrence envelopes.
  • scheduler_router.py уже обращается к Go scheduler. Расписание не переносим в память web и не создаём второй таймер.
  • В web/templates/ 18 Jinja-шаблонов; CSS и клиентские скрипты обслуживают существующие страницы. В том числе есть страницы backup, categories, sources, schedule, summaries, stats, telegram и settings.
  • docker-compose.example.yml уже содержит отдельные web, executor, worker, scheduler, article-ingestion, article-processing и extractor. Это локальный пример, не свежий аудит VPS.

Память проекта подтверждает распределение ответственности после PR28; live production в этой работе не проверялся и не изменялся. Полный маршрутный контракт, включая неудачные запросы, фиксируем из запускаемого Python baseline до реализации, а не только из списка декораторов.

Компоненты внутри процесса не обещают независимого развёртывания. Для замены реализации на другом языке нужны стабильные DTO/ошибки и транспортный адаптер; это предусмотрено интерфейсами и contract-тестами. Сетевые API и дополнительные контейнеры вводятся только при доказанной потребности в отдельном жизненном цикле.

Итог первого этапа: web заменён, не добавлен поверх старого. После замеров отдельно решаем, какие существующие процессы разумно объединить: сравниваем credentials, права БД, egress, память и область отказа. Конкретное сокращение числа контейнеров сейчас не обещается.

4. Контракты и правила переноса

  • Совместимость: method/path, trailing slash, query defaults, пагинация, сортировка, даты UTC, null/empty, JSON поля, коды и headers ответов, RSS/XML, redirects и job receipts. OpenAPI и используемые frontend маршруты входят в inventory.
  • Auth: сохранить Basic, совместимость уже выданных HS256 JWT и cookie, roles/expiry, cookie flags и rate limits; тестировать отказ, истечение и неверный algorithm. ForwardAuth принимается только при явном доверенном режиме и установленной границе proxy. Не расширять набор доверенных заголовков. Cookie mutations требуют проверки защиты от cross-origin/CSRF; если нужна смена пользовательского auth-контракта, отдельно согласовать дельту.
  • Приём jobs: перенести существующие правила producer lock, coalescing, idempotency aliases, max pending/selected IDs/payload, worker availability и occurrence receipts. Сохранить wire payload и hash-совместимость с существующими producers. Дубликат и конфликт различимы. При timeout не создавать второе задание вслепую. Параллельные старый Python и новый Go producer проверяются на одной тестовой БД.
  • UI: перевести Jinja в Go html/template, сохранив DOM/CSS/JS и Book-оформление. Не добавлять SPA/Node runtime. Типизированные view models; экранирование HTML и данных внутри script проверяется отдельно. Изменяемый клиентский код писать на TypeScript, только если изменение необходимо для контракта.
  • Действия с AI/доставкой: тяжёлые операции уже отправляются в существующие durable jobs. Оставшиеся синхронные операции выявить в inventory; сохранить ответы через узкие приватные typed adapters executor с отдельным токеном, fixed origin, bounded body/time и allowlist операций. Не проксировать произвольный URL/SQL/весь Python API. Не менять prompts, provider keys и семантику доставки.
  • Бэкапы/maintenance: сохранить текущие API и проверки прав, file streaming и лимиты upload. Файлы и restore выполняются существующим приватным backend через ограниченный контракт; web не получает новые host mounts или pg superuser. Рекурсивные удаления и реальные restore в QA запрещены; использовать изолированные fixtures.
  • БД: текущую схему не пересоздавать. Вынести существующий Python bootstrap миграций в явную одноразовую команду для локального Compose/CI; readiness web проверяет нужную версию. Не допускать зависимость «executor ждёт web, web ждёт миграцию в executor». Не запускать два независимых владельца миграций.
  • Ограничения: bounded HTTP/DB pools, timeouts/cancellation, безопасные ошибки и aggregate logs. Go web не получает Gemini/Telegram credentials. Ошибка одного адаптера не выдаётся за успешный результат.

5. Этапы реализации и ответственность

Lead фиксирует контракты, проверяет diff и принимает результат. Исполнение на Luna (gpt-6-luna); ниже последовательные участки с одним владельцем общих файлов. Отдельный reviewer проверяет auth, транзакции и affected paths; зелёные отчёты исполнителя не заменяют независимый прогон.

  1. Inventory и baseline. Luna: фактические registered routes и схемы, связи шаблонов/JS, auth matrix, синтетические snapshots ответов и SQL side effects. Файлы: новые tests/fixtures/web-contract-v1/, English guide docs/web-api-components.md. До фиксации baseline остальные этапы заблокированы. Любая операция без понятного владельца останавливает только зависимый участок.
  2. Компоненты и публичный web. Новый go-web/: cmd/news-web, internal/httpui, auth, jobs, schedules, repositories, backend, config. Public feed/search/digest/article, static и auth parity; маршруты админки пока не объявляются готовыми. Gate: differential reads и malformed/auth tests.
  3. Команды и админка. Luna: queue acceptance, scheduler facade, CRUD, health/stats, typed Python adapters, все admin templates. Python changes ограничены private adapters и bootstrap; AI internals не трогаются. Gate: все inventory rows имеют реализацию и regression evidence, включая ошибки.
  4. Замена и удаление дубля. Локальный Compose заменяет web, добавляет только одноразовый migration job; новый go-web/Dockerfile, private fixture gate и CI. После полного acceptance удалить заменённые Python public/admin/API runtime и web-only зависимости; CLI/executor/tests сохранить по реальным callers. В документации показать логические границы отдельно от процессов и Docker.
  5. PR и review. Предлагаем два последовательных PR: (1) baseline, компоненты, все public/admin/API маршруты, private adapters и локальная Compose/fixture замена без production-переключения; (2) удаление заменённого Python web после принятия совместимости и переноса regression coverage. При необходимости разделять по проверяемой функциональности, а не по языку. Перед push проверить состояние целевого PR и начать от актуального main. Merge, image publication и выкат требуют отдельного разрешения.

6. Проверки и критерии готовности

Часть локальных проверок выполнена; browser QA, CI и review ещё не завершены.

  • Go: go test -race ./..., go vet ./..., go mod verify; Linux amd64/ARM64 builds, локальный Mac ARM64. Новые скрипты gate должны иметь проверенные cleanup и отсутствие внешнего egress.
  • Python regression: python -m pytest tests -q в согласованном окружении; PostgreSQL-dependent tests на isolated PG16/17. Сравнение одинаковых read API на Python baseline и Go; нормализация только случайных ID/часов, не семантических различий.
  • Полный source/processing/job fixture: настоящий web → durable queue → worker → executor → ingestion/processing; fake AI, synthetic RSS/Telegram/Page Monitor, fake Telegram/Telegraph. Повтор одной команды создаёт один job и одну разрешённую delivery attempt; никакой отправки наружу.
  • Auth и безопасность: анонимные public reads; отказ admin/API без прав; Basic→cookie→действие, Bearer, expired/invalid JWT, неверные ForwardAuth headers, CORS/CSRF, XSS в title/summary, path traversal и upload limits. Нет токенов в логах.
  • Транзакции: конкурентные submits Python/Go, conflicting idempotency key, queue full, stale heartbeat, lost response, отмена; scheduled occurrence/revision и next_run сохраняются. Текущий heartbeat timeout не объявляется исправленным этим переносом.
  • UI в браузере: feed/filter/search/article/digest, login и все admin pages, сохранение settings и schedule, queue polling/error display, mobile widths, dark mode и keyboard. Использовать только синтетические данные и заблокированную внешнюю доставку. Здоровый контейнер не считается доказательством работающей админки.
  • Нагрузка: сравнить одинаковый synthetic сценарий до/после — latency, DB connections, container working set/cache и restarts. Не обещать ускорение или уменьшение памяти до замеров; production-лимиты не повышать.

Готовность: все routes inventory покрыты; новые auth bypass не появились; public outputs/commands и persisted state совместимы; нет скрытого Python web fallback; количество постоянных app-контейнеров не выросло; CI и review без нерешённых замечаний.

7. Риски и восстановление

Основные риски: расхождение JWT/roles, доверие proxy headers, потеря идемпотентности, изменения сериализации дат/HTML, опасные backup paths и потеря bootstrap миграций при удалении Python main. Их проверяем до удаления соответствующего пути.

До одобренного выката существующая production-схема работает без изменений. Локальный rollback — старый web image/Compose с тем же schema contract; не откатывать БД поверх новых данных. В будущем при rollout переключать один web, не запускать обе миграционные команды одновременно. Изменение формата данных или auth, препятствующее возврату, требует обновления плана и отдельного решения.

8. Решение и разрешения

К одобрению: реализация этапов 1–4 на Луне с независимой проверкой и подготовкой PR/review по этапу 5. Компоненты разделены по назначению; web заменяется без добавления постоянного контейнера. Оставшиеся контейнеры сейчас не объединяем.

Пользователь одобрил ревизию 1 ответом «да давай — погнали». Разрешены реализация на Луне, локальные изолированные проверки, commit/push и PR/review по описанным этапам. Merge, публикация images и production rollout требуют отдельного разрешения. Исполнение начато с фиксации baseline контрактов; этапы реализации и QA ещё не завершены. Реальные сайты, каналы доставки, shared browser и Readeck не используются для локального gate.

Открытые вопросы для discovery: полный перечень синхронных backend операций и действующая защита cookie mutations. Их исследуем без запросов к пользователю, пока контракт можно сохранить; материальные изменения выносим как конкретную дельту.

9. Журнал исполнения

Ревизия 1 одобрена. Локальная чистка Python сохранена отдельно: commit a4a11b2, ветка codex/remove-unused-python-processing, без push/выката. Web реализуется в codex/web-api-components от 667cb3d; остальные dirty документы сохранены.

Baseline: реальные ASGI-запросы без lifespan подтвердили различия HTML Basic и API JWT/cookie, 301 redirects, 404 trailing-slash, 401/403. Обнаружены и явно учитываются исправления случайных ошибок: успешный Basic login в Python падает с 500 из-за обращения к строке как к credentials; /auth/me с Basic падает из-за отсутствующего exp. Go вернёт документированный token/user response без изменения полномочий. При ошибке БД публичные read API будут возвращать ограниченный 503, а не выдуманную статью с 200; реальная статья ID1 читается из БД. Это явные исключения differential parity, согласованные с требованием не выдавать ошибку за успешный результат.

Auth/public реализация разбита на независимые Luna lanes с фиксированным интерфейсом. Root проверяет общий контракт. Независимый Go race + PostgreSQL17, vet/module verification и Linux amd64/ARM64 build прошли. Python regression после private bridge: 1055 passed; последующие targeted ASGI/gate проверки: 27 passed. Полный Docker gate выполняется итеративно. Docker29 не публикует loopback-порт на internal network; изоляция сохранена, для QA добавлен временный фиксированный relay через docker exec. На реальной bootstrap-схеме обнаружены и исправлены пропущенные ORM client defaults (UUID задания, значения и timestamps CRUD), затем двойной private API prefix. Прогон v7 подтвердил Go web → durable queue → worker → executor → ingestion/collector/processing, успешные receipts всех 8 источников (4 RSS, 1 Telegram, 3 Page Monitor), обработанные статьи и идемпотентность occurrence; private analysis/Telegram/download также прошли. Gate выявил расхождение ограничений backup upload/cleanup в worker mode, они приводятся к прежнему 409. Финальный полный pipeline gate v8 прошёл (25 checks): все 8 source receipts succeeded, без ошибок, создано и обработано 2 fixture статьи по тестовому лимиту; ни одного OOM или неожиданного рестарта. В браузере проверены лента, modal/full text, пустой поиск, Basic admin на URL без credentials, dashboard/categories/stats/summaries, создание отключённого источника, сохранение/повторная загрузка Telegram settings, editor расписания и mobile390/dark без горизонтального overflow. Найдены и исправлены отсутствующие DTO-поля списка бэкапов; повторный UI gate для этого исправления ещё нужен. Worker recovery gate прошёл с Go web. Полная Python regression: 1078 passed, 22 subtests. Actual scheduler и расширенный ingestion gate ещё проверяются, CI/review не выполнены. В синтетическом ARM64 Docker gate web использовал примерно 9–10MiB; production-ускорение/память не заявляются. PostgreSQL16 race suite также прошёл. Все изменения локальные, task-owned стенды очищаются после каждого прогона; production не затронут.
