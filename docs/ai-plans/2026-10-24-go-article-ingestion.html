3. Архитектурное решение

Go scheduler → existing durable jobs → Go job worker
                                      ↓
                              Python executor / orchestrator
                                 ↓ collect-and-save
                    private Go ingestion → PostgreSQL News
                                 ↓ existing API
                    Go collector/extractor → HTTP / shared Cloak
                                 ↕ narrow selector-assistance API
                              Python executor (existing AI)

Python executor: existing article processing / AI → digest / delivery

Отдельный Go ingestion process, новый модуль go-ingestion/. Это DB-aware слой приложения, а существующий collector остаётся без БД. Не переносим orchestration всего pipeline в этом PR: Python вызывает один законченный этап и получает только bounded status/counters. Доступ к Go extractor — через существующий API, без прямого CDP. Новый сервис переиспользуется через внутренний HTTP-контракт; standalone manual collection API в этом этапе не добавляется.

Новый ingress принимает только доверенный envelope существующего durable job. Новый сервис не является вторым владельцем очереди и не отправляет сообщения. Разрешённые kinds на первом этапе — news_processing и сборочная часть news_digest только при run_processing=true, как в проверенном background_execution.py::execute_job. Остальные kinds и source probes сохраняют текущий путь.

Режим интеграции: новый явный ARTICLE_INGESTION_MODE=python|go, repository default python для безопасного включения после отдельного выката. В режиме go обязательны URL/token сервиса и существующие Go source modes; при недоступности — явная ошибка, без переключения на Python. Опциональность — только граница переключения и отката, целевая production-схема использует Go.

4. Новые контракты и защита записи

Private ingestion API v1 — новый
POST /internal/v1/ingestion/runs, GET /internal/v1/ingestion/runs/{run_id}, POST /internal/v1/ingestion/runs/{run_id}/cancel, health/readiness. Bearer authentication, bounded strict JSON, version=1. Envelope: job_id, attempt_generation, worker owner/generation/backend PID, executor_instance_id и deadline UTC. Не принимает произвольные SQL/schema/source credentials и caller-supplied targets: sources читает сам из ограниченной News schema. Ответ — run_id, state, per-source outcome/code и счётчики; без тел статей, private config или HTML.
Idempotency и восстановление
Уникальный run на (job_id, attempt_generation); digest неизменяемого envelope, повтор с другим содержимым — conflict. Повтор POST после потерянного ответа возвращает тот же run, не запускает второй проход. Перезапуск сервиса восстанавливает committed per-source progress. Новая попытка job может повторить сетевой сбор, но уже сохранённые статьи не дублирует. Одновременно один проход данного job; не создаём неограниченную in-memory очередь.
Fencing
Каждый commit валидирует настоящую advisory lease Go worker, heartbeat и deadline по DB time, running job/attempt/owner и активный executor receipt. Порядок блокировок соответствует RemoteJobFence.transaction_fence: worker status → job → ingestion run → source state. Проверка и запись в одной транзакции; отдельный GET health не заменяет fence. Cancellation помечает run отменённым под теми же блокировками; после подтверждённого cancel новых commits быть не может. При неизвестном результате отмены Python сначала сверяет run, не объявляет этап завершённым и не запускает альтернативного writer. Перед recovery старого run проверяется отсутствие живого владельца исполнения.
DB privilege boundary
Новая отдельная роль: SELECT sources/config и необходимых job/receipt/lease данных, SELECT/INSERT/UPDATE только разрешённых ingestion-полей articles, source fetch metadata и новых ingestion tables/sequences. Без DELETE статей, DDL, доступа к AI secrets/settings и scheduler schema. Поскольку SELECT FOR UPDATE требует дополнительных прав, роли даются только необходимые column-level UPDATE для row locks на fence rows; отдельный negative privilege test доказывает запрет изменения owner/state. Discovery шага 1 завершено: выбран narrow SECURITY DEFINER fence, который только валидирует и удерживает блокировки до commit pgx-транзакции. Бизнес-запись остаётся Go, runtime не получает UPDATE на queue/worker rows. Function schema-qualified, PUBLIC execute отозван; search_path фиксируется на pg_catalog и фактической News schema, lease hash использует её явное имя. Новый migration ID: 012_article_ingestion. Проверка минимальных grants на реальном PostgreSQL обязательна до приёмки.

Предлагаемые новые таблицы: article_ingestion_runs, article_ingestion_source_runs (пер-source receipt/progress и digest config), source_collection_state (bounded Page Monitor cursor/segments/acks + версия). Additive migration; никакой конвертации/удаления существующих статей и cursor reset в migration. В БД сохраняются только bounded state и метрики, не captured HTML.

5. Инварианты данных и поведения

  • Schema parity: title/url/content/summary/image_url/media_files/published_at/fetched_at/hash и ad metadata по существующим моделям. Новая статья: pending, processing_attempts=0, processed=false; остальные flags явно соответствуют ORM defaults — нельзя рассчитывать на Python defaults при SQL INSERT. UTC и JSON/null различия покрыть fixtures.
  • URL dedup: основной URL плюс Telegram/message/original link проверяются как сейчас. Completed/processed material не перезаписывается. Для незавершённого — только текущий разрешённый набор enrichment-полей; не сбрасывать AI stages, attempts, retry_wait/exhausted и категории. Конфликт unique URL не валит весь проход.
  • Title/hash parity: strip/lower; одинаковый title внутри source за последние 7 дней, batch seen sets как в Python; SHA-256 от title + ":" + url. Это существующие правила, не новая эвристика похожести. Unicode lowercase и Python JSON/hash Page Monitor сравниваются golden fixtures. Не вводить глобальный unique title и не удалять дубли в старых данных.
  • Конкурентные записи: один ingestion save writer сериализуется коротким transaction advisory lock; UPDATE существующих articles под row lock и с повторной проверкой processing flags после блокировки. AI может параллельно завершить статью: ingestion не затирает его результат. Сеть вне lock. URL conflicts обрабатываются через bounded retry/savepoint, не через продолжение в aborted transaction.
  • Изменение source: перед commit проверить source существует, enabled и collection-relevant config fingerprint не изменился. Удалённый/изменённый source получает skipped/config_changed; cursor старой конфигурации не переносится. Не перезаписывать admin config. Политика last_fetch/error_count/last_success фиксируется по текущим путям, не превращать failed/deferred в success.
  • Page Monitor: partial-prefix сохраняется; cursor продвигается только до committed/duplicate items. Сбой перед commit — повторяем; после commit до ответа — читаем receipt. Limit не подтверждает невключённый хвост. Empty/resource_limit/deferred не подтверждают непросмотренные материалы. Старое состояние процесса не объявляется durable; при первом Go запуске новый bounded scan безопасен благодаря DB dedup.
  • Telegram: сохранить исходные message/original links, media и ad markers; enrichment использует существующий extractor API, не удерживает SourceManager batch slot и не теряет пост при timeout. Не менять правила парсинга канала и ограничения collector.
  • Admission: существующие batch/source limits и различие busy/deferred/resource_limit/unavailable сохраняются. Бounded wait, не tight loop; отсутствие slot не расходует article processing attempts. Не повышать число вкладок и не вводить новые произвольные большие memory limits.

6. AI остаётся Python: узкий мост для селекторов

Нельзя незаметно отключить обучение Page Monitor, но переносить AI в Go тоже не нужно. В Python executor добавить authenticated internal adapter к существующим get_page_structure и _study_source_structure. Go запрашивает только нужные learned selectors, а при прежних условиях study передаёт bounded HTML уже захваченной страницы; Python вызывает прежний analyzer и сохраняет patterns прежним способом. Go перепарсивает тот же snapshot через существующий parse API — без повторной навигации.

Запрос связан с активным job/attempt/source и ограничен deadline, одним study на snapshot, максимальными payload/response размерами не выше существующего Page Monitor контракта. Adapter возвращает только validated selectors/version. У него нет API произвольного prompt, URL fetch или изменения source config. При сбое study сохраняем валидный extracted prefix, как сейчас. HTTP handlers executor не должны блокироваться ожиданием ingestion: callback обслуживается параллельно; DB write lock на время ожидания не удерживается.

AI client, prompts, analyzer, Gemini model и формат записанных patterns не меняются. Этот adapter — изменение transport, не AI-реализации. Fixtures доказывают прежнюю последовательность load → optional study → same-snapshot parse и fencing всех Python writes.

9. Риски, откат и открытая проверка

Главные риски — отличие Python/Go normalization и timestamps, потеря ack при partial scan, late writes после отмены, расширение DB privileges, циклическое ожидание selector callback. Для каждого есть обязательный fixture выше. Совместная News DB — сознательная граница этого этапа; отдельную БД/перенос ownership всей модели не делаем.

Ограниченная discovery до кода store: проверить минимальные права для transactional fence и точный набор current selector-memory storage dependencies. Метод: прочитать store/job fence/extraction memory, реализовать isolated SQL permission proof и golden load/study fixture. Результат — выбранная privilege strategy и зафиксированный callback contract в этом же плане. Если нужны широкие grants или изменение AI storage/behavior, зависимая работа останавливается и согласуется дельта; незаметного расширения нет.

Откат будущего выката: приостановить dispatch, дождаться drain либо подтверждённой cancellation, остановить ingestion, проверить отсутствие его writers и только затем включить прежний Python collection mode. Данные и additive tables оставить; старый image должен работать с добавленной схемой. Не восстанавливать backup поверх новых статей, не сбрасывать cursor/queue/receipts, не удалять volumes. Общий browser и Readeck не перезапускать. Процедура production switch и реальные immutable image pins появятся только при отдельно разрешённом выкате.
