Обработка статей на Go

Версия 1 · 26 октября 2026 · Одобрено пользователем · Реализация начата.
Пользователь одобрил версию1 сообщением «Погнали». Основание — PR #27, слитый и выкаченный как b1625d0. Проверенный checkout cc482ef имеет тот же tracked tree, что origin/main. Посторонние локальные изменения сохранены.

Цель: Go самостоятельно выбирает статьи, вызывает существующий экстрактор и Python AI, сохраняет результаты и назначает повторы. Python больше не управляет обработкой отдельных статей. Промпты, модели и смысл AI-результатов сохраняем.

Существующий поток заданий: Go scheduler → Go job worker → Python executor.
После переноса: Python executor вызывает Go article processor → тот вызывает Go extractor и узкий Python AI API → Go атомарно сохраняет статью, категории и итог попытки → Python продолжает дневные сводки и доставку.

AI API возвращает структурированный анализ и не записывает поля Article/ArticleCategory. Go решает, какие проверенные поля принять и когда повторять. Существующие Python AI/prompts могут читать справочники; learning bridge сохраняет только свою существующую статистику, не результаты обработки статьи.

Вне этапа: production и его БД, выкаты и публикация образов, браузер/Readeck, настройка лимитов, worker heartbeat bug, новая очередь или scheduler, переписывание AI и доставки. Реальные сайты, модели и сообщения в тестах не используются. Остановленный мониторинг не включаем.

2. Что подтвердилось в коде

  • orchestrator.py::_process_unprocessed_articles сейчас выбирает статьи, увеличивает attempts до сетевой работы, сохраняет recovery deadline и outcome. process_selected_articles и reprocess_failed_extractions используют тот же pipeline.
  • AIProcessor.process_article_outcome сохраняет успешные стадии при последующем сбое; get_summary_by_source_type пока смешивает smart filter, extraction и AI. Поэтому обернуть весь этот метод HTTP-ручкой недостаточно — оркестрация останется Python.
  • processing_outcome.py::outcome_fields возвращает попытку для busy/native_browser_busy, но настоящие ошибки исчерпывают бюджет. Нельзя заменить это одним generic retry.
  • Категории сохраняются вместе с флагами статьи в одной транзакции через существующее отображение AI-category → display category/Other. Готовая summary может использоваться без повторного извлечения архивного текста.
  • У Python extractor adapter есть learned-pattern и stability side effects. Их нельзя молча потерять при прямом вызове Go extractor.
  • У go-ingestion уже есть fenced run/receipt и отмена. Его SQL fence разрешает только ingestion-совместимые job kinds; нельзя без проверки использовать его для selected reprocess.

Репозиторные defaults: MAX_WORKERS=5, batch=25 (допустимо до100), attempts=3, retry=1800/21600 секунд, attempt timeout=600 секунд, text limit=100000 символов. Это не снимок настроек production. В переносе сохраняем действующие значения и отдельные ограничения smart filter, не повышаем их.

3. Предлагаемая архитектура

Отдельный приватный go-processing/ сервис. Его можно улучшать и переиспользовать отдельно от сбора. Он запускает только принятый run; своего периодического loop/scheduler, брокера и отдельной worker lease не получает. Параллелизм ограничен существующим бюджетом, общий браузер остаётся с прежними двумя слотами.

Расширить go-ingestion было бы вариантом с меньшим числом контейнеров, но это связало бы сбор источников с ожиданием AI и обработкой статей. Для выбранной пользователем цели разделения сервисов рекомендуем отдельный processor.

Новые приватные контракты — предлагаются этим планом

  • POST /internal/v1/processing/runs, GET /internal/v1/processing/runs/{id}, POST .../{id}/cancel, GET /healthz. Версия1; отдельные ARTICLE_PROCESSING_URL/TOKEN. Детерминированный run ID из job ID и attempt generation; конфликтующий повтор envelope —409, точный повтор возвращает существующий run.
  • Run envelope содержит существующий job fence: job/attempt, owner/generation/backend PID, executor instance и deadline. Допустимая операция и selected IDs/force/dry_run сверяются с canonical job kind/payload в БД. Клиент не может расширить выборку произвольным body.
  • Узкий AI callback в текущем Python executor: анализ уже подготовленного bounded текста через существующий AIClient. Отдельный ARTICLE_AI_TOKEN, не выдаём processor токен управления Python jobs. Связываем callback с активным job/executor fence, article attempt и fingerprint входа; проверяем identity до вычисления и применения ответа.
  • Extraction context/feedback bridge ограничен чтением learned pattern и записью существующих learning/stability результатов. Он не извлекает статьи, не управляет повторами, не принимает произвольный Python/SQL и не пишет Article/ArticleCategory. В будущем его можно переносить отдельно.
  • Ответ processor содержит счётчики и ограниченные исходы/коды ошибок, совместимые с durable job receipt; без article body, промптов и сырых ответов AI в логах/метриках. Python executor ждёт processor, затем выполняет неизменённые сводки/доставку.

Изменения моделей, промптов и fallback внутри AI-провайдера сюда не входят. Не используем get_article_summary_with_metadata как «AI endpoint»: он сам управляет извлечением. Вызываем compute-часть с готовым текстом; source-specific extraction/fallback решения выполняет Go.

4. Данные, транзакции и восстановление

  • Новые additive таблицы article_processing_runs и article_processing_items — run/claim identity, прогресс и конечные receipt. Это предлагаемые имена; migration не изменяет существующие публичные состояния статьи и не копирует тела/промпты в receipts.
  • Отдельная роль processor: только нужные чтения, processing-поля Article, scoped ArticleCategory и новые receipts. Нет удаления статей, управления очередью/lease, записи дайджестов или административных прав. Новый fenced entry/commit guard проверяет четыре допустимых kind/payload; SQL и минимальные grants проходят отдельный review на ограниченной роли.
  • Одна короткая транзакция claim → извлечение/AI вне транзакции → короткая транзакция save. Не держим worker/job/article row locks или общий DB write lock на время HTTP/AI. Порядок блокировок фиксирован и одинаков на claim/commit.
  • Перед category delete/insert и записью результата проверяем актуальный fence, claim/attempt и входной snapshot. Сначала блокируем/проверяем нужную статью, затем атомарно меняем категории и поля. Устаревший результат не может удалить новые категории или перезаписать новые данные.
  • Успешные summary/category/ad стадии переживают следующий сбой. Пустая summary, неверные категории и challenge HTML не становятся success. Advertisement остаётся terminal по текущим правилам, даже если необязательная summary отсутствует.
  • busy/native_browser_busy остаются локальным ожиданием: попытка не расходуется, число не становится отрицательным, partial fields сохраняются. Retry-After валидируется; ошибки провайдера/неверный input не маскируются под busy. Admission wait остаётся внутри текущего общего бюджета.
  • Падение после claim восстанавливается из durable deadline; final attempt становится exhausted по тем же правилам. Отмена/потеря worker lease запрещает поздний commit; timeout, cancel и потерянный submit/ack сверяются по run receipt. Не создаём второй механизм владения очередью.
  • Run replay и применение в БД идемпотентны. Exactly-once оплату AI-провайдера не обещаем: при потерянном ответе и неизвестном исходе действует документированная политика настоящей ошибки/повтора, без скрытых бесконечных повторов.

6. Приёмка до PR

  • Обычный RSS, Telegram и Page Monitor; короткий Telegram пост, unsupported/non-article URL, metadata-only/challenge input, большие архивные данные, Cyrillic/emoji. В Go различаем byte limits и Unicode code points: Python len нельзя заменить len(bytes).
  • Summary-only/category-only/ad-only recovery; valid partial stage + ошибка следующей; force extraction использует свежий вход даже если improvement-only policy сохраняет более длинный архивный текст. Invalid/empty AI output не превращается в completed.
  • Нормализация категорий, display mapping/Other, finite confidence и local-category isolation. Не меняем policy при порте. Category mapping failure откатывает целую запись конкретной статьи, инфраструктурный сбой прерывает job до доставки.
  • Stable-ID batching, per-source/cycle limits, sparse IDs, существующий published_at/date filter и NULL publication dates. Не подменяем его fetched_at. Параметры selected IDs, force, preserve completed stages, dry_run и повторного reset проходят тот же pipeline.
  • Многократный busy на каждой позиции бюджета attempts; malformed/boolean/NaN/огромный Retry-After; настоящий последующий сбой; crash на последней попытке. Есть проверка сохранности исходного текста и предыдущих успешных стадий.
  • Дубликат submit, потеря ack/HTTP ответа, отмена, worker/executor restart, старый generation/backend PID, истёкший deadline, две одинаковые run заявки, overlapping selected/background claims, смена входа во время AI. Поздние ответы не пишут данные; provider keys остаются только Python.
  • Ограниченная DB роль: позитивная реальная transaction и негативные queue/article-delete/foreign-claim права. Реальный Go processor и настоящие PostgreSQL16/17; внешние сервисы только fake во внутренней сети.
  • go test -race ./..., go vet ./..., go mod verify в новом module; существующий Python suite; актуализированные worker/scheduler/ingestion orchestration gates; реальный новый processing gate. Linux amd64 и ARM64 сборки плюс локальный Mac ARM64.
  • Реальный локальный admin/CLI запрос создаёт durable job; Go обрабатывает синтетические статьи, Python fake AI вызывается, новые поля/категории сохраняются и публикация отдаёт только допустимые результаты. Тест отправки — только fake Telegram/Telegraph.
  • Память/CPU, длительность и число запросов измеряются на одинаковом synthetic workload. Не обещаем ускорение AI или экстрактора от одного переноса. При заполненном Docker-диске source-mounted прогон не подменяет финальный CI-built image gate.

7. Риски, возврат и одобрение

Главные риски — потеря partial stages, расход attempts на busy, неатомарные категории и запись от старого worker. Поэтому fixtures и fencing идут раньше переключения. Новые receipts остаются additive. Возврат к прежнему app image возможен только после остановки/fencing новых processing runs; не запускаем Python и Go писателей параллельно, не сбрасываем Article и не восстанавливаем старую БД поверх новых данных.

До одобрения разрешены только inspection и этот план. Одобрение версии1 запускает реализацию на Луне, независимую проверку, затем обычный PR/review workflow. Оно не разрешает merge, публикацию образов, migrations/выкат в production, изменение браузера/Readeck, реальные AI/site тесты или переобработку пользовательских статей. Дальнейший rollout потребует отдельного явного разрешения.

Решение для одобрения: отдельный Go article processor с собственными run receipts, текущим Go job worker и узким Python AI/learning bridge; переносим все четыре processing-kind, сохраняя публичные результаты, данные и retry policy.

8. Реализация и локальная приёмка · 26 октября

Реализован отдельный go-processing/: canonical job payload, SQL fence, additive migration 013, ограниченная runtime DB-роль, bounded batches/goroutines, HTTP-first/native extraction policy, partial stages, retry/exhausted, атомарные категории и защита от устаревшего результата. Старые Python article processor/SmartFilter/retry runtime удалены.
