Минимальный .env, настройки и онбординг

Редакция 3 · 29 октября 2026 · Одобрено · Реализация, приёмка и review

Результат: типовая установка запускается без ручного составления DSN, паролей БД и служебных токенов. Владелец настраивает приложение в браузере. Предлагаемый исполнитель — Terra 6.1, затем один итоговый PR и независимое review. Этот документ не разрешает изменения production, публикацию образов, реальные AI-запросы или отправку сообщений.

1. Цель и минимальный .env

# Для публичной установки; localhost имеет рабочий default
SITE_BASE_URL=https://news.example.com

Используем существующее имя SITE_BASE_URL, без нового алиаса SITE_URL. API-ключи, пароль администратора, JWT signing key, master key шифрования, пароли PostgreSQL и внутренние токены пользователь в этот файл не вводит. Они либо вводятся через интерфейс, либо автоматически создаются и сохраняются в приватном постоянном состоянии установки.

Минимальность измеряется количеством обязательных действий владельца, а не переносом прежних 33 строк в другой редактируемый файл. Технические параметры получают проверенные defaults. Семь разных подключений runtime сохраняют назначение и права; пользователь перестаёт собирать их вручную. Нельзя заменять их общим привилегированным DB-пользователем.

Внешний PostgreSQL поддерживается расширенным локальным мастером установки. Адрес и доступ к внешней БД нужны до старта web и не могут впервые задаваться в ещё не работающем браузерном интерфейсе. После подключения браузер показывает готовность хранилища без паролей и технических полей пулов.

2. Что подтверждено в текущем коде

  • Рабочий source HEAD e37f687, наблюдавшийся origin/main — 4c9b53a; перед разработкой проверить актуальный main и создать свежую codex/-ветку. Несвязанные локальные изменения не включать в работу.
  • .env.example содержит 33 переменные и 7 runtime DSN: web, executor, scheduler, worker, ingestion, processing, execution. docker-compose.example.yml вручную связывает роли, токены и два локальных PostgreSQL.
  • go-web/internal/config/config.go требует ADMIN_PASSWORD при старте; JWT_SECRET при отсутствии заменяется паролем администратора. go-web/internal/auth/ реализует Basic/JWT/cookie API, admin pages и опциональный trusted forward auth; отдельного хранилища локального администратора сейчас нет.
  • go-domain/cmd/news-domain/main.go вызывает StartupAISettings до обслуживания запросов; пустая новая установка не имеет отдельного режима онбординга. Некоторые Telegram-настройки и ключи захватываются при создании объектов.
  • AI provider/model profiles с CAS уже есть в go-domain/airuntime/settings.go. Источники, категории, Telegram chat IDs и расписания уже управляются через БД/API; их не нужно повторно переносить в новую систему.
  • go-domain/backup/create.go сейчас копирует .env и другие входные файлы в архив. HTTP restore в go-domain/webbackend/backups.go возвращает 501. Нельзя считать перенос master key решённым существующим restore API.
  • go-ai v0.1.0 — независимая библиотека. Чтение env, онбординг, БД и хранение секретов остаются задачей News.

При подготовке плана читались исходники и публичные технические справочники. Production, реальные ключи и внешние AI/Telegram API для этого плана не проверялись; тесты реализации ещё не запускались. Старые memory-снимки с Python не использованы как описание текущего runtime.

Единственный источник истины для управляемых настроек — БД. Env нужен для старого режима и одноразового импорта. После успешного adopt или миграции ключа его удаление либо ошибка расшифровки не вызывает скрытый fallback на env. Админка показывает эффективное значение и где оно хранится; изменения через CAS, конфликт — 409 и предложение перечитать данные.

Background получает только разрешённый несекретный snapshot runtime-настроек через отдельный read-only private API с существующей подходящей purpose-аутентификацией. Ни provider keys, ни master key, ни web admin password этот ответ не содержит. Snapshot фиксируется на начало задания, запрашивается вне lease mutex/DB write transaction; работающий job завершается со своей revision. Новые задания получают новую revision, без рестарта. При недоступности настроек нет молчаливого перехода на другие значения.

4. Автоматическая установка и доступ к БД

Новый managed Compose использует существующие image families; новая постоянно работающая служба не появляется. В executor image добавляется Go-команда newsctl. Подготовка — одноразовый setup profile без Docker socket; существующий one-shot migrate выполняет provisioning и schema migrations, затем запускаются runtime-сервисы.

# Предлагаемый интерфейс installation bundle
docker compose --profile setup run --rm --no-deps setup prepare
docker compose up -d

Это будущие команды, не существующий сейчас интерфейс. CI собирает bundle из нового managed Compose, минимального env example и quickstart. prepare работает только с разрешёнными state volumes; provisioning подключается к БД после healthcheck. Подготовка не стартует остальные сервисы и не требует уже существующих секретных файлов. Повторный prepare идемпотентен и никогда автоматически не меняет созданные ключи/пароли.

  • В свежем managed-профиле один PostgreSQL 17 с раздельными news/scheduler DB и ролями компонентов. Проверять также совместимость с PostgreSQL 16. Это выбор нового локального профиля, не перенос или объединение действующих production-БД.
  • Setup генерирует случайные отдельные пароли и purpose-токены, создаёт runtime manifest и выдаёт каждой роли только её файлы. Bootstrap DB-owner credential видят только PostgreSQL и одноразовая maintenance-команда, не web/background/domain.
  • Provisioner использует существующие ingestion/processing role templates и добавляет проверенные web/domain/worker/execution grants. Предусмотренные fence EXECUTE grants сохраняются, PUBLIC не получает их. Владелец не вводит семь DSN и не выбирает размеры пулов.
  • Файлы секретов — 0600, каталог — 0700, правильный UID владельца; каждый runtime получает только собственный read-only mount. Web имеет свой signing key, domain — отдельный encryption key. Родительский store нельзя монтировать во все контейнеры.
  • При существующих данных БД и отсутствующем/повреждённом state нельзя объявлять установку новой и генерировать замену master key. Проверяются manifest и признаки уже инициализированных данных; требуется явное recovery/adopt.
  • Для внешнего PostgreSQL локальный newsctl prepare --external-db читает bootstrap credentials интерактивно или из защищённого файла, без argv/logs. Если CREATE ROLE/DB недоступны — принять предварительно подготовленный role bundle с проверкой прав; не расширять права и не подставлять DB owner в runtime.

Runtime-file reader — маленький News-компонент с version/service validation и allowlist полей; не записывает данные в os.Environ. Общий stdlib reader предлагается в go-tools/runtimeconfig, без зависимости от fixture-кода. У standalone extractor/egress — самостоятельная поддержка узкого secret-file контракта, без зависимости от News SettingsService. Меняется только загрузка конфигурации: CDP, browser lifecycle и изоляция трафика не меняются.

5. Первый вход и онбординг

  1. Хранилище. Экран показывает готовность DB и компонентов. Технические DSN и пароли не выдаются браузеру. Неверный DB bootstrap исправляется локальным установщиком, не публичным HTTP-редактором.
  2. Администратор. Первое создание разрешено только на неинициализированной установке с одноразовым setup token из локального установщика. Владелец отдельно одобрил локальное исключение HTTP: только явный LOCAL_HTTP_SETUP, loopback SITE_BASE_URL и Compose publication на 127.0.0.1; публичная установка требует реального TLS или явно доверенного TLS proxy. Host/X-Forwarded-Proto сами по себе доверия не создают. Токен живёт 15 минут, в БД хранится hash, передаётся в теле HTTPS-запроса, не в URL/HTML/logs/localStorage. Выпуск нового токена — явная локальная команда. Создание аккаунта и погашение токена — одна транзакция; из двух одновременных запросов успешно создаёт администратора только один. После этого /setup не становится публичным из-за пропуска следующего шага.
  3. AI. Выбрать Gemini/OpenAI, ввести ключ и модели. Сохранение не делает внешнего запроса. Статусы «не настроен», «ключ сохранён, не проверен», «проверен» различаются. Проверить подключение — отдельное явное действие с предупреждением о реальном API-вызове.
  4. Telegram — необязательно. Bot token, основной и служебный chat ID, доставка выключена по умолчанию. Telegram-источники публичных каналов не требуют bot token. Сохранение и диагностика не отправляют сообщения; кнопка тестовой отправки отдельная, с явным адресатом.
  5. Источники и категории. Использовать существующие формы RSS/Telegram/Page Monitor, без дублирующего импорта и новых источников за пользователя. Сохранять промежуточный прогресс.
  6. Расписание и запуск. Показать итог и недостающие возможности. Создать расписание выключенным; включение — явный шаг. Первый проверочный сбор не публикует в Telegram. Реальная доставка включается отдельно после проверки адресата.

После первого входа шаги продолжаются в обычной admin-сессии. Необязательные шаги можно пропустить и вернуться к ним через настройки. Без AI/Telegram web и управление работают, соответствующие операции показываются как недоступные; отсутствие интеграции не превращает весь контейнер в unhealthy. Нельзя ставить AI-задания в очередь или тратить article attempts, пока AI не настроен. Не добавлять ради этого новый job-state без необходимости: валидация до enqueue и выключенное расписание покрывают новый bootstrap.

Для существующей установки нет нового публичного захвата администратора и обязательного повторения мастера: показать заполненные шаги и предложить недостающие. Старые источники, категории, расписания, enabled/due instants и доставка сохраняются при adopt. Автоматически запускать сбор, AI-пробы и Telegram при импорте нельзя.

6. Секреты и авторизация

Provider/Telegram credentials шифруются AES-256-GCM с random nonce, version/key_id и AAD, связывающим installation, credential type и provider. Master key не лежит в БД и не передаётся web/background. Web кратковременно принимает ключ от авторизованного администратора для записи и проксирует его в domain; не хранит и не получает его обратно. Это защита отдельного SQL dump, а не обещание защиты при полном захвате приложения/хоста. Стандартная библиотека Go: AEAD/random nonce.

GET возвращает только configured/revision/updated_at, без plaintext и частичных фрагментов ключа. Запись и удаление — admin-only, CSRF/Origin защита для браузерных запросов, CAS. Пустое поле означает «не менять» только при явно определённой форме; удаление — отдельная операция. Повреждённый ciphertext/неверный key_id не маскируется отсутствием ключа и не вызывает fallback. Секреты не попадают в usage, ошибки, логи и HTML. Ротация provider key действует на новые операции; существующие retry сохраняют snapshot модели и credential revision.

Локальный admin password хранится как salted Argon2id hash, а не обратимо зашифрованный пароль. Начальная политика — минимум m=19 MiB/t=2/p=1 и не более двух одновременных password-hash проверок; измерить время/RSS на ARM64/Linux в текущем бюджете. Сохраняются rate-limit/lockout. Это минимальная конфигурация OWASP, а не результат проведённого benchmark. Подобрать совместимую исправленную x/crypto версию без неоговорённого повышения toolchain.

Basic/JWT/native API и опциональный Forward Auth сохраняются. В managed web admin-pages принимают корректную cookie-сессию; новая browser-сессия HttpOnly/Secure при HTTPS и SameSite. Нельзя включать TrustForwardAuth по одному заголовку или автоматически доверять произвольным proxy. Новая установка генерирует отдельный signing key; fallback JWTSecret=admin password в managed-режиме отсутствует. Сброс пароля — локальная CLI recovery-команда, без публичного reset endpoint.

При adopt сохранить эффективный прежний signing key, включая старый fallback, и действующие claims до их исходного TTL. Переход к credential revision предусматривает ограниченный legacy grace period; смена пароля отзывает также legacy-сессии. Не вводить аккаунты читателей, invitations, обязательный SSO или новую многопользовательскую модель.

7. Данные и контракты

Существующие settings keys и AI CAS остаются совместимыми. Новые версии typed groups покрывают AI/Telegram/операционные настройки; модели и обычные параметры не шифруются. Нужны аддитивные таблицы: singleton состояния установки/онбординга, singleton локального admin credential, encrypted integration credentials с revision. Имена и очередной номер миграции сверить с текущим ledger непосредственно перед реализацией; существующие 001–015 не переписывать.

  • SettingsService — один владелец в domain, но distinct компоненты settings, credentials, onboarding и auth. Общие JSON-контракты и purpose permissions позволяют менять реализацию, не создавать контейнер для каждой ответственности.
  • Предлагаемые новые endpoints: setup status/claim; admin installation progress; typed configuration GET/PUT; write-only integration credentials PUT/DELETE; read-only private runtime snapshot. Описать схемы, 401/403/409/422/503 и parity fixtures в OpenAPI до подключения UI.
  • Существующий /api/v1/ai/settings сохраняет форму и CAS; configured считается по effective credential resolver. Telegram token и chat IDs читаются snapshot resolver, а не только constructor env. Не выдавать расшифрованный ключ отдельным HTTP GET даже private web.
  • Новые grants минимальны: web видит auth и несекретные данные, domain — encrypted rows, прочие runtime роли не читают credentials. Не расширять их права до migration owner.
  • Режим legacy env остаётся временной совместимостью только без принятого managed manifest. Если managed state есть, ошибка файла/ключа закрывает зависимые возможности; нельзя тихо стартовать по старому env.

8. Переход существующей установки и восстановление

Новый newsctl adopt --dry-run читает канонический Compose/legacy config локально и показывает только имена групп, источники значений и необходимые grants. Применение — отдельная явно подтверждённая команда, идемпотентная по installation ID/revision. Сначала создать приватное состояние, импортировать конфигурацию/credentials, проверить паритет, только потом переключать runtime на role files. Ни массовой ротации токенов, ни новых DB-пользователей на месте существующих, ни удаления старых источников.

Импорт не переписывает shared PostgreSQL, браузер или соседние приложения. Перед будущим production adopt обязательно проверить ссылки других Compose/systemd на старый .env; если он нужен защищённому соседу, его нельзя удалять или сокращать в рамках News автоматически. Это блокирует соответствующий production-переход, но не локальную разработку managed-профиля. Старый конфиг удаляется только после отдельного успешного acceptance; нет автоматического продолжительного двойного управления.

Два режима backup. Обычный DB backup содержит ciphertext и явное указание, что для восстановления требуется состояние ключей. Отдельный переносимый recovery bundle включает DB dump, manifest и необходимое приватное состояние, но целиком шифруется passphrase, вводимой через терминал; passphrase не хранится внутри архива, argv или env. Не подкладывать открытый master key рядом с SQL dump и не продолжать копировать legacy plaintext .env в managed-архив.

Нужен проверенный offline newsctl restore: расшифровать и проверить manifest/key IDs, восстановить в пустую изолированную БД и role volumes, проверить decrypt и вход администратора. Применение поверх непустой БД по умолчанию запрещено. После восстановления расписания/доставка остаются приостановлены до подтверждения владельца; receipts сохраняются, старые пользовательские сессии отзываются явно. Веб-restore 501 не объявлять реализованным без отдельной реализации; в этом этапе достаточно полноценного CLI recovery.

При потере master key нельзя перегенерировать его поверх ciphertext: восстановить защищённое состояние либо явно повторно ввести интеграционные ключи через авторизованный recovery-процесс. Создание администратора не открывается повторно. Старые plaintext backups не удалять без разрешения владельца.

10. Проверки и критерии готовности

Все проверки ниже запланированы. Используются fake keys и изолированные HTTP/Telegram fixtures; нет реальных API-платежей, источников или сообщений.

  • Fresh install. Только SITE_BASE_URL; prepare/up с пустыми volumes; PostgreSQL roles/schema готовятся автоматически; повторный prepare/restart сохраняет ключи/ID и не создаёт второго администратора. Web/domain healthy в setup mode, фоновые действия не стартуют.
  • Изоляция. Проверки разрешений каждой роли, root DSN отсутствует в runtime, domain master key отсутствует в web/background/extractor; сервис не получает весь private store. Обход managed через legacy env запрещён.
  • Auth. Истёкший/повторный setup token, гонка двух claim, публичный повтор setup, неавторизованный credential write, CSRF/cross-origin, Basic/JWT/cookie/Forward Auth и password reset. Нагрузочная граница Argon2 не выходит за текущий memory budget.
  • Secrets. Нет plaintext в DB, обычном backup, GET API, HTML, usage и логах. Дубликат/повреждение ciphertext, чужой key_id/AAD и потеря volume — явный отказ. Key rotation при выполняющемся retry сохраняет snapshot. Удаление не оживляет env fallback.
  • Онбординг. Реальные UI/backend/PG, desktop/mobile/keyboard; оба fake AI provider, сохранение без вызова, смена модели, Telegram skip, ошибка/409/перезапуск. Две вкладки не перетирают настройку. Поле ключа очищается после записи, повторный GET возвращает только metadata.
  • Рабочий путь. Источники → сбор → AI → категории/реклама → дайджест → fake доставка. Первый тест без публикации; существующая доставка и receipt semantics не ломаются. Config-missing не тратит article attempts и не создаёт ложный processing failure.
  • Adopt. Изолированная копия legacy fixture: byte/semantic паритет effective config, DSN/auth и сохранённые источники/категории/расписания/due. Повторный импорт идемпотентен; ошибка до commit не активирует половину managed state. Runtime Env сравнивать как карты значений, не зависимые от порядка списки.
  • Recovery. Encrypted bundle → пустой PG и новые role volumes: ключи расшифровываются, admin входит, сообщения/dispatch выключены. SQL dump без ключа не запускает генерацию нового master key. Неверная passphrase/повреждение/непустая БД не приводит к перезаписи.
  • Общие gates. make test/vet; targeted race auth/settings/claim/credentials; существующий PG16/17 full image gate; Linux amd64/arm64 build и локальный Mac ARM64. Парсинг Compose и автоматическая проверка единственного необходимого пользовательского env параметра. Эти команды нельзя объявлять пройденными по наличию плана.

11. Риски, откат и граница одобрения

Самые существенные риски: публичный захват первой установки, потеря encryption state, незаметный fallback/дрейф при импорте, расширение DB прав и автоматическая отправка после recovery. Соответствующие отрицательные проверки обязательны до PR acceptance. TLS/proxy/DNS и полноценный multi-user/SSO redesign, Serbian localization, новый AI provider и изменения go-ai не входят в этап.

Новые таблицы и managed startup вводятся аддитивно. До переключения legacy режим продолжает работать; старые env credentials не удаляются установщиком. Если после managed adoption появились новые зашифрованные credentials, простой откат старого image их не прочитает: использовать проверенную версию managed reader либо явно экспортированный оператором legacy compatibility snapshot. Не обещать универсальный rollback одним git revert. Реальный production rollback требует отдельно проверенных configs и сохранённого key state.

После проверок удалять собственные disposable volumes/fixtures, role bundles, временные ключи, архивы, binaries и task caches, предварительно подтвердив владение. Не чистить пользовательские volumes и общий Docker/Go cache. Оставить компактные безопасные результаты, без реальных ключей и объёмных дампов.

На одобрение: эта архитектура и реализация managed bootstrap, типизированных настроек, encrypted credentials, onboarding, legacy adoption и CLI recovery на Terra 6.1. Реализация выполняется; полный набор приёмочных проверок ещё не завершён. Commit/push/PR — после соответствующего разрешения; merge, image publication, production adoption, изменение настоящих env/grants/volumes и реальные provider/Telegram проверки отдельно. Health, Assistant, shared browser и Readeck не затрагиваются.

Редакция 3: текущий Cloak и база без ручной настройки

Контракт

  • Новая локальная установка сохраняет автоматическое создание PostgreSQL, БД, ролей, паролей, схем и миграций. Пользователь не вводит DSN, имена семи ролей или SQL. Повторный запуск ничего не ротирует.
  • Добавить явный вариант подключения к существующему Cloak: перенести фактические параметры extractor/CDP/native proxy/egress и подключения News к существующим сетям в защищённые role manifests и Compose override. Не подменять native backend общим CDP и не обходить существующую egress-изоляцию. Не придумывать endpoint, network, лимиты или токены.
  • Для текущей установки автоматически извлекать подключения News и scheduler из защищённого канонического Compose-конфига. Показывать оператору только безопасное резюме; сохранять DSN, роли, search_path, scheduler topology и данные. Не требовать вручную собирать семь DSN.   • Установщик проверяет и применяет только согласованные аддитивные миграции News. При недостающих правах сообщает точный необходимый шаг, не расширяет права shared PostgreSQL автоматически. Базы, volumes и роли соседей не меняются. Свежий внешний PostgreSQL остаётся расширенным операторским режимом; он не должен усложнять обычную установку.
  • Не переносить БД на новый сервер, не менять PostgreSQL major version при adoption. Сохранить статьи, источники, категории, расписания/due instants, receipts, ключи и администратора. Импорт не запускает сбор, AI или Telegram.
  • Браузер и Readeck: никаких build/pull/recreate/restart, смены image/config/сетей/grants/лимитов. Разрешены только изменения конфигурации сервисов News в локальных fixtures. Production в этом этапе не меняется.
