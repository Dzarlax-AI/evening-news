Evening News: поэтапная миграция бэкенда на Go

Сохранено 16 октября 2026 года. Статус: предложение долгосрочного направления, полная миграция не одобрена и не начата. Это постоянная точка входа в проектный план; при дальнейшем обсуждении обновляем этот файл.

Цель — упростить приложение и эксплуатацию, постепенно заменить Python-бэкенд на Go, сохранить интерфейс и поведение системы. Экономия памяти, сроки и объем переноса заранее не установлены.

1. Что уже решено, а что предлагается

Отдельный Go-экстрактор и изолированные проверки native Go/Cloak worker уже одобрены в своих планах. Полный перенос приложения обсуждается как возможное продолжение. Сохранение этого документа не разрешает реализацию, изменение production, commit, push или публикацию образов.

Связанные документы: история Go-прототипа и выделения экстрактора, одобренный план native Go/Cloak, реализация, замеры и ограничения worker, подготовка экстрактора к production. Состояние длительных тестов в них — датированный снимок; перед решением о следующем этапе нужно проверить фактический результат.

2. Проверенная текущая архитектура

Интерфейс находится в web/templates/ и web/static/: Jinja2, CSS и обычный JavaScript. Отдельного React/Next-приложения нет. FastAPI в news_aggregator/main.py раздает статику, рендерит страницы и подключает API. Значительная часть данных ленты и фильтров загружается JavaScript через JSON API.

Фронтенд отделен по файлам, но зависит от серверных Jinja-шаблонов, конфигурации и авторизации. Публичные маршруты находятся в news_aggregator/public.py, админские страницы — в news_aggregator/admin.py, основной API — в news_aggregator/api/. Важно сохранить и /api/v1, и /api/public, а также /auth, URL страниц и редиректы.

Очередь, scheduler и монитор браузера стартуют через lifespan того же Python-приложения. docker/Dockerfile упаковывает веб-ресурсы и Python в один образ. Cloak работает отдельно; новая Go release unit находится в go/. PostgreSQL остается хранилищем данных.

3. Предлагаемая целевая структура

Браузер пользователя → Go-приложение → PostgreSQL
                          │
                          ├→ источники, очередь, обработка, AI API, дайджесты, доставка
                          │
                          └→ private extraction API → Go worker → Cloak
                                                                └→ контролируемый egress

Основной бэкенд — модульное Go-приложение. Экстрактор сохраняет отдельный жизненный цикл и возможность независимого обновления. Новые брокеры, отдельный frontend runtime и микросервис для каждого модуля не входят в предложение.

Внешний вид и браузерное поведение интерфейса сохраняются. Серверные части Jinja потребуется перенести на выбранный механизм Go-шаблонов; автоматическая совместимость синтаксиса не предполагается. CSS и JavaScript можно переиспользовать, проверяя API, cookies, экранирование и вставку контента.

6. Проверки и критерии решения

  • Использовать существующие source-backed fixtures, extraction method ledger и regression tests; различать совпадение старой реализации и подтвержденное улучшение по исходному материалу.
  • Проверять отмену, timeout, HTTP 429/Retry-After, лимиты, восстановление незавершенных заданий, повторный запуск scheduler, сохранение результатов и исключение незавершенных статей из публикации.
  • Сверять auth/cookie semantics, защищенные admin-маршруты, экранирование шаблонов и HTML-контента, форматы ошибок, пагинацию и фильтры.
  • Сравнивать полный набор процессов: приложение + worker + Cloak + gateway + необходимая инфраструктура. Учитывать warmup, одинаковую нагрузку, повторы, idle и длительный рост; не подменять общий расход памятью одного Go controller.
  • Изолированный PostgreSQL, синтетические или явно разрешенные данные, отключенные реальная доставка и scheduler вне проверяемого сценария. Существующий dev Compose не считать изолированным без проверки подключений и mounts.

Существующие команды проверки (не отчет об их выполнении при сохранении этого документа):

go -C go test ./...
go -C go vet ./...
go -C go mod verify
# Linux with CGO and a supported toolchain:
go -C go test -race ./...
.venv/Scripts/python.exe -m pytest tests -q -rs

Python PostgreSQL-тестам требуется TEST_DATABASE_URL выделенной loopback test DB. Реальные browser/network-тесты требуют отдельного opt-in и стенда; skips не объявляются успешной проверкой. Известные команды и результаты конкретных сравнений хранятся в документах этапа экстрактора.

Ручная QA: публичная лента и фильтры; поиск; статья и ссылки/медиа; дайджест; вход/выход администратора; управление источниками и категориями; расписание; принудительная обработка; ошибки и повтор без реальной отправки.

7. Риски и откат

Основные риски: незаметное изменение extraction/quality, потеря накопленного learning, двойная обработка во время совместной работы Python и Go, повторная доставка после сбоя, несовместимые SQL-состояния, auth-регрессии и отличие Jinja от Go-шаблонов. Переходный период с двумя runtime может временно увеличить RAM. Сам Chromium останется отдельным крупным потребителем памяти.

Откат проектируется для каждого этапа: остановить admission нового исполнителя, завершить или зафиксировать его задания, вернуть предыдущий маршрут и сохраненный образ. Python и Go не должны независимо владеть одним расписанием/заданием. Нельзя предполагать, что внешний AI-вызов или отправку сообщения можно откатить транзакцией БД; нужны явные правила deduplication и доставки. Удаление колонок, старых образов и Python откладывается до завершения окна проверки.

9. Approval gate и ведение документа

Для реализации полной миграции требуется отдельное явное одобрение. Текущий запрос разрешает сохранить план как артефакт, а не начать переписывание. Уже одобренные работы по Go/Cloak продолжаются в рамках своего плана.

Перед реализацией очередного этапа актуализировать исходники, результаты предыдущих проверок, scope и rollout/rollback. После выполнения записывать фактические изменения, команды и результаты, skips, ограничения и оставшиеся gates. Не переносить в план secrets и не выдавать старые замеры за текущее состояние.
