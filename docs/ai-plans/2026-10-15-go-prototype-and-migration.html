Последующая проверка production-совместимости: pinned CloakBrowser 0.5.2 не прошел повторные CDP/recovery проверки; обычный Chrome не является заменой этой проверки. A–C одобрены · обязательно полное покрытие экстракции · 15 октября 2026

Цель: проверить, позволяет ли более простой Go-конвейер уменьшить расход ресурсов и сложность сопровождения, сохранив качество сбора, обработки и публикации. Экономия памяти заранее не обещается.

Актуальное направление после обсуждения: отдельный Go-экстрактор с независимым обновлением и откатом. Конкретный следующий этап описан в разделе 11; реализация одобрена и выполняется. Предыдущие разделы сохраняют историю прототипа; полный перенос приложения на Go больше не является выбранным следующим шагом.

1. Решение и границы первого этапа

Рекомендуется: изолированный прототип → сопоставимые замеры → отдельное решение о переносе. Одобрение этого документа разрешает только этапы A–C: фиксацию контрактов, Go-прототип и сравнительный отчет. Изменение production, интеграция с боевым обработчиком и перенос сайта потребуют следующего согласования по результатам.

  • Gemini вызывается по HTTP. analyze_article_complete уже объединяет несколько результатов: «свести все к одному AI-запросу» не является новым выигрышем. Дайджест использует отдельный анализ и Telegram-доставку.

Стенд: существующий docker-compose.dev.yml использует общую БД. Его нельзя использовать как изолированную песочницу для Go. Для прототипа нужны отдельные PostgreSQL/Chrome, собственные env и учетные данные без Telegram-доставки.

3. Целевая архитектура и упрощение

Источники RSS / Telegram / custom
    → ограниченный сбор и нормализация → уникальность URL / hash
    → пригодный исходный текст, иначе HTTP extraction
    → Chrome только по необходимости или настройке источника
    → проверка качества → существующий AI-контракт
    → PostgreSQL: контент + категории + durable outcome
    → сохраненный дайджест → отдельная контролируемая доставка

Итоговая возможность — один Go-сервис с PostgreSQL и внешним Chrome. Сначала прототип CLI; API и UI не входят в его реализацию. Модули по ответственности: source, extract, process, store; digest, delivery, web добавляются только на следующих этапах.

  • Один цикл обработки, ограниченный пул работников и очередь с верхней границей; batch-выборка по ID. context задает общий deadline, вложенные операции расходуют оставшийся бюджет.
  • Один DB pool и прямой SQL вместо универсальной очереди операций поверх ORM. Никаких сетевых запросов под открытой SQL-транзакцией. Уникальный URL и атомарные outcome/category updates сохраняются.
  • Единый бюджет попыток и явные результаты. Ошибка инфраструктуры прекращает цикл; ошибка конкретной статьи изолируется. Классифицированная реклама — terminal, неизвестный результат — не успешный.
  • Не загружать HTTP HTML повторно для каждого selector/fallback. Сначала существующий полезный текст, затем единичный bounded HTTP-разбор. Browser ограничивает возвращаемые данные до передачи в приложение: text/metadata и необходимый bounded markup с атрибутами для CSS/AI selectors. Заменить markup только текстом можно после доказательства эквивалентного выполнения селекторов внутри страницы.
  • Явное владение browser target/session/socket; закрывать только свои ресурсы, отменять и дожидаться своих задач. Shared Chrome и чужие вкладки не принадлежат сервису.
  • Небольшой кеш с TTL и ограничением байтов, identities селекторов уникальны. История и category feedback в PostgreSQL. Удаление AI-обучения селекторов допускается только после доказанной замены для трех custom-источников.
  • Go toolchain и библиотеки выбираются и фиксируются в lockfiles при старте. Кандидаты: стандартные HTTP/JSON/XML, PostgreSQL driver и библиотека HTML/CDP после проверки fixtures. Не писать собственный CDP или HTML-парсер ради сокращения зависимостей.

4. Этапы A–C: конкретный объем прототипа

Уточнение после одобрения: пользователь потребовал учесть все методы экстракции. Полный инвентарь и порядок переходов зафиксированы в extraction-methods.md: E01–E15, M01–M04, R01–R02, T01–T05, C01–C05, X01. Каждый активный ID требует положительных, отрицательных и fallback проверок; список из 40 примеров сам по себе не закрывает gate. Dormant helpers и API-only возможности отмечены отдельно. Неподдержанное явно проваливает replay, а не пропускается.

5. Corpus, измерения и критерии перехода

Планируемый минимум: 4 примера на каждый из 8 действующих источников (32) плюс 8 негативных/краевых случаев (не менее 40 всего). Это объем будущего набора, а не утверждение о уже собранных данных. Если материал источника не удалось сохранить, пробел отражается в отчете, а gate остается незакрытым.

  • Положительные случаи: полный текст и snippet, Telegram со ссылкой и без нее, изображения/вложения, JS custom, mixed Cyrillic/Latin, missing date, относительные ссылки, category feedback и изоляция Serbia.
  • Отказы: реальный challenge и нормальная статья про Cloudflare; реклама и неизвестный ad verdict; nested oversized HTML и compressed expansion; maps/app-store URLs; 429 с Retry-After, 5xx/timeout, malformed AI JSON; cancellation и DB rollback.
  • Для сравнения не запрашивать LLM заново на каждом прогоне: одинаковые prompt inputs и recorded/stub responses. Иначе вариативность модели смешивается с эффектом языка. Изменение промптов, стоимости AI и качества summary — отдельный эксперимент после этого gate.
  • Число найденных статей/дубликатов, URL, title/date/image/media и терминальные outcomes сравниваются с ожидаемыми ответами. Для основного текста — отдельно длина, полнота, boilerplate и ручная проверка каждого расхождения. Python-ошибка не становится автоматически эталоном: исправление ожидаемого ответа описывается и проверяется независимо.
  • Одинаковая машина Linux/amd64, лимиты контейнеров, concurrency, byte caps, corpus и число browser fallback. Cold/warm прогоны разделены; idle после одинакового ожидания. Измерить RSS/PSS, cgroup memory, peak, live heap/allocations, CPU, длительность, HTTP/AI calls, FD/CDP, goroutines, кеши и cache hit rate.
  • Сравнение на двух уровнях: одинаковая processing-задача Python против Go и полный предполагаемый deployment footprint. Для временного Python+Go обязательно складывать оба приложения и Chrome; уменьшение только Go-worker нельзя выдавать за уменьшение всей системы.
  • Soak: минимум 6 одинаковых последовательных циклов после прогрева, включая отказ/отмену и idle; сохранять profiles. Продолжение с sustained read-only soak не менее 24 часов для Go-прототипа на изолированном стенде. Эти интервалы — тестовые критерии, не доказательство отсутствия любой утечки.

Gate C: все восемь источников покрыты, существенных регрессий содержания/metadata/outcomes нет, принадлежавшие прогону ресурсы освобождаются, рост live heap после прогрева объяснен профилями. Переход должен показывать воспроизводимую пользу памяти/CPU либо конкретное уменьшение сложности без ухудшения ресурсного бюджета. Эффект меньше разброса трех прогонов считается недоказанным. Целевой RSS и процент экономии до замеров не назначаются.

Go pprof и runtime metrics дают heap/goroutine profiles; GOMEMLIMIT — мягкий runtime budget, не hard RSS cap и не лимит Chrome. Профилирование снимается отдельно от основных timing-прогонов, чтобы учитывать накладные расходы. Источники: Go diagnostics, Go GC guide.

7. Следующие этапы D–F — дорожная карта после замеров

D. Перенос обработки. После отдельного одобрения возможен минимальный пилот: Python сохраняет сбор, scheduler, попытки, DB commit, auth и отправку, а Go вызывается как ограниченный article worker и возвращает typed field updates. Python удерживает свою reservation до завершения вызова и cleanup, перед внешней работой сохраняет попытку; Go не получает production DB write и Telegram credentials. Измеряется весь Python+Go+Chrome footprint. Если такая граница усложняет эксплуатацию без пользы, пилот не становится постоянной архитектурой.

Для следующего Go-owned writer предлагается exclusive stop/drain/switch: остановить и проверить все Python writer entry points — scheduler, manual process/force/retry, digest-triggered processing, source test/refresh и вспомогательные CLI — затем включить единственный Go writer. Python временно обслуживает только чтение и разрешенную админку, каждый оставшийся write endpoint имеет явно проверенное владение. Просто выключить SCHEDULER_ENABLED недостаточно.

Если потребуется одновременная работа двух реализаций с записью, нужен отдельный контракт shared claims и fencing: потеря PostgreSQL lock-соединения должна делать последующие stale commits невозможными, а не только просить задачу отмениться. Advisory lock сам по себе этого не гарантирует. Этот вариант не входит в A–C и не является механизмом по умолчанию. Текущая process-local reservation между Python и Go не работает. Read-only shadow не меняет articles/settings и не отправляет сообщения.

E. Дайджест и сайт. Сначала snapshot/read-contract tests для URL, pagination/filter/search/RSS, date/timezone, категории, admin preview, auth cookies/Basic/ForwardAuth, backup/export и расписаний. Затем перенос по группам без смены публичных маршрутов и внешнего вида. JS остается TypeScript при существенной новой frontend-разработке; полный frontend rewrite не включен. Никакого механического копирования всех сервисных оберток.

Дайджест генерируется и сохраняется отдельно от отправки. До включения нового sender нужна запись delivery intent/result и запрет параллельных отправителей. Для сетевого timeout после возможного приема Telegram нельзя обещать exactly-once: пометить delivery ambiguous, не повторять автоматически, проверить фактическую публикацию. Новая схема delivery и поведение ручного retry потребуют отдельного согласования.

F. Один production-сервис. После smoke/soak/parity: Go берет scheduler/web/delivery, старый Python становится остановленным fallback. Переключение по immutable image digest, с актуальным backup; проверить первую обычную processing-задачу и первый запланированный digest. Только после успешного периода наблюдения удалять Python runtime и устаревшие совместимые слои. Удаление legacy DB-флагов откладывается до окончания rollback window.

Подготовленные решения не означают разрешение менять схему, auth, proxy, env или deploy сейчас. Полная миграция состоит из отдельных реализуемых планов D/E/F с проверяемыми контрактами.

8. Риски, ручная QA и откат

  • Качество extraction: три custom-источника могут зависеть от браузера/обучения. Ручной QA каждого источника: найденные статьи, основной текст, ссылки, дата, изображения, вложения, отсутствие повторов и challenge-текста.
  • Unicode и limits: 100000 Python characters не равны 100000 Go bytes; отдельно соблюдать rune/byte budgets. Декомпрессия ограничивается после распаковки независимо от Content-Length, кодировки и chunked transport.
  • AI и обучение: сохранить prompts, actual configured model/endpoint, category examples/mapping и original labels/confidences. Для malformed/NaN/inf/bool confidence сохранить существующий finite fallback и clamping: некорректная confidence сама по себе не отменяет иначе валидный результат. Неизвестный ad verdict или отсутствие обязательной стадии не могут превращаться в completed.
  • Публичность: незавершенное не публикуется; явный classified-ad view и authenticated admin preview сохраняются. Не переносить permissive preview в анонимный API.
  • Суммарная RAM: Chrome остается отдельным крупным потребителем. Падение RSS Go не доказывает экономию всей установки; работа двух приложений может ее съесть.
  • Расписания и доставка: сохранить timezone и существующие моменты запуска. Отказы и busy не обозначаются success; неполная обработка не приводит к ложной рассылке.

Откат A–C: остановить только изолированный стенд и удалить только его явно названные временные данные после проверки paths/volumes. Production не изменяется, DB rollback не нужен.

Откат D–F: остановить новые writers/sender, дождаться либо отменить и join текущий цикл; проверить отсутствие выполняющихся задач/DB writes и ambiguous delivery. Вернуть сохраненный совместимый Python image digest и прежние маршруты/режимы writer. Новые schema additions остаются совместимыми, бизнес-данные не откатываются из старого backup. Восстановление дампа — отдельное решение при повреждении данных, поскольку оно теряет новые статьи и delivery history.

11. Следующий этап: самостоятельный Go-экстрактор

Раздел 11 одобрен · сервис реализован · изолированные проверки пройдены · production gate открыт

Задача: вынести извлечение в приватный stateless-сервис, чтобы выпускать его независимо от Python, ограничивать ресурсы и локализовать сбои. Использовать существующее Go-ядро. Собственная БД, брокер и перенос сайта для этого этапа не нужны. Выигрыш памяти подтверждается только замером всей связки.

Текущее состояние и выбор

На ветке prototype/go-extraction-parity есть offline replay и отдельные loopback-only HTTP/CDP adapters. Сопоставление захваченных данных завершено в пределах отчета качества; это не готовый сетевой сервис. Публичный transport, полный runtime fallback, learned state и сквозная обработка остаются открытыми. Исторические замеры и статусы выше не являются новой проверкой production.

Из трех вариантов выбран отдельный приватный контейнер: он позволяет сохранить Python и обновлять извлечение отдельно. Один Go-монолит остается возможностью позднее, но потребовал бы гораздо большего переноса. Сервис с собственной очередью/БД добавил бы координацию и миграции без подтвержденной необходимости.

Предлагаемый API v1

  • POST /v1/extract: один запрос — одна статья. Вход: request ID, URL, доступный исходный контент/HTML, strategy, browser policy, source type, selectors и ограниченный budget. Это отдельный wire-контракт с allowlist полей, не экспорт всех replay-полей; injection-поля cancel_at, now и fixture alternatives в сетевой API не входят.
  • Ответ: contract version, build version, request ID, outcome, исходный и конечный URL, content/title/date/author/image/media, method/provenance, truncation и ограниченная trace; selector observations либо запрос изучения структуры. Outcome: success, rejected, needs_selector_study, failed; failure содержит стабильный code и retryable. HTTP 400 — некорректный вход, 401 — auth, 413 — размер, 429 — занято, 503 — draining/неготовность. Корректно завершенное извлечение, включая отказ сайта или отсутствие полезного текста, возвращает HTTP 200 с outcome; сетевые/неоднозначные ошибки клиент разбирает отдельно.
  • GET /health/live — процесс; GET /health/ready — прием запросов и состояние обязательных зависимостей; GET /version — build и поддерживаемый API. Отказ Chrome не блокирует HTTP-only работу: capability браузера видна в health и проверяется для запроса, требующего его. Все endpoints только в приватной сети; extract требует service token.
  • Ограничить размер всего JSON до decode, поля, декодированный HTML, DOM и ответ. Сервер задает верхние пределы; клиент может только уменьшать budget. Учитывать JSON escaping и сумму полей, а не только каждый HTML отдельно. Не отправлять большие DOM туда-обратно при обычном URL-запросе; markup передавать лишь при уже имеющемся capture или изучении структуры.

Ресурсы, ошибки и сеть

Общий request deadline включает HTTP, браузер, fallback и cleanup; отмена клиента отменяет работу. Admission без неограниченной очереди, отдельный semaphore для Chrome; при перегрузе 429 с Retry-After. Python владеет durable retry, Go выполняет только ограниченные method attempts внутри одного вызова. Режим shadow не меняет DB, learned state, attempts или отправку. Автоматический fallback на Python при transport failure разрешен только на пилоте, последовательно и с оставшимся общим бюджетом; он явно отражается в метриках и не запускает две обработки одновременно.

Loopback-защиту существующих adapters не удалять ради публичных URL. Добавить отдельную public-fetch policy: только HTTP(S), запрет credentials/private/loopback/link-local/metadata адресов, проверка DNS и фактического соединения, redirect и browser subrequests; CDP endpoint берется только из серверной конфигурации. Для браузера дополнительно изолировать egress от внутренних сетей; доказать блокировку workers/WebSocket/frames/popups без потери обязательных JS-источников. Если нужный источник несовместим с проверенной политикой, он остается на Python до явного решения, а не получает скрытый обход.

Логи без текста статьи, токенов и query secrets. Метрики: in-flight/отказы admission, latency, методы/outcomes, HTTP/browser calls, собственные targets, Go heap/goroutines, контейнерная память и Chrome. URL не использовать как label. CPU/RAM limits и concurrency подобрать на стенде по измерениям; числовую экономию заранее не назначать.

Независимый выпуск и откат

Отдельный multi-stage Dockerfile и CI job собирают неизменяемый образ с commit tag/digest; Python использует совместимый API v1 и отдельную настройку endpoint. Внутри v1 новые поля только optional, прежняя семантика сохраняется; несовместимое изменение требует v2. CI проверяет старый клиент с новым сервером и новый клиент с поддерживаемым предыдущим сервером. Образы Python, Go и Chrome не обязаны обновляться одновременно.

Обычный выпуск: запустить новый Go-образ рядом, проверить ready/version и smoke, переключить endpoint, убрать старый из приема и дождаться ограниченного drain собственных запросов. На первом этапе допускается короткое окно недоступности с контролируемым retry: бесшовный deploy не обещается без проверки текущего proxy. SIGTERM выключает readiness, прекращает admission, завершает/отменяет запросы и закрывает собственные browser resources. Откат — прежний digest и endpoint; Python-only режим возвращается отдельным флагом. Миграций БД нет, восстановление backup не требуется.

Допущения, риски и открытые решения

Предполагается один доверенный потребитель — Python, private deployment и сохранение действующих article semantics; source-first оптимизация отдельная. Точные значения concurrency/deadlines/container limits выбираются на стенде. Топологию private network, egress/proxy и хранение service token сверить перед production rollout. Основные риски: двойные runtime и transient DOM увеличивают peak RAM; JS ломается из-за изоляции; усложняется stateful обучение; смена версии API или два retry-слоя меняют результаты. Ни один из них не считается закрытым существующими replay-тестами.

Критерий завершения: независимо обновляемый и откатываемый образ, совместимый клиент, все обязательства методов сохранены и проверены на своей стороне границы, необъясненных регрессий нет, bounded cleanup подтвержден, полная ресурсная стоимость измерена. Польза независимых выпусков допустима как отдельный результат; экономия памяти заявляется только при воспроизводимом подтверждении.

Approval gate: пользователь явно одобрил реализацию раздела 11 («Ну давай да, экстрактор действительно отделяется хорошо»). Разрешены новый API, public transport, Python-интеграция и изолированные проверки; production cutover, push, PR и deploy остаются за отдельным разрешением.

Фактический результат, 16 октября: реализованы отдельный Go HTTP-service, public transport/pipeline, Python-клиент и выключенная по умолчанию интеграция, независимый образ и CI.
