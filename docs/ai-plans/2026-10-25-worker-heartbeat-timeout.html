Worker heartbeat diagnostics and failure reproduction

2026-10-25 · Revision 1 · Implemented: diagnostic scope; production incident remains unresolved.

Evidence and limits of the diagnosis

Four post-PR25 scheduled Go ingestion runs completed all eight sources with zero errors. During read-only investigation the worker restarted at 13:26:10 UTC on heartbeat stage=commit reason=timeout, following five earlier update-stage timeouts. It reacquired lease generation 32 at 13:26:21 UTC. No OOM or new exhausted articles were observed. Short CPU sampling after the event cannot characterize the failure instant. Historical PostgreSQL logs were insufficient for correlation. Production root cause is unproven.

Heartbeat runs BEGIN, a fenced status-row UPDATE, and COMMIT on a dedicated lease connection every five seconds. Its existing deadline defaults to five seconds. Any failure invalidates the lease. Bookkeeping and ingestion fences also lock the status row. Possible row contention is not established historical causality; a commit timeout does not prove a disk problem.

Approved scope and boundaries

Reproduce controlled update/commit failures and normal concurrent idle work on isolated loopback PostgreSQL. Fix only a proven code defect within the existing contract. If root cause remains unproven, add bounded phase durations and tests, explicitly identifying the result as diagnostic work. Preserve existing fail-closed fencing, error semantics, deadlines, limits, database schema and public API. Do not change AI, alert policy, production configuration, shared browser or Readeck.

Risks and recovery

An applied UPDATE or unacknowledged COMMIT does not establish a confirmed heartbeat. Preserve failure invalidation and do not blindly continue or retry uncertain writes. Timing checks must tolerate scheduling variance. All reproduction data is synthetic. A future rollback uses the previous immutable worker image after explicit pause/drain authorization, preserving receipts and data; no database restore or volume deletion.
