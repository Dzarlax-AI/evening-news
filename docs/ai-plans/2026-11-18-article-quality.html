Качество статей и дедупликация

Сервер Evening News выдаёт для статьи только подходящие изображения, исключает явно бессодержательные публикации и показывает одну карточку для повторов одного события. Важные обновления получают собственные карточки.

Что видно в текущем коде

  • Картинки. rssImages принимает каждый подходящий URL из медиаэлементов и HTML записи RSS. trustedRSSMedia пропускает изображения по признаку rss_feed. Он подтверждает происхождение из фида. Иконка внутри фида получает тот же признак, что и редакционная фотография. Экстрактор веб-статей может собирать медиа со всего HTML документа, включая блоки за пределами текста. В предыдущей проверке статьи Blic о Pištaljka №18559 в галерее были варианты одной картинки и служебный SVG 60×60. Путь каждого изображения до сохранения ещё надо подтвердить.
  • Бессодержательные записи. shouldProcess проверяет длину, язык, признаки спама и качество формы. Отдельный AI-анализ классифицирует рекламу. На первом скриншоте обведена карточка «Все мы в случайный момент жизни» (Сербия ТГ, 17 ноября, 14:01). Её резюме сообщает, что пост содержит только фразу «Все мы в рандомный момент нашей жизни».
  • Повторы. Ingestion проверяет URL и точный заголовок внутри одного источника за семь дней. Проверка в обработчике на первой попытке использует MD5 нормализованного текста, а текущий ingestion пишет в hash_content SHA-256 от заголовка и URL. Кэш в памяти может замечать совпадения текста до перезапуска. В дайджесте уже есть редакционная группировка по сюжету, а для обычной ленты такого механизма нет.

Основание — локальный main на b0332f4, два скриншота ленты и предыдущая проверка галереи. По скриншоту Nvidia видны близкие заголовки и разные вводные. Решение об объединении требует исходного содержания обеих записей. Развёрнутую версию сервера и записи от 17 ноября в этой проверке не сверяли.

1. Отбирать картинки на сервере

Первый источник для проверки — The Verge. По наблюдению пользователя, у этого источника часто встречаются посторонние или некорректно отображаемые картинки. Причину для The Verge пока не подтвердили. Случай Pištaljka нужен как дополнительная регрессия.

  1. Взять несколько недавних статей The Verge с проблемной галереей и одну с корректными фото. Для каждой сверить медиа записи RSS, сохранённые поля статьи, публичный API и тело оригинальной публикации. Для неподходящих элементов определить точку появления. Для визуально искажённых фото проверить размеры и пропорции выдаваемого CDN-варианта и отображение в галерее. Редакционную обложку и разные иллюстрации из статьи включить в контрольную выборку.
  2. Зафиксировать происхождение элементов Pištaljka по доступному read-only снимку или сохранённому фиду. Подготовить обезличенные примеры RSS, Telegram и HTML страницы с редакционным фото, логотипом, пикселем, похожими материалами и двумя CDN-вариантами одного изображения.
  3. Сохранить приоритет медиа, явно относящихся к записи. Для страничной экстракции брать фото из выбранного тела статьи. В RSS фильтровать служебные изображения в HTML записи и сохранить действующее ограничение на происхождение RSS-фото. В Telegram учитывать собственные вложения поста и исключать аватарки, реакции и декоративные элементы. Проверять известные служебные атрибуты, явные малые размеры и подтверждённые шаблоны URL. Сохранять редакционную инфографику, включая SVG с доказанным происхождением.
  4. Объединять варианты одного фото по явному каноническому адресу, srcset или известному правилу конкретного CDN. Подписанные URL и параметры, выбирающие разные фотографии, сохранять. Выбирать одну рабочую версию, сохранять порядок и выводить обложку из того же набора. Если подходящих фото нет, отдавать пустую галерею. Изображения не требуют дополнительных сетевых запросов по умолчанию.
  5. Применить общую политику к новым записям и к серверной выдаче уже сохранённых медиа. Проверить обычную обработку, ручное переизвлечение и go-domain/media/refresh.go. Разделить исходные медиа и отобранный набор на сервере. RSS сейчас теряет размеры и сведения о вариантах, а refresh перезаписывает сохранённые поля. Сохранять только метаданные, нужные для правил, с действующими ограничениями объёма. Для старых рядов без метаданных применять только подтверждённые правила и сначала показать результат пробного пересчёта. Любое массовое переизвлечение или обновление сохранённых медиа согласовать по выборке.

Основные точки в коде — go/extractor/{rss_images,article_media,telegram_media}.go, go-processing/internal/processing/{media,runner}.go, go-domain/media/refresh.go, go-web/internal/repositories/postgres.go. Проверить поля image_url, primary_image, media_files и images по публичным маршрутам.

2. Проверять содержательность поста

Расширить существующий вызов анализа структурированным решением о пригодности для ленты. Первой включить оценку постов Telegram. Публикацию можно явно пропустить, если исходный текст содержит только реакцию без контекста, подпись к мему без самостоятельного смысла или обращение к аудитории без содержательной информации. Сохранять короткие сообщения о событии, объявления, полезные инструкции, обзоры и объяснения. Обработчик должен передавать анализу исходный текст и проверять наличие внешних ссылок и вложений по метаданным Telegram. Запрещать скрытие по одному тексту, если вложение или ссылка могут давать содержательный контекст, а этот контекст не проверен. При повторной обработке с готовым резюме брать исходный текст. При нехватке данных оставлять публикацию.

Добавить отдельную причину в результат обработки с переиспользованием текущего состояния rejected. Сохранить исходную запись и возможность ручной переоценки. Применять решение до перехода в completed, чтобы режим показа рекламы его не отменял. Сбой анализа обрабатывать по действующей политике повторов. Отсутствие нового поля в старом или частичном ответе трактовать как отсутствие решения. Один вердикт используется для обеих локалей.

Приёмочный пример с первого скриншота. Если исходный пост содержит только показанную фразу и у него нет содержательного контекста во вложении или по ссылке, карточка «Все мы в случайный момент жизни» отсутствует в ленте, поиске и новом дайджесте. Сверка карточки №18564 и оригинала выявила видео. Первый этап оставляет реальный пост видимым при непроверенном видеоконтексте. Контрольный пример с той же фразой без ссылок и вложений должен исключаться, а короткое сообщение о перекрытии улицы с местом и временем проходит фильтр.

Основные точки — go-domain/analysis/{prompt,validate}.go, go-domain/airuntime/article_callback.go и go-processing/internal/processing/. Начать с режима, в котором решение записывается для сравнения и не влияет на публикацию.

3. Показывать один материал на повтор события

  1. Сохранить URL-проверку при сборе. Совпадение заголовков у разных URL считать сигналом для сравнения. Сейчас по одному заголовку запись может быть отброшена внутри пачки и при проверке того же источника за семь дней. Заменить раннее скрытие по кэшу текста проверкой отдельного версионированного отпечатка после извлечения или получения исходного текста достаточного объёма. Отпечаток участвует в выборе представителя только после допуска статьи. Если первая поступившая копия завершилась ошибкой или была отклонена, следующая пригодная копия должна появиться в ленте. Обновления по тому же URL регулируются отдельным существующим правилом ingest.
  2. Для близких текстов начать с ограниченного окна в 48 часов как параметра пробного прогона. Отбирать кандидатов по оригинальным и нормализованным заголовкам, именам, числам и ключевым словам в заголовке и резюме. Сравнивать записи одного и разных источников. На размеченной выборке измерить, попадают ли в кандидаты одно событие на разных языках и разные события с близкими заголовками.
  3. Для похожих кандидатов проверять, совпадают ли действующее лицо, действие, объект и существенные обстоятельства. При необходимости использовать один ограниченный вызов существующего AI-провайдера на небольшую пачку кандидатов. Требовать явного результата «повтор того же факта», «существенное обновление» или «неясно». Автоматически объединять только уверенные совпадения с представителем группы. При пропуске сравнения, сбое или сомнении показывать обе статьи. Оценить точность, задержку и стоимость на пробном прогоне, прежде чем решать, нужны ли эмбеддинги.
  4. Сохранять обратимую связь с представителем и причину объединения. Выбирать стабильного представителя среди опубликованных материалов, по умолчанию первую пригодную карточку группы. При активном фильтре источника или категории выбирать из совпавших с фильтром. Для поиска выбирать из совпавших с запросом результатов. Применять отбор до подсчёта и пагинации. Прямые ссылки на оригинальные карточки должны продолжать открываться. Для нового дайджеста брать один представительный материал группы из доступного снимка выпуска. Сохранённые выпуски остаются историческими снимками.

Основные точки — go-processing/internal/{processing,store}/, go-ingestion/internal/store/store.go, миграции go-domain/migration/, go-web/internal/repositories/postgres.go и go-domain/digestworkflow/snapshot.go. Для первой версии предполагается аддитивная миграция PostgreSQL под отпечатки и связи. Короткая транзакция проверяет актуальность решения и представителя перед записью, а повтор обработки должен давать тот же результат. При параллельной обработке блокировать или перепроверять конфликтующий выбор представителя. Старые значения hash_content сохраняются для совместимости.

Порядок работы и проверки

  1. Собрать исходные примеры. Для обеих записей Nvidia сопоставить ссылки, исходные заголовки, даты и существенные факты. Зафиксировать, был ли второй текст повтором или обновлением. Дополнить примерами коротких содержательных постов, рекламы, аналитики и разных новостей про одну компанию. Проверить обе локали. Воспроизвести Pištaljka на изолированных данных.
  2. Реализовать и проверить отбор медиа. Расширить существующие фикстуры RSS, Telegram, экстрактора и публичного API. Проверить, что варианты CDN схлопываются, разные фото остаются, служебный SVG пропадает, нужная инфографика остаётся, а обложка и галерея согласованы. Проверить выбранные статьи The Verge и Pištaljka через API, веб и Android на тестовом сервере. На The Verge должны сохраниться корректная обложка и разные редакционные фото. Подтверждённые посторонние картинки и дубли вариантов должны исчезнуть. Если дефект пропорций остаётся при корректном ответе API, зафиксировать его отдельно с конкретным экраном и исходным изображением.
  3. Запустить пробный прогон фильтра и дублей. На одних данных сравнить старый и новый результаты. В журнале держать идентификаторы, версии и причины решений. До прогона зафиксировать размеченные пары, критерии достаточного охвата кандидатов и допустимый бюджет задержки и AI-вызовов. Отдельно измерить охват разноязычных пар. В отчёте указать числитель и знаменатель для найденных дублей и ложных объединений. Для включения правила контрольные дубли должны дать одну карточку, а размеченные самостоятельные новости и существенные обновления должны остаться видимыми.
  4. Проверить сквозное поведение. Повторное задание, две конкурентные обработки дублей, первая копия отклонена, разные события с одинаковым заголовком и разными URL, сбой AI, старая запись без метки, скрытие или удаление представителя, пагинация, поиск, фильтр источника и категории, RU/SR, прямая ссылка, снимок нового дайджеста. Проверить, что после отключения новой политики медиа возвращается прежний набор URL, в том числе после refresh. Проверить, что один перегруженный картинками RSS-элемент обрабатывается согласно действующим ограничениям фида. Использовать модульные Go-тесты затронутых модулей, изолированный PostgreSQL и существующий image fixture gate. Проверять дайджест без отправки сообщений. Все проверки этого раздела запланированы.

После утверждения задачи по медиа и анализу содержательности можно реализовать независимо в указанных модулях, назначив одного владельца общего runner.go. Дедупликация зависит от результата допуска и согласованного контракта хранения. Для ограниченных изменений можно использовать доступную быструю модель, а интеграцию, SQL, совместимость и результат пробного прогона проверит ведущий агент.

Откат и исторические данные

Включать правила медиа, пригодности и группировки отдельно. Сохранить исходные медиа и статьи. Отключение серверного отбора возвращает прежнюю проекцию из сохранённых исходных медиа. Отключение группировки возвращает карточки к самостоятельному показу. Для уже пропущенных бессодержательных записей предусмотреть ограниченную повторную обработку по коду причины с сохранением истории попыток. Сначала использовать изолированную БД. Пакетную обработку старых статей согласовать после пробного отчёта с перечнем затрагиваемых записей.
