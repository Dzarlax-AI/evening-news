SourceManager и RSS → Go

Редакция 1 · 23 октября 2026 · Implemented / PR review pending. Пользователь одобрил перенос на Луне, PR и review. Production не входит в разрешение и не изменяется.

1. Что переносим и какой результат считаем готовым

Переносим в существующий приватный Go-сервис сетевой сбор RSS/Atom и runtime-диспетчер источников: ограничение параллелизма, ожидание браузерной ёмкости, вызовы typed source runners, изоляцию ошибок и сбор результатов. Отдельный сервис, брокер и scheduler для этого этапа не нужны.

SourceManager сейчас содержит также CRUD, чтение конфигурации, дедупликацию и запись статей. Они остаются в Python. Поэтому результат этапа — Go-владелец source collection, а не удаление всей Python-класса SourceManager. Python становится адаптером подготовки конфигурации и сохранения результатов. Scheduler, управление попытками article processing, Gemini, digest/Telegram delivery и web/admin остаются прежними.

Python scheduler → Python: SELECT enabled sources
→ Go SourceManager: RSS / Telegram / Page Monitor collection
→ Python: Page Monitor state / optional selector AI / normalization
→ Python: dedup + DB write → existing article processing

Готовность: в режиме Go batch обычный сбор всех трёх типов проходит через новый Go manager; Python не выполняет RSS fetch/parse и собственный сетевой fan-out для этого маршрута. Статьи доходят до неизменённого persistence-пути без потери metadata, фильтров или partial-prefix semantics. Ускорение и снижение памяти — измеряемые гипотезы, не обещания.

2. Что подтверждено текущим кодом

  • services/source_manager.py: fetch_from_all_sources_no_db запускает все coroutines через gather, ограничивает общий I/O semaphore (по умолчанию 5), отдельно сериализует Go-backed Telegram/custom; возвращает словарь по имени источника. Ошибка источника превращается в пустой список. Другие методы класса выполняют CRUD, URL/title dedup и сохранение.
  • sources/rss_source.py: bounded HTTP через core/http_client.py, затем feedparser. RSS content и summary различаются; сохраняются image, publication date, guid, author, tags. Приоритет дат: published → updated → created → parsed fields → текущее UTC; приоритет картинок: image enclosure → media content → thumbnail → HTML img. Bozo в fetch трактуется иначе, чем в connection test.
  • Go уже содержит gofeed v1.3.0 и extractFeed в go/extractor/sources.go. Последний извлекает один entry из переданного RSSXML; это ещё не полноценный сетевой RSS source collector. Зависимость повторно не добавляется, offline API не ломается.
  • Telegram/Page Monitor имеют готовые typed runners и guarded public transport. Page Monitor Python хранит snapshot, acknowledged hashes, offsets и learned selectors; опционально выполняет AI study и reparse того же HTML. Telegram Python дополнительно обогащает linked articles. Эти post-processing части нельзя случайно потерять при переносе fan-out.
  • В orchestrator.py уже есть граница read → fetch без DB lock → save через execute_write. Новому manager нельзя выдавать доступ к PostgreSQL или держать DB transaction во время I/O.
  • Существующий Go API использует общее admission ограничение, body cap 8 MiB и server WriteTimeout 36 с. Это требует явного согласования с длительным batch, а не простого добавления goroutines.

3. Контракт и владельцы состояния

Новый endpoint: POST /v1/sources/collect с тем же private Bearer auth. Existing extract/Telegram/Page Monitor endpoints сохраняются. В запросе: contract_version, request_id, bounded batch budget, ordered descriptors с уникальным source_id, типом rss/telegram/custom, URL, source_name, typed config и подготовленными learned selectors/cursor. Source_id, а не имя, используется для корреляции; одинаковые имена не должны перезаписывать результаты. По ordinal сохраняется исходный порядок передачи в persistence.

Ответ содержит request_id/build_version и результат для каждого descriptor: source_id, outcome (success / partial / deferred / failed / rejected), items или существующий typed payload, finite error_code, retryable, retry_after, final_url, fetched_at и необходимые pagination/study поля. Пустой успешный feed отличается от timeout или ошибки. Выдуманные URL, error text со страниц, credentials и неограниченный raw XML/HTML не логируются. Python валидирует request/source IDs, типы, объёмы и состав ответа.

Manager вызывает typed runners внутри процесса; не делает HTTP-запросы к собственным endpoints и не захватывает один и тот же admission slot второй раз. Общий server admission и browser ownership остаются действующими. RSS идёт только через существующий guarded public HTTP transport, без Cloak. URL из feed не запускают сетевые обращения к статьям, картинкам или external XML entities при парсинге.

Page Monitor: Python adapter получает явные prepare/finalize методы, сохраняя текущую обработку offsets, partial prefix, snapshot и acknowledged hashes. Go получает только подготовленную fetch/parse конфигурацию. После batch admission slot освобождается; Python при необходимости делает прежний AI study и один вызов существующего parse endpoint на том же HTML/snapshot. Finalize не должен заново fetch страницу. При недоступности study сохраняется валидный prefix по прежним правилам.

Telegram: Go manager возвращает существующий typed payload. Python сохраняет нынешние metadata/ad flags и linked-article enrichment после освобождения batch slot; повторного channel fetch нет. Браузерный слот не удерживается во время AI или Python post-processing.

БД и dedup: остаются на одном Python write path. Сохраняются telegram/original candidate URLs, batch URL/title dedup, 7-дневный title check внутри источника, обновление unprocessed и защита completed. Snapshot статей не считается успешно сохранённым из-за одного успешного HTTP-ответа manager. Миграции БД не планируются.

4. Параллелизм, время, память и режимы

Начальные границы нового batch-контракта: до 8 descriptors на запрос; fixed worker pool не более текущих 5 source I/O задач; browser-capable Telegram/custom выполняются по одному, RSS может идти параллельно. Это перенос существующего source fan-out из Python, не увеличение browser concurrency или числа браузеров. Вся очередь ограничена размером descriptors, а не goroutine на каждый источник. RSS wire/decoded body cap — 5 MiB; request/response JSON — максимум существующих 8 MiB. Лимиты не повышаются автоматически при несходящемся тесте.

Batch budget максимум 120 с, с резервом на serialization. Таймер источника запускается после получения source/browser ёмкости, а не во время очереди. Внутренние Telegram/Page Monitor операции сохраняют свой предел 30 с; RSS HTTP — до нынешних 60 с, outer source budget не больше 120 с. Для нового route устанавливается отдельный bounded write deadline с transport margin; общий WriteTimeout старых endpoints не увеличивается. Поведение middleware и HTTP client должно быть проверено на реальном сервере, а не только httptest Recorder. Стандартный механизм: net/http ResponseController; при невозможности установить deadline — явная ошибка, не бесконечный запрос.

Не начатые к завершению окна источники возвращаются deferred с source_id; Python подаёт оставшиеся в следующих bounded окнах, с общим deadline прохода и без tight loop. При заполнении response budget результаты уже выполненных источников не теряются: возвращается явный per-source partial/deferred, остальные source IDs остаются на повторе. RSS result, который даже один превышает response cap, получает явный resource_limit; его нельзя объявить полностью доставленным или молча обрезать. Продолжения Page Monitor сохраняют существующие next_offset semantics. Отмена клиента/drain отменяет дочерние ctx и дожидается cleanup, не оставляя tasks/targets.

Для rollout предлагается один новый переключатель SOURCE_MANAGER_MODE=python|go, default python. Go batch требует Go режимы Telegram/Page Monitor; несовместимая mixed-конфигурация отклоняется явно. В python manager mode существующие per-source режимы работают как раньше. Автоматического fallback целого batch в Python нет: он вызовет двойной fetch и изменит snapshot. Private service URL/token и текущие limits переиспользуются; Go без DB/AI secrets.

6. Матрица проверок и измерений

  • RSS/Atom parity: namespaces, Atom alternate links, HTML/CDATA, unicode, declared encodings, content vs summary, три fallback даты и отсутствие даты с зафиксированным Now; enclosure/media/thumbnail/HTML image priority, author/guid/tags, пустой feed, отсутствующие link/title, malformed XML и невалидный entry. Отличия от feedparser фиксируются отдельно, а не автоматически принимаются как улучшение. RSS test_connection сохраняет собственную текущую bozo-семантику.
  • Manager: смешанный batch RSS/TG/custom, повторы source_id, одинаковые source names, пустой список, unknown type, disabled source, один timeout при успехе остальных, очередь дольше per-source operation timeout, общий deadline, partial response и deferred IDs, отмена/drain/следующий запрос. Нет slot re-entry, утечек goroutines/targets и starvation browser lane.
  • Security/resource: auth, body bounds и decoded compressed limits, redirects, DNS rebinding/private addresses, external entities без network, RSS parser без media fetch, aggregate response accounting до выделения лишней памяти, source/job caps. Gate не может автоматически переключиться на менее защищённый Python transport.
  • Python integration: snapshot/offset/ack parity, selector study той же страницы без повторной навигации; Telegram linked enrichment после batch slot; preservation ad/media/date fields; сохранение успешных источников при отказе другого. Две одинаковые подачи в isolated PostgreSQL дают те же статьи без лишних записей; готовые статьи и source relations сохранены. Никаких AI/network вызовов внутри execute_write.
  • Команды: из go/ — go test ./..., go test -race ./..., GOOS=linux GOARCH=amd64 go build -o /tmp/news-source-manager-check ./cmd/extract-service. Python: .venv/bin/python -m pytest tests/test_source_manager_go_serialization.py tests/test_telegram_go_source.py tests/test_page_monitor_go_source.py tests/test_telegram_source_parity.py tests/test_page_monitor_source_parity.py tests/test_processing_outcomes.py tests/test_processing_batches.py -q, плюс новые RSS/batch/client/persistence suites. CI — существующие Python/PostgreSQL и Go integration workflows.
  • ARM64 и Linux: локальные Mac ARM64 unit/parity tests и отдельная Linux/amd64 CI/Compose acceptance на fixture origin. Замерять весь fetch→decode→normalize→save путь: wall time, cgroup anon/file/peak отдельно, heap, targets и goroutines до/после серии. Сравнение с Python на одном corpus, одинаковых лимитах и числе источников. Если memory.peak недоступен, не выдавать sampled maximum за настоящий peak. Проверить цикл на прежнем 256 MiB worker budget; при нехватке остановиться и разобрать buffering, не поднимать лимит.

7. Выпуск, риски и восстановление

Этот план готовит реализацию, локальные/synthetic проверки и PR/review. Merge, публикация production images и выкат этим запросом не разрешены. Push ветки может автоматически запустить существующую CI candidate publication; разрешение на такой push и PR подтверждается при одобрении реализации. Production rollout потребует app + Go worker, согласованной версии контракта, pause/drain News, immutable image provenance, сохранённых .env/config и исходных enabled flags. Браузер, его limits, PostgreSQL и соседние сервисы не изменяются. Заранее проверить read paths News и общих browser clients; не перезапускать Assistant.

Rollback сборщика предусмотрен переключением SOURCE_MANAGER_MODE обратно в python при согласованном app restart: эта ветка сохраняется до production acceptance. Никакого одновременного запуска двух collectors на production. Не откатывать таблицы или стирать уже сохранённые статьи; dedup обрабатывает повторные fetch. При startup failure — диагностика и решение с пользователем, без автоматического rollback.

Основные риски: RSS parser parity; PM state drift; source-name коллизии; nested admission deadlock; длительный batch против server/client deadlines; memory buffering; silent omission при response cap. Каждый риск привязан к тестам выше. Вынос scheduler, DB writes или AI в Go — отдельный следующий проект, не скрытое расширение этого PR.

8. Gate и открытые ограничения

Для начала реализации требуется одобрение редакции 1. После него выполняются Luna → synthetic/fixture parity → PR → review; любые найденные несовместимости RSS/PM сначала воспроизводятся тестом. Если нельзя сохранить обозначенные семантику или ограничения, работа останавливается перед изменением контракта и план уточняется.

Без production-инвентаризации ещё не известно, есть ли feeds с приватными адресами, нестандартной авторизацией/encoding или payload выше новых aggregate caps. На этапе preflight без реальных fetch проверить только обезличенные конфигурационные характеристики; секреты не переносить в DTO и не публиковать. Для таких источников Go mode должен явно отказать/оставаться неактивным до отдельного решения, не обходить public transport guards. Список разрешённых real-source acceptance запросов и production release approval остаются открытыми.

По AGENTS.md HTML Planning Gate реализация начинается после одобрения. Пользователь одобрил редакцию 1: «Го, план одобряю. Делай перенос SourceManager и RSS на Луне, потом PR и review. Прод пока не трогай». Результаты исполнения и изменения утверждённого scope будут записаны в этом же файле.

9. Результаты реализации — 23 октября 2026

  • На Луне реализованы RSS/Atom collector, приватный batch endpoint, fixed worker pool и browser lane, source-ID correlation, общий admission без повторного захвата, operation/batch budgets и cancellation/drain. Aggregate reservation ограничивает удерживаемые результаты до передачи в очередь; окончательная сериализация дополнительно проверяет wire cap.
  • Python bridge сохраняет PM cursor/snapshot/ack и same-HTML reparse, Telegram enrichment после освобождения batch slot, существующий persistence и Python mode. SOURCE_MANAGER_MODE остаётся python по умолчанию; production overlays не менялись.
  • Root: полный Go suite с race detector прошёл; после review-исправлений повторно прошли затронутые pipeline/service/cmd packages с race detector. go vet и module verification прошли. Linux/amd64 static binary собран.
  • Root: полный Python suite с отдельной локальной PostgreSQL — 1071 passed, 10 skipped, 22 subtests passed. После последующих исправлений wire contract и budgets — 183 targeted tests passed; после исправления реального PageMonitorAdapter — 50 targeted tests passed. Финальный CI повторяет полный suite с PostgreSQL.
  • Linux/amd64 fixture gate на ARM64 Docker host: реальный worker, guarded HTTP RSS/Telegram/Page Monitor, отдельный ошибочный RSS не нарушает успешные результаты. Шесть Go-only collection → Python → isolated SQLite циклов дали 7 сохранённых статей каждый раз. Два RSS с одинаковыми именами сохранили разные source IDs; повтор не создал дубли. Python source fetch в этом прогоне запрещён тестом.
  • Первый успешный gate: cgroup memory.peak 83 726 336 bytes (около 80 MiB) при cap 268 435 456 bytes; memory.events max/oom/oom_kill = 0. После обработки inflight/admission = 0, goroutines = 6. Это synthetic HTTP-only worker под amd64 emulation; Cloak и production load в замер не входят.
  • Gate использует только собственную internal Docker network и fixture TLS. Для Docker Desktop API доступен через loopback proxy к docker exec; внешней сети у worker/origin нет. SHA binary/source, image digests, memory anon/file и подтверждение cleanup сохраняются в JSON report. Новый CI step повторяет gate и публикует отчёт как test artifact.
  • В review исправлены: удержание нескольких полных ответов до aggregate cap, RSS null payload при отказе одного источника, сохранение явного пустого title, отсутствие finite error у malformed runner failure, передача per-source budget и deadline через реальный PageMonitorAdapter. Добавлены regression tests; списки RSS/TG не обрезаются молча.
  • README и новый английский docs/go-source-manager.md обновлены. Шесть посторонних локальных файлов сверены с исходными SHA256 и сохранены без изменений.

Граница приёмки: пока нет real-source acceptance, native Linux timing и измеренного Python-vs-Go performance comparison. RSS parity подтверждена только committed corpus. Browser capture покрыт существующими tests; этот новый end-to-end gate HTTP-only. Эти ограничения не позволяют заявлять ускорение или готовый production rollout.

Выпуск: PR/review готовятся после финального независимого прогона. Merge, production images и deploy не выполнялись и не разрешены этим этапом.
