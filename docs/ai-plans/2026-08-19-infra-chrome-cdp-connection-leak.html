Implementation Plan: Restore Evening News Collection and Telegram Delivery Reliability

Implementation completed in an isolated worktree; production deployment remains pending.

Task Summary

Restore the shared infra-chrome service safely, prevent Evening News from leaking Chrome DevTools Protocol connections, and make Telegram delivery failures visible and actionable. The work has two independent reliability tracks: browser-backed collection and delivery of the already-generated daily digest.

Confirmed Current Behavior

  • infra-chrome is running but unhealthy; its /json/version health check returns HTTP 502.
  • The CloakBrowser server process has 1,023 file descriptors against a soft limit of 1,024; 1,019 are sockets.
  • There are 1,524 established TCP entries in the browser network namespace.
  • news_web owns 508 established connections to infra-chrome:9222. personal_assistant owns none.
  • Each leaked client connection causes CloakBrowser to retain two loopback socket endpoints to Chromium on port 5100.
  • news_web itself retains 512 sockets and logged 3,453 remote-browser connection attempts in the retained log window.
  • The deployed client repeatedly reaches the TCP preflight, then Browser.create() fails without releasing the partially opened WebSocket.
  • The periodic process monitor calls get_browser() every five minutes, so it actively creates more failed connections while the browser is unavailable.
  • The previous repair restarted only infra-chrome. That reset its descriptor count but did not repair the client reconnect lifecycle, so the failure accumulated again.

Confirmed Telegram Delivery Incident

  • The last user-observed successful channel digest was 24 July 2026.
  • Article ingestion, processing, scheduling, and daily-summary generation continued; on 19 August the service generated eight daily summaries before attempting delivery.
  • The rich-message request failed with Telegram HTTP 400 Bad Request: chat not found, and the regular HTML fallback failed with the same response.
  • The configured production channel ID matched the expected value, was a clean string, and had not changed since 7 March.
  • The production token belonged to @evening_news_bot. A different bot with the same display name had been granted channel administrator rights, so the production bot could not address the channel.
  • After the correct bot was added, Bot API verification reported administrator with can_post_messages=true, and a short message sent through the production TelegramService succeeded.
  • The separate service chat was verified as reachable during diagnosis, but the digest failure path did not use it to notify the user.
  • send_telegram_digest() returned only success=false after fallback failure, losing the Telegram error detail; the scheduler logged unknown error and then unconditionally logged that the complete cycle finished successfully.

Root Causes

Chrome/CDP resource exhaustion

The primary defect is in the Evening News remote-browser connection lifecycle. A failed or interrupted nodriver connection is abandoned without awaiting Connection.aclose(). CloakBrowser correctly sees the client socket as still open and keeps the corresponding proxy connection to Chromium. Repeated application and monitor retries eventually exhaust the server's file-descriptor limit.

CloakBrowser's multiplexer amplifies the resource cost, but raising nofile or restarting only Chrome would merely delay recurrence. The client must close partial and stale sessions and bound its reconnect rate.

Telegram delivery reported as success

The immediate Telegram outage was an operational identity mismatch: the configured channel ID was correct, but administrator access had been granted to a different bot. The software defect was the handling of that external failure. Low-level send methods collapsed Telegram's structured HTTP error into False; the orchestrator therefore returned no useful error, and both scheduler paths treated an unsuccessful result as a warning rather than a failed task. The final unconditional success log made a multi-week delivery outage invisible.

Desired Behavior

  • One shared CDP connection is reused while healthy.
  • A failed, timed-out, stale, or cancelled connection is explicitly and asynchronously closed.
  • Only a fully started browser object is published to the global pool.
  • Reconnect attempts have a finite timeout and cooldown, preventing retry storms.
  • The process monitor observes and cleans state without creating an unbounded stream of connections.
  • A Chrome restart is followed by a successful client reconnect, and descriptor counts return near baseline.
  • Every Telegram attempt returns structured success or failure details without exposing bot tokens or chat IDs.
  • If both rich delivery and regular fallback fail, the digest task is marked failed and cannot emit a success completion log.
  • A single non-recursive alert is sent to the independently configured service chat when channel delivery fails.
  • The service chat is the standard operational channel for scheduler failures, task timeouts, stuck-task recovery, Chrome unavailability, and digest-delivery failures.
  • Repeated instances of the same problem are deduplicated and summarized; isolated per-source extraction errors do not create one alert per article.
  • Scheduler status exposes the last outcome, last error, and last successful completion instead of only last_run.
  • Manual digest API requests return a failure status when generation succeeds but delivery does not.

Assumptions and Boundaries

  • The production channel ID and bot token remain unchanged; no credential rotation is planned.
  • The verified service chat remains a distinct, reachable notification target.
  • Generated summaries remain valid when delivery fails, so recovery may resend an existing digest without regenerating it.
  • Delivery failures will not trigger an unbounded automatic retry loop; the normal next schedule remains authoritative unless a manual resend is requested.
  • The expired Tailscale node key for wireguard is a separate infrastructure issue. Direct SSH access works and the Tailscale repair is not bundled into this application deployment.
  • No unrelated AGENTS.md or existing working-tree changes are part of this implementation.

Recommended Implementation

Chrome/CDP lifecycle

  1. Refactor news_aggregator/core/browser_pool.py to create a candidate Browser, await its startup with a bounded timeout, and call await candidate.aclose() on every exception or cancellation before re-raising.
  2. Do not assign the candidate to _browser until startup, attach, and target discovery have all completed.
  3. Replace fire-and-forget browser.stop() cleanup with an awaited, timeout-bounded asynchronous close for remote connections. Clear the global reference before awaiting close so concurrent callers cannot reuse a closing object.
  4. When an existing connection is stale, close it before reconnecting instead of setting _browser = None and losing the cleanup handle.
  5. Add a reconnect cooldown after failures. Calls during the cooldown fail fast with the last typed error rather than opening another socket. A successful connection resets the cooldown.
  6. Change the process monitor to inspect the pool state and invoke the same bounded reset path; it must not bypass the cooldown or create parallel reconnect attempts.
  7. Log the exception type as well as its message so empty TimeoutError messages are diagnosable.
  8. Pin the tested nodriver version in requirements.txt instead of the current open-ended lower bound. The exact version will be selected by the isolated compatibility test, not guessed in production.

Telegram delivery and scheduler truthfulness

  1. Introduce an internal TelegramDeliveryResult value containing success, transport, HTTP status, Telegram error code/description, and message ID when available. Keep tokens and chat IDs out of logs and API responses.
  2. Make regular, rich, split-part, and service-message paths preserve their actual result. When rich delivery and regular fallback both fail, retain both attempts and surface the final actionable Telegram description instead of unknown error.
  3. Have send_telegram_digest() return the expected and delivered part counts plus structured attempt details. Partial split delivery is a failure, not success.
  4. In both scheduler digest paths, treat an unsuccessful delivery as a task exception after attempting one service-chat alert. The alert failure is logged but never recursively alerts or hides the original channel failure.
  5. Centralize operational alerts for all scheduler task exceptions, timeouts, stuck-task recovery, and Chrome unhealthy/recovered state transitions. Use a bounded deduplication window and send a recovery notification after a previously alerted condition clears.
  6. Aggregate source-level processing failures into the task summary. Do not send one Telegram alert for every failed article or retry attempt.
  7. Persist generic scheduler outcome fields: last_status, last_error, and last_success_at. Update them centrally in the task executor so no task can be logged as successful after raising or returning a failed result.
  8. Return an appropriate non-2xx response from the manual send-digest endpoint when delivery fails, while retaining a safe structured body for the admin UI.

Implementation Steps

  1. Add focused failing unit tests for partial connection cleanup and reconnect throttling.
  2. Implement one private close helper that always awaits aclose() with a timeout and suppresses only cleanup failures.
  3. Refactor candidate startup so failed objects remain reachable for cleanup.
  4. Add monotonic-time cooldown state protected by the existing connection lock.
  5. Route process-monitor cleanup through the same pool functions.
  6. Run the focused tests, then the full relevant Python test suite and static checks.
  7. Add failing tests that reproduce Telegram HTTP 400, failed rich fallback, partial split delivery, and the scheduler's current false-success log.
  8. Implement structured Telegram delivery results and adapt every existing caller.
  9. Add a single service-chat failure alert with a recursion guard and safe redaction.
  10. Route scheduler exceptions, timeouts, stuck-task recovery, and Chrome state transitions through the same deduplicated operational-alert helper.
  11. Add and validate the scheduler outcome migration, then expose the fields through the existing scheduler API.
  12. Make scheduled and manual digest entry points propagate failure truthfully.
  13. Build an immutable Evening News image and record its digest.
  14. Run a non-production CDP smoke test: connect, open/close a tab, interrupt the browser, reconnect, and verify descriptor counts return to baseline.
  15. Only after the smoke test, perform the controlled production recovery and deploy the reviewed image.

Controlled Production Recovery

After explicit approval and once the permanent image is ready:

  1. Capture a final read-only snapshot of container identity, descriptors, connections, and health.
  2. Stop news_web first so its 508 client sockets are closed.
  3. Restart infra-chrome and wait for /json/version to return HTTP 200 with a low descriptor baseline.
  4. Deploy/start the reviewed Evening News image by immutable digest.
  5. Exercise one real browser-backed extraction path.
  6. Verify both containers, the public news health endpoint, CDP connection count, tab cleanup, logs, and descriptor stability over a bounded observation window.

If immediate service restoration is desired before the code fix, the same stop-Chrome-start sequence can be used as a temporary recovery, but recurrence remains possible and must be stated explicitly.

Test Plan

  • Failed startup closes the candidate WebSocket and leaves _browser unset.
  • Cancelled startup performs the same cleanup.
  • A stale shared browser is closed before replacement.
  • Repeated calls during cooldown do not call the connection factory again.
  • A successful retry resets failure and cooldown state.
  • Shutdown awaits remote connection closure.
  • Browser tab cleanup still runs on success, extraction error, and cancellation.
  • Integration smoke: browser restart followed by reconnect does not increase established sockets on each retry.
  • Production soak: descriptor and connection counts remain stable after scheduled fetch and process-monitor cycles.
  • Telegram HTTP 400 preserves Bad Request: chat not found through service, orchestrator, scheduler, and manual API boundaries.
  • A failed rich message followed by successful HTML fallback is reported as delivered with both attempts recorded.
  • Failure of both rich and HTML delivery marks the scheduled task failed and emits no success completion log.
  • Partial split delivery reports expected and delivered counts and remains failed.
  • Exactly one alert is attempted against the service chat; alert failure does not recurse or replace the primary error.
  • Repeated identical task/Chrome failures inside the deduplication window do not produce repeated alerts.
  • A recovery transition produces one recovery message and resets the deduplication state.
  • Multiple article/source failures are summarized in one task-level alert rather than emitted individually.
  • Successful delivery records last_status=success, clears stale error text, and advances last_success_at.
  • Failed delivery records last_status=failed and a redacted actionable error while preserving the previous successful timestamp.
  • The migration is idempotent on a production-like schema and rollback removes only the newly added nullable fields.

Data, API, and Operational Impact

  • Database: five nullable outcome fields are added to schedule_settings; existing schedules require no backfill and initially report an unknown outcome.
  • API: scheduler responses gain optional outcome fields. Manual digest delivery changes from HTTP 200 with success=false to a non-2xx delivery error with a safe structured body.
  • Telegram: no bot, token, channel ID, or permission changes are part of the code deployment. Production access has already been repaired operationally.
  • Notifications: the service chat becomes the standard operational channel for significant task and infrastructure failures. Alerts are concise, deduplicated, non-recursive, and paired with recovery messages.
  • Deployment: the application migration runs before the replacement image handles schedules. Chrome recovery retains the controlled stop/restart/start order.

Manual QA Checklist

  • news_web and infra-chrome report healthy.
  • The public news health endpoint returns the expected success response.
  • One JavaScript-heavy article extraction succeeds.
  • One Telegram browser extraction succeeds if a configured source is available.
  • Open tab count returns to baseline after each extraction.
  • Only one shared client CDP connection remains established during idle operation.
  • No repeating connection or process-monitor errors appear in fresh logs.
  • A manual Telegram test reaches the main channel through the production service.
  • A simulated main-channel failure reaches the service chat exactly once and is visible as failed in scheduler status.
  • A successful digest updates scheduler status and contains the expected full-version link.
  • The next scheduled run uses the normal schedule rather than entering a retry storm.

Risks

  • Stopping news_web creates a short production outage during recovery.
  • A cleanup timeout must not leave the connection lock held.
  • An overly long cooldown could delay recovery; an overly short cooldown could recreate the retry storm.
  • CloakBrowser 0.5.8 may change Chromium identity or licensing behavior and therefore requires a separate image/digest review.
  • A malformed service-chat configuration could make alert delivery fail; the primary channel error must remain visible in logs and scheduler status.
  • Changing low-level Telegram methods from booleans to structured results requires auditing every caller to avoid truthiness regressions.
  • A scheduler-status migration must remain backward compatible during image rollback.
  • Including raw Telegram response bodies could leak identifiers; only allowlisted error fields may be persisted or returned.
  • The repository contains an untracked AGENTS.md; it must remain outside the implementation diff unless the user explicitly asks to add it.

Rollback Plan

  • Keep the current Evening News image ID and production compose unchanged until the replacement passes smoke tests.
  • If the new client lifecycle regresses extraction, redeploy the previous immutable image and restart the pair in the controlled order.
  • If CloakBrowser remains unstable, revert the browser service to the previously used raw Alpine Chrome image while preserving the same internal CDP contract.
  • Do not use a larger nofile limit as rollback or remediation; it only increases time to exhaustion.
  • If structured Telegram results regress a caller, redeploy the previous image; nullable scheduler fields may safely remain until a reviewed cleanup migration.
  • If service alerts are noisy or misrouted, disable only the alert call while retaining truthful task failure and persisted status.

Implementation Record

Implemented on branch fix/evening-news-reliability in an isolated local worktree. No production container, database, compose file, bot permission, or deployed image was changed by this implementation.

  • Remote nodriver candidates are now retained until startup succeeds, and failed, cancelled, stale, tab, and shutdown paths await bounded cleanup.
  • Reconnect attempts share one lock and a 60-second monotonic cooldown; the process monitor is passive and cannot create sessions merely to check health.
  • nodriver is pinned to 0.50.3, the version inspected and tested for the lifecycle contract.
  • Telegram sends return a structured result containing safe HTTP/Telegram error fields; Bad Request: chat not found is preserved through digest orchestration.
  • Scheduled digest delivery now raises on final delivery failure instead of logging a false success. Manual delivery returns HTTP 502 with a safe structured body.
  • Scheduler runs persist start/finish/success timestamps, status, redacted error, and duration. Failures do not overwrite the previous successful timestamp.
  • Task failures, timeouts, stuck recovery, aggregated processing warnings, scheduler-loop/capacity problems, and Chrome unavailable/recovered transitions use a deduplicated service-chat alert manager.
  • Review follow-up made failed alerts retry immediately without phantom recovery, added environment-backed service-chat fallback when the database is unavailable, and classified top-level processing failures as failed scheduler runs.
  • The required scheduler outcome migration now blocks startup when its application cannot be guaranteed; the browser monitor sends alerts without constructing the full orchestrator.
  • Backup script absence and non-zero exit status no longer disappear as successful scheduled runs.
  • The Docker workflow now runs the full deterministic pytest suite in Python 3.12 first; build-and-push has an explicit needs: test gate.

Verification: python -m py_compile passed for changed Python modules; pytest tests/ -q completed with 51 passed, 4 skipped in the final local review. The four skipped tests are real external Chrome/network smoke checks and now require RUN_REAL_BROWSER_TESTS=1. Production CDP smoke, descriptor soak, migration execution, image build, and deployment remain intentionally pending.
