Implementation Plan: CloakBrowser Infra Browser

Approval required before implementation

Task Summary

Evaluate and wire CloakBrowser as the separate browser infrastructure service for Evening News, preserving the current app contract of connecting to a Chrome DevTools Protocol endpoint at BROWSER_WS_ENDPOINT=ws://browser:9222.

Current Behavior

  • docker-compose.example.yml defines a browser service using gcr.io/zenika-hub/alpine-chrome:123.
  • The web app depends on browser and connects through BROWSER_WS_ENDPOINT=ws://browser:9222.
  • news_aggregator/core/browser_pool.py uses nodriver to connect to a remote CDP endpoint and serializes tab use with a single-tab semaphore.
  • docker-compose.dev.yml currently leaves browser support commented out for dev.
  • Relevant tests already exist around the browser pool and extraction: tests/test_browser_pool.py, tests/test_extraction_browser.py, and tests/test_website_extraction.py.

Upstream Facts Checked

  • CloakBrowser ships a Docker image with EXPOSE 9222.
  • The image includes a cloakserve command, described upstream as a CDP multiplexer.
  • cloakserve defaults to port 9222, serves /json/version, and launches patched Chromium processes behind that endpoint.
  • The upstream Dockerfile pre-downloads the Chromium binary during image build, but production should still pin the image tag and avoid floating latest.

Desired Behavior

The application should keep using the same CDP endpoint shape, while the browser container runs CloakBrowser instead of Alpine Chrome. The first implementation should be reversible and isolated, preferably through a Compose override or clearly scoped browser service change.

Recommended Approach

Start with an infra-only spike: add a CloakBrowser compose override and verify that nodriver can connect to cloakserve without changing Python extraction code. Only replace the default production browser service after the smoke test passes. 

browser:
  image: cloakhq/cloakbrowser:<pinned-version>
  command: ["cloakserve", "--port=9222"]
  environment:
    - CLOAKBROWSER_AUTO_UPDATE=false
  networks:
    - news_network
  restart: unless-stopped
  healthcheck:
    test: ["CMD-SHELL", "curl -fsS http://localhost:9222/json/version >/dev/null"]
    interval: 30s
    timeout: 10s
    retries: 3
    start_period: 30s

Files Likely to Change

  • docker-compose.cloak.yml - new local/prod-like override for the CloakBrowser browser service spike.
  • docker-compose.example.yml - after validation, optionally replace the default browser image/command and add a healthcheck.
  • README.md and CLAUDE.md/AGENTS.md - update browser infrastructure notes if the migration is accepted.
  • tests/ - only if nodriver needs a small endpoint compatibility adjustment.
  • news_aggregator/core/browser_pool.py - only if cloakserve requires HTTP endpoint handling that the current host/port parsing cannot support.

Implementation Steps

  1. Create a Compose override that replaces only the browser service with CloakBrowser running cloakserve --port=9222.
  2. Use a pinned image tag or digest if one is available locally from Docker metadata; do not ship latest as the final default.
  3. Set CLOAKBROWSER_AUTO_UPDATE=false for deterministic runtime behavior.
  4. Start only the browser service and verify /json/version returns a CDP WebSocket URL.
  5. Start the app with BROWSER_WS_ENDPOINT=ws://browser:9222 and verify browser_pool.get_browser() connects.
  6. Run focused browser/extraction tests and inspect logs for CDP connection, tab open, content fetch, and tab close behavior.
  7. If the override works, update the default production example compose and docs.
  8. If it does not work, keep the override as an experimental artifact or delete it and document the blocker.

Test Plan

  • docker compose -f docker-compose.example.yml -f docker-compose.cloak.yml up -d browser
  • docker compose -f docker-compose.example.yml -f docker-compose.cloak.yml exec browser curl -fsS http://localhost:9222/json/version
  • docker compose -f docker-compose.example.yml -f docker-compose.cloak.yml logs --tail 120 browser
  • pytest tests/test_browser_pool.py -q
  • pytest tests/test_extraction_browser.py tests/test_website_extraction.py -q
  • Manual extraction smoke test against one JS-heavy page, one Telegram public channel page, and one custom page-monitor source if credentials/data are available.

Deployment and Runtime Impact

  • No database schema or API contract changes are expected.
  • The browser container image will likely be larger than Alpine Chrome and may use more memory.
  • The app remains isolated from browser binaries; the Python app container continues to depend only on nodriver.
  • Network exposure should remain internal to the Compose network unless a test explicitly publishes port 9222 locally.

Risks and Edge Cases

  • nodriver may not fully tolerate cloakserve's rewritten CDP WebSocket URLs.
  • CloakBrowser image tags and binary licensing need a final pinning/licensing check before production deployment.
  • CloakBrowser may spawn one Chromium process per fingerprint seed; we should keep the current single-tab behavior until resource usage is measured.
  • Auto-update or first-run downloads at runtime would make production less deterministic if not disabled or pinned.
  • The existing checkout has corrupt/missing Git objects; committing this work from the current clone may require repairing or recreating the repository first.

Rollback Plan

Remove the CloakBrowser override or revert the browser service back to gcr.io/zenika-hub/alpine-chrome:123. Because the app contract stays ws://browser:9222, rollback should not require application code changes.

Open Questions

  • Which image tag or digest should be pinned after Docker metadata is inspected?
  • Should the first change stay as an optional docker-compose.cloak.yml override, or replace docker-compose.example.yml after smoke testing?
  • Do we want persistent fingerprint seeds for specific sources, or should the default random identity per browser process remain for now?

Approval Gate

Implementation must not start until this plan is explicitly approved. Approval means creating the CloakBrowser Compose override first, running the CDP smoke checks, then deciding whether to promote the change into the default production Compose file.
