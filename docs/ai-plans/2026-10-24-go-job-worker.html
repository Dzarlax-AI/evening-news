1. Результат и честная граница первого этапа

Сначала отделяем механизм исполнения заданий от News-кода. Новый Go worker владеет PostgreSQL lease, heartbeat, claim, ограничением активной работы, timeout, recovery, retention и терминальными состояниями. Python становится приватным исполнителем уже существующих доменных операций: обработка статей, AI, selector learning, сохранение News-данных, дайджесты и бэкапы.

После этого этапа NewsOrchestrator.run_full_cycle ещё остаётся на Python. Перенос последовательности collect → process → summaries → delivery в Go — следующий этап с отдельным контрактом шагов. Нельзя назвать вызов целого Python pipeline по HTTP завершённым переносом оркестратора.

Web продолжает принимать задания в существующие таблицы и читать их статус. Go забирает потребление очереди и управление жизненным циклом, но первый релиз не переносит producer API в отдельный универсальный queue service. Переиспользуемое ядро Go не должно импортировать модели Article/Category или знать Gemini/Telegram: News-специфичные правила располагаются в отдельном адаптере.

3. Почему перенос разбит

ВариантРешение

Python executor остаётся отдельным процессом, поэтому экономия памяти и ускорение заранее не обещаются. Его функции и AI-модель не переписываются. Проверяем преимущество прежде всего в чётком ownership и возможности независимо развивать Go runner.

4. Новый приватный контракт

Предлагаемые, ещё не существующие компоненты: модуль go-worker/ с cmd/worker, пакетами store/runner и News adapter; Python entrypoint news_aggregator/executor.py с ограниченным private API. Исполнитель не запускает старый consumer, не захватывает worker lease и не производит расписания.

  • POST /internal/v1/job-executions: версия, job_id, owner_id, generation, attempt_generation, неизменный deadline_at. Тип операции и payload исполнитель читает из DB; caller не передаёт произвольные URL, Python modules, prompts или команды.
  • Короткий ответ 202 означает durable acceptance, а не успешное завершение. GET /internal/v1/job-executions/{job_id}/{attempt} возвращает bounded state/result; результат — только существующие безопасные скаляры, без HTML/статей/токенов. Go сам завершает job после проверенного результата.
  • Один повтор идентичного старта возвращает тот же receipt; изменение immutable envelope даёт conflict. Потеря POST-ответа сначала разрешается чтением receipt. HTTP timeout не считается доказательством, что исполнитель остановился.
  • Нужна одна additive таблица background_job_executions, ключ job_id + attempt_generation, immutable envelope hash, executor instance, state/timestamps и bounded result/error. Она фиксирует acceptance и исход после потери связи. FK/retention должны позволять удалять terminal job без удаления scheduler occurrence receipts. Старые jobs без execution receipt сохраняются.
  • Отдельный service token, фиксированный executor endpoint/alias, private network без публичного порта/Traefik route. Поддерживается ровно один Python executor на DB schema: он удерживает отдельный session advisory lock, отказывает в старте второму процессу и теряет readiness при разрыве lock connection. Executor endpoint должен вести прямо на этот singleton без балансировки или перекрывающегося rolling replacement. Body максимум 8 KiB, durable result максимум 4 KiB; строгие методы, version/schema, no redirects, finite error codes. Секреты не попадают в очередь, HTTP errors, logs или fixtures.

Не удерживать HTTP request или DB transaction на время AI. Task создаётся под собственным fence context. После restart Python не переисполняет незавершённые receipts сам: Go выявляет потерю executor instance, инвалидирует старую попытку и применяет recovery policy. Отдельный singleton advisory lock и durable receipt исключают параллельный запуск одного receipt; различие instance ID служит доказательством остановки старого процесса только при указанной топологии без параллельных экземпляров и балансировки.

5. Инварианты корректности и восстановления

  • Go держит session advisory lock на выделенном pgx connection; потеря connection/heartbeat запрещает новые claims, отменяет активное исполнение и закрывает session. Нельзя вернуть владеющее lease соединение в pool. Heartbeat не конкурирует за один pgx connection с произвольными длительными запросами.
  • Python перед commit проверяет актуальный DB owner, generation, статус job и attempt; row locks удерживаются через commit. Владение advisory lock и свежесть lease должны быть доказуемы для удалённого fence. Одна проверка bearer token или generation из HTTP недостаточна. До портирования обязательны race-пробы с реальным PostgreSQL и takeover.
  • При неизвестном исходе RPC Go не запускает параллельный дубль. Для non-delivery jobs: invalidate attempt → interrupted/reclaim с новым attempt_generation; завершённые article stages и попытки сохраняются. Для jobs, способных отправить дайджест, сохраняется нынешняя консервативная delivery_unknown policy без автоматической повторной отправки.
  • Article retry counters и job recovery attempts — разные вещи. Существующее ожидание busy/admission не расходует article attempts и не откладывает статью по старому получасовому пути. Числа recovery/timeout брать из действующих настроек; не повышать concurrency или browser limits.
  • Начальная подготовка article_reprocess переносится в Python executor: reset и initialized_at в одной fenced транзакции. После takeover повтор подготовки не сбрасывает уже сохранённые стадии.
  • Backup остаётся с общим persistent storage. Повтор/обрыв не перезаписывает чужой архив; временные файлы принадлежат конкретной попытке. Сценарии записи/публикации файла при потере fence проверить отдельно: DB fence сам по себе не защищает файловую систему или внешнюю отправку.
  • Alert failure/recovery и legacy completion остаются через существующий Python News-адаптер: фиксированные события по job_id, чтение сохранённого результата, прежняя дедупликация; не два независимых отправителя уведомлений.

Exactly-once Telegram/Telegraph delivery и exactly-once AI billing не обещаются. Отправка во внешнюю систему и DB commit не являются общей транзакцией. Неопределённость сохраняется явно, вместо слепого replay.

8. Следующий этап: сам оркестратор на Go

После успешного первого этапа расширяем контракт с whole-job executor на явные domain stages. Go выбирает последовательность collect/persist → article processing → summaries → delivery, владеет checkpoint/retry и решением о следующем шаге. Python продолжает только согласованные доменные операции и AI. Нужно отдельно определить ownership selector/cursor state, durable stage checkpoints, атомарное подтверждение результата, сохранение category/ad filtering и публикаций.

Это последующая работа, не включённая в approval первого этапа. Для неё план уточняется по фактическому receipt/fence implementation. Полный перенос source-state/News persistence или переделка AI не прячутся в эту часть. Переписывать полный pipeline одновременно с новым queue transport не предлагается.

9. Откат, границы разрешения и одобрение

Разработка и fixtures не меняют production. Будущий cutover: остановить dispatch, дождаться drain, сохранить jobs/receipts/config и due instants, применить additive schema, остановить прежнего владельца и включить одного нового. Прежний immutable Python worker image сохраняется для отдельно разрешённого отката. Перед возвратом старого владельца остановить Go и Python executor, доказать отсутствие старых writers, сохранить новые receipts и неопределённые delivery outcomes. Не восстанавливать старый DB snapshot поверх живой очереди и не удалять таблицы/тома.

На одобрение: первый этап — Go queue/job lifecycle и приватный Python executor, additive execution receipts, synthetic/local проверки, реализация на Луне, PR и независимый review. Пока без переноса NewsOrchestrator в Go, без AI redesign, без merge/publication/deployment и без изменений браузера/Readeck. Любое material расширение контракта или границ требует обновить этот же план и согласовать дельту.

Планирование: основную ветку и пользовательские dirty файлы не меняли; чтение сохранённой памяти использовалось для ограничений, текущая архитектура проверена по deployed main. Новых замеров эффективности или гарантий ускорения нет.

11. Production cutover — разрешён 24 октября 2026

Пользователь разрешил выкатку («давай деплить»). Разрешение включает необходимый merge PR #21, публикацию проверенных app/executor и Go job-worker образов через CI и ограниченное переключение этих процессов. Общий browser, Readeck, extractor, egress, PostgreSQL, Traefik и scheduler image/config не меняются и не перезапускаются. Единственное временное действие над scheduler — revision-protected pause/resume dispatch; due instants и schedule revisions сохраняются.

  1. Исправить недостающую CI publication Go worker: normal Dockerfile, main-only GHCR SHA tag, guard против существующего tag и per-SHA serialization; независимый review, PR CI, merge и main CI.
  2. От актуального server Compose подготовить candidate. Web меняет только image. Прежний Python worker становится private executor с теми же data/backups/cache/logs, outbound/control identity и лимитом 512 MiB; новый Go worker получает 64 MiB и только DB/private executor networks. Новый token и Go DB URL — в новых root-only env files, без перезаписи существующих .env. Оба background процесса имеют 180s stop grace.
  3. Сохранить immutable image pins, canonical config, полную очередь/receipts и scheduler inventory в root-only rollout directory. Сравнить fingerprints исключённых контейнеров. Pause dispatch, дождаться пустой активной очереди и отсутствия leased dispatch, сделать backup News schema; не менять due times и не удалять jobs.
  4. Остановить старого Python owner; запустить candidate web с additive migration 011, затем один Python executor и один Go worker. При проблеме остановиться до resume и сообщить; rollback — отдельно разрешённое решение с сохранением новых receipts и delivery_unknown, без restore старого snapshot поверх очереди.
  5. Проверить schema/health/auth isolation, Go lease backend и heartbeat, реальный durable dry-run job (без сайтов/AI/отправок), публичную страницу/feed, admin facade, memory/restarts и неизменность исключённых контейнеров.
