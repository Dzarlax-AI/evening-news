Дайджесты: восстановление SR, все категории и push-уведомления

Редакция 2 · 12 ноября 2026 · Одобрено пользователем; передано в новую сессию для выполнения.

Команда пользователя: «Исправляй через PR и восстанови сербский дайджест за 11 ноября с отправкой. И сделай так, чтобы такие пропуски больше не считались успешными».

1. Результат и границы

Отдельный PR от актуального main, исправление неполных результатов генерации/доставки и восстановление ровно сербского выпуска 11 ноября 2026 в прежний настроенный сербский Telegram-канал. Реальный AI-вызов для этого выпуска и его отправка разрешены приведённой командой; повторного разрешения на них после согласования плана не требуется.

  • Не готовый обязательный SR-выпуск больше не выдаётся за успешный SR retry или полностью успешный двуязычный запуск.
  • Успешный русский выпуск и его подтверждённая доставка сохраняются. Не перегенерировать и не отправлять RU повторно.
  • До вызова Telegram — явная конечная причина ошибки. После начала внешней отправки неопределённость остаётся delivery_unknown, без слепого повтора.
  • В этапе A не менять структуру БД, авторизацию, источники, browser/egress, Readeck, публичный API дайджеста или iOS. Этап B добавляет только необходимую push-инфраструктуру, миграции, ограниченный API подписок и iOS-клиент, описанные в дополнении v2 ниже.

3. Изменение поведения

  • Разделить безопасные диагностические причины: нет перевода категории, не готовы переводы/исходные данные, исчерпан разрешённый лимит генерации, ошибка провайдера. Не включать в публичные ошибки тексты статей, SQL или приватные настройки.
  • SR retry считается успешным только после существования корректного SR-выпуска; если доставка была разрешена сохранённой политикой — также после подтверждённой либо уже выполненной идемпотентной отправки. Отсутствие SR не маскируется нулём отправленных частей.
  • Для двуязычного основного задания недостающий обязательный SR отражается явным неполным/неуспешным результатом, а не общим зелёным успехом. RU receipt остаётся completed. Проверить путь от domain receipt через orchestration до durable job/error code и существующего механизма оповещения об ошибках.
  • Сохранить явные режимы отключённой SR-генерации или доставки: они не требуют отправки. Не менять зафиксированные настройки уже работающих заданий.
  • Исправить границу внешнего действия: только доказанные ошибки до публикации получают безопасный failed. Реальная сетевая неоднозначность, потерянный receipt и устаревшее fencing-поколение не становятся основанием для автоматической повторной отправки.
  • Ограничения автоматических попыток сохраняются. Исторические 12 заданий и их счётчики не переписываются задним числом.

5. Выполнение и роли

  1. После согласования — последовательная реализация одним исполнителем gpt-6-luna, medium: domain, затем зависимый execution, tests и операторская процедура. Один владелец связанных файлов устраняет конфликт private error-контракта. Контракты и предельные случаи задаёт ведущий агент.
  2. gpt-6.1-sol, high — отдельное focused review фактического diff: ложный успех, граница отправки, сохранность RU, повтор recovery и unknown. Исполнитель исправляет конкретные замечания; ведущий проверяет исходники и результаты.
  3. Commit/push/PR, автоматический review, PostgreSQL 16/17 и штатные CI gates. После зелёных проверок — merge, публикация точного accepted candidate без VPS build.
  4. Выпуск необходимых executor и background образов: первый содержит domain, второй — go-execution. Для согласованной category validation дополнения v2 требуется также обновить web (app в production Compose), без других web-изменений. Перед заменой проверить активные задания и штатно завершить/осушить их без потери receipts. Закрепить immutable digests; остальные контейнеры не перезапускать.
  5. Ведущий выполняет recovery по процедуре ниже и проверяет реальные receipts. Обновить этот же план фактическими результатами.

Реализация этапа A начата 12 ноября: Luna medium ведёт domain/execution и recovery-процедуру; ведущий — category validation, интеграцию и production. Конкретная production-отправка остаётся за ведущим агентом.

6. Проверки

  • Регрессии с isolated loopback PostgreSQL: отсутствует только перевод категории; нет перевода статьи; исходная статья изменилась; provider error; лимит попыток исчерпан. Во всех обязательных SR-сценариях нет succeeded без выпуска.
  • Обычная RU-генерация/отправка сохраняется при отложенном SR; основной двуязычный job явно сообщает недостающий SR. Отключённая доставка отдельно остаётся корректным режимом.
  • До внешнего I/O — failed с конечной причиной. Неизвестный outcome после отправки — delivery_unknown. Старые и ошибочные receipts, подменённые UUID/locale/date и stale fence не приводят к отправке.
  • Recovery SQL: двойной запуск создаёт одну задачу; конкурентная активная попытка, completed/частично отправленный/unknown receipt запрещают слепой повтор; исходные 12 dispatches и готовый RU не меняются.
  • go test -race -count=1 ./..., go vet ./..., go mod verify в затронутых модулях; PostgreSQL 16/17 и полный synthetic integration gate в CI. В тестах только fake providers и fake Telegram.
  • Production: health, свежий heartbeat, restart/OOM, нормальные scheduled receipts, защищённые соседи. Публичный pinned SR detail и HTML за 11 ноября, затем completed delivery intent и подтверждённая часть/Telegram message receipt. Принятая queue-задача не считается отправкой.

7. Восстановление 11 ноября

Цель — исходный RU-выпуск 6c215a61-23ad-58af-bab2-2db2df086401, дата 2026-11-11, только парный sr-Latn. Композиция берётся из сохранённого RU snapshot/плана, а не из текущей ленты. Настроенный адресат берётся из прежней pinned policy; его значение не печатается и не меняется.

  1. Непосредственно перед admission повторно проверить отсутствие парного SR и sent/completed/unknown частей/intent, отсутствие активного SR job и неизменность RU ID/date/policy.
  2. В одной короткой транзакции проверить/заполнить отсутствующие переводы категорий и допустить один recovery job с устойчивым idempotency key. Не сбрасывать attempts/dispatches и не подменять payload старого задания. Существующий worker выдаёт новый claim/fence; обычный serbian_digest_retry использует сохранённую дату и адресата.
  3. Существующий ограниченный provider workflow создаёт только SR и штатно отправляет его. После generation/send ошибки не создаётся новая неограниченная цепочка повторов.
  4. Проверить парность date/locale/плана, публичную доступность, job result и фактическую доставку. При unknown остановить повторные отправки и исследовать receipt; не считать timeout доказательством отсутствия сообщения.

Поведение пушей

  • В Settings появляется опция уведомлений о новом дайджесте. Системное разрешение запрашивается после явного включения пользователем, без обязательного диалога при первом запуске. Отказ, отзыв разрешения, регистрационная ошибка и ожидающее подтверждение устройства показываются честно.
  • Язык подписки следует выбранному языку новостей: RU и SR — отдельные готовые выпуски. RU-пуш не ожидает SR, SR-пуш не приходит до сохранения корректного SR-выпуска. Категории не дробят один дайджест на серию уведомлений.
  • Нажатие открывает вкладку «Дайджест» с точными date/locale/edition_id, включая холодный запуск. Устаревший payload валидируется, не меняет язык скрытно и не подставляет другой день. Изменение языка в Settings синхронизирует подписку и отменяет ещё не отправленные события старой версии подписки.
  • Обычная дедупликация: не больше одного события нового дайджеста на устройство/день/язык, даже при новой редакции выпуска, повторе транзакции или рестарте worker. Ссылка остаётся pinned на выпущенную редакцию. Новая подписка не получает весь архив; уже восстановленный ноябрьский выпуск не рассылается задним числом всем новым подписчикам.
  • APNs acceptance и фактическое получение на устройстве — разные результаты. HTTP 200 помечает accepted; подтверждённую доставку можно заявить только для реально проверенного устройства. Потерянный ответ не становится accepted; нет бесконечных слепых повторов или обещания exactly-once показа.

Backend и граница регистрации устройства

  • Создать durable outbox в той же транзакции, где впервые сохраняется готовый выпуск. Fanout и APNs-запросы выполняются после commit ограниченными пакетами через существующие News-компоненты, без нового контейнера. Ошибка APNs не откатывает дайджест, RU/SR-генерацию или Telegram.
  • Новые миграции: installations/subscriptions, события готовности и delivery attempts с unique keys, leases, ограничениями попыток, TTL и конечными статусами. Cutover фиксируется явно; миграция не сканирует старый архив для рассылки. Проверить все production writers выпуска: Generate и persistLocalizedEdition, повторные вызовы и сбои транзакции.
  • Предлагаемый узкий API: POST /api/public/push/installations создаёт pending-регистрацию; POST /api/public/push/installations/{id}/activate подтверждает её; PUT и DELETE того же installation меняют язык/токен или отключают свою подписку. GET списка чужих устройств отсутствует.
  • Первичная регистрация должна подтвердить владение устройством через APNs challenge: приложение принимает nonce только для собственной текущей pending-регистрации. Дальнейшие операции требуют отдельного installation capability из Keychain; сервер хранит его hash. Сам по себе client UUID, device token или общий secret, встроенный в приложение, не даёт права менять чужую подписку. Смена токена требует повторной проверки привязки. Неактивированные записи имеют короткий TTL.
  • Ограничить IP/installation/token rate, размер и формат запросов, nonce TTL и число проверочных уведомлений. При недоступном APNs регистрация остаётся pending, а не фиктивно enabled. Не выводить device tokens, capability, nonce, payload или APNs private key в логи/публичные DTO.
  • APNs private key хранится только в domain credential storage: расширить provider allowlist/schema безопасно, использовать существующее шифрование и минимальные роли. Public web передаёт регистрацию private domain; он не получает APNs signing key. Routing tokens шифруются, удаляются при отписке и очищаются по политике неактивности. Новые grants, runtime/config catalog и управление integration credentials рассматриваются вместе.
  • Topic задаётся серверной конфигурацией для com.dzarlax.NewsFeed. Sandbox/production изолированы. Обрабатывать невалидные токены и ответы APNs; ответ для старой версии токена не должен деактивировать уже обновлённую привязку. Ограниченные повторы для явных временных отказов, отдельный unknown для неоднозначного результата.

Приложение, Apple Developer и privacy

Проверка ведущим 12 ноября: после входа пользователя в Apple Developer подтверждено: у App ID NewsFeed уже включена Push Notifications capability; существующий APNs provider key имеет scope всех topics команды и sandbox/production. Соответствующий локальный приватный файл найден и прошёл криптографическую проверку без вывода содержимого. Текущий development provisioning profile разрешает APNs и действителен до 11 ноября 2027, но подписанная установленная сборка ещё не содержит APNs entitlement. Credentials на сервер пока не перенесены; canary и доставка ещё не проверены.

В текущем NewsFeed NewsFeed.entitlements пустой, APNs delegate/registration отсутствуют. В backend исходниках и News DB push/device infrastructure не найдена. В Apple Developer наличие ключа не проверено; пользователь ответил: «Не знаю — проверить при настройке».

Сначала проверить App ID capability, provisioning и существующий подходящий APNs provider key/место его безопасного хранения. App Store Connect API key не считать APNs-ключом. Новые credentials не помещать в Git, приложение, HTML или переписку. Если ключа/доступа нет, явно зафиксировать зависимость; код с fake APNs и этап A могут продолжаться, реальные пуши до настройки не объявляются готовыми.

iOS изменения: UIKit application delegate через SwiftUI adaptor, UserNotifications delegate, регистрация/обновление token, защищённый installation client и Keychain capability, Settings состояния, маршрутизация точного выпуска в ContentView и локализации en/ru/sr/sr-Latn. Включить Push Notifications capability и корректное signing entitlement, а не добавлять случайную строку environment.
