Ожидание экстрактора вместо отложенных статей

Редакция 1 · 23 октября 2026 · In progress. Редакция 1 одобрена пользователем: реализация на Луне, PR/review и выкат только приложения. Браузер, extractor и Readeck не изменяются.

Причина и результат

На production после PR #15 Python запускает 3 обработки статей, Go принимает 1 запрос. В go/service/server.go занятый общий слот немедленно даёт 429 busy до чтения тела. Python client не ждёт; сохранение попыток уже исправлено PR #14, но processing_outcome.py назначает обычную паузу 1800 с. Первый плановый цикл 13:08:46 Europe/Belgrade дал три retry_wait с attempts=0. Локальный TestAdmissionAndDrain подтверждает отказ при занятом слоте.

Цель: три параллельные обработки по очереди получают Go-экстракцию в том же проходе; AI для уже извлечённых статей продолжает выполняться параллельно. Go/browser concurrency и ограничения памяти сохраняются.

Схема и границы

Добавить общий асинхронный admission helper в Python перед HTTP-вызовами частного Go-сервиса. Один активный запрос на endpoint в пределах event loop; максимум 8 ожидающих, ожидание не дольше 120 с и не за пределами существующего outer deadline. Состояние изолировано между endpoint/event loop, без секретов в ключах и без неограниченного реестра. Никаких фоновых задач и дополнительных браузерных вкладок для ожидания.

Article, Telegram, Page Monitor и SourceManager используют один helper. Permit приобретается до сериализации большого тела, создания HTTP session и запуска HTTP timeout; освобождается после закрытия ответа/session, при исключении и отмене. На одну операцию ровно один permit: не держать его вокруг нормализации, selector AI, Telegram enrichment, DB или Gemini. Вложенный повторный acquire запрещён.

Текущие outer deadlines остаются конечными и не увеличиваются глобально. Истечение времени именно в очереди классифицируется как local busy без расходования попытки; реальный HTTP/extraction timeout сохраняет прежнюю классификацию. Ручная отмена распространяется наружу, не превращается в успех или retry. При нехватке времени запрос к Go не отправляется.

На явный 429 busy до запуска обработки допускается ожидание Retry-After и повтор только внутри исходного ограниченного окна, с максимумом 8 повторов; permit не удерживается во время паузы. После transport timeout/неизвестного результата повторов нет. Реальную перегрузку после исчерпания окна отложить на короткий срок 60 с с сохранением attempts, а не на обычные 30 минут. Это earliest retry, фактический запуск зависит от существующего scheduler; сам scheduler здесь не переделывается. Non-busy retries и exhausted остаются прежними.

Это координация одного Python-процесса, который сейчас запускает один uvicorn worker. Межпроцессной очереди нет; 429 другого клиента обрабатывается ограниченным повтором. Go остаётся защитой от реальной перегрузки. Схема БД, wire JSON v1, auth и Go worker не меняются.

Риски, восстановление и approval gate

Риски: удержание permit через нормализацию/AI, отмена ожидания, смешанные сроки, несколько loops и отказ внешнего клиента. Их закрывают перечисленные проверки и общий helper. При неизбежной недоступности сервис всё равно возвращает finite retryable outcome; бесконечного ожидания нет.

Rollback: прежний immutable app image с сохранённым Compose, без DB restore/удаления статей; при неудачном старте сначала диагностика и отдельное согласование отката. Browser/Readeck/worker не трогать. После фактической приёмки обновить этот HTML и Personal Memory; задачи в memory не записывать.
