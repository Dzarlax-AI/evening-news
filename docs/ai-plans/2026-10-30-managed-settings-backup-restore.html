Восстановить настроенный News, а не архив новостей

30 октября 2026 · Одобрен · реализация и изолированная проверка · Managed + native Cloak + внешняя PostgreSQL

Основной результат — компактный зашифрованный бэкап настроек и проверенная операторская инструкция. После потери установки восстанавливаются источники, правила, доступ и расписания; статьи собираются заново. Полная история статей и доставок не является целью. Новый backup-сервис, контейнер, публичный endpoint и универсальный restore CLI не нужны.

Подтверждённая исходная точка

Код News работает на Go. Managed credentials хранятся в integration_credentials в зашифрованном виде; расшифровка зависит от NEWS_CREDENTIAL_KEY, key ID и installation ID из приватного domain manifest и installation_state. Приватные runtime.json существуют отдельно для web/domain/background/extractor/egress. Adopted setup имеет adoption-committed.json; нельзя предполагать наличие installation.json свежего installer-профиля.

go-domain/cmd/newsctl/recovery.go отказывает native/external backup/restore. Его фиксированный список файлов в recovery/archive.go не содержит egress и предназначен для другого профиля. Не снимать эти запреты ради инструкции. Текущий веб-экспорт содержит application data и encrypted credentials, исключает managed_admin/setup_tokens и не включает весь комплект приватного состояния; он не является восстановлением managed-установки. /admin/backup всё ещё предлагает restore и автосохранение, хотя worker-mode операции ограничены. План основан на исходниках и последнем rollout evidence, без нового обращения к production.

Что не сохраняем в основном бэкапе

articles и их содержимое, editorial editions/daily summaries, AI usage/stats, очереди jobs, execution/ingestion/processing receipts, worker generation/heartbeat, scheduler occurrences, delivery attempts, logs, caches, browser profile/cookies, контейнерные writable layers и общий PostgreSQL volume. По запросу владельца отдельный полный архив возможен позже, но не смешивается с этим форматом.

Повторный сбор не гарантирует прежнюю историю: RSS выдаёт ограниченное окно, публикации могут исчезнуть. Принятая цель — продолжить работу с настроенными источниками. Отправленные Telegram-сообщения никуда не исчезают, а локальный delivery ledger в этом формате не восстанавливается. Поэтому никакой автоматической повторной отправки или replay после restore.

Операторский комплект

Предлагаемый отдельный формат settings-recovery-v1, не выдаваемый за существующий newsctl recovery bundle:

news-settings-<UTC>.tar.age
  manifest.json        # profile, versions, installation ID, sizes, checksums
  settings/            # allowlisted configuration records, no article data
  schedules.json       # definitions, no live dispatch state
  private/             # current keys, administrator metadata, role files
  deployment/          # pinned Compose + reviewed role/target mappings
  RESTORE.md           # matching operator procedure/version

SQL/JSON — только явные конфигурационные записи; не дамп двух целых баз. Выбор SQL/JSON по конкретной таблице зафиксировать при оформлении инструкции, сохранить типы JSON и ID без преобразования строк через shell. Полная схема создаётся из миграций соответствующей версии приложения, а не восстанавливается из произвольного cluster dump.

Шифровать стандартным age в отдельный новый файл с отказом от overwrite. Age уже используется библиотекой в проекте; для операторской инструкции CLI age — отдельное prerequisite, его наличие и версию проверяет оператор. Рекомендуется recipient encryption: на сервере достаточно публичного recipient, приватный recovery key хранится отдельно от VPS и архива. Никакой новой самописной криптографии. Manifest/checksums тоже находятся внутри зашифрованного архива; проверка archive SHA не заменяет decrypt/restore test. Открытый staging только в закрытом временном каталоге/зашифрованном томе, без вывода содержимого и с обязательным cleanup; удаление файла не обещает forensic erasure на SSD.

Backup: минимальное окно обслуживания

  1. Preflight: распознать adopted/native/external профиль; определить активные News DB/schema, scheduler target, роль каждого volume и exact image pins. Проверить свободное место и recipient. Это метаданные, не env/log dump.
  2. Сохранить исходные dispatch/operational states. CAS pause scheduler, остановить только web для исключения ручных записей, дождаться завершения принятых работ и in-flight delivery. При delivery_unknown не объявлять операцию выполненной и не повторять доставку.
  3. Штатно остановить только background после drain и domain после завершения callbacks. Подтвердить отсутствие активных News writers/leases. PostgreSQL, extractor/egress, Cloak, Readeck и proxy не останавливать.
  4. Прочитать allowlisted конфигурацию News и определения расписаний в read-only snapshots, скопировать соответствующие текущие private state и инфраструктурные mappings. Разные БД не имеют общей pg_dump-транзакции: согласованность обеспечивается отсутствием writers, а не обещанием атомарного cross-DB snapshot.
  5. Собрать manifest, зашифровать, проверить целостность и наличие всех обязательных entries; опубликовать только завершённый новый архив. Не сохранять полный DB dump и не экспортировать роли всего shared cluster.
  6. Запустить только ранее работавшие News processes, проверить health и прежний admin path. Вернуть исходный dispatch state с актуальным revision; если он был paused, оставить paused. При ошибке backup сообщить отказ и безопасно восстановить исходную доступность по записанному состоянию, не оставлять web выключенным из-за неудачного архива.

Длительность окна и размер архива измеряются на fixture, обещаний секунд заранее нет. Пропуск шага quiesce ради online export в первый вариант не входит.

Restore: новая чистая установка без истории

  1. Отдельно одобрить целевое окружение. Проверить recipient key, archive version/profile/size limits и exact pinned application version. Полностью проверить authenticated decryption, затем manifest и entry checksums. Отказать неизвестным файлам, symlinks, path traversal, повреждению и неполному набору ключей до target mutation. Не распаковывать непроверенный tar прямо в /root/news или volumes.
  2. Создать только новые пустые News и scheduler targets с нужной схемой. На shared PostgreSQL не использовать restore --clean/--create для существующего aistack, не трогать соседние schemas. Роли/grants/search_path создаются/проверяются только для News по точной матрице; несовпадение существующего пароля/роли — остановка, не автоматический ALTER чужой identity.
  3. Создать схему миграциями сохранённой версии. Импортировать конфигурационный allowlist транзакционно в установленном FK-порядке, согласовать штатные seed rows без глобального TRUNCATE CASCADE, восстановить ID/sequences. Архив не содержит schema DDL для всего cluster. Режим restore только в пустую конфигурацию; конфликты или повторный запуск не должны дать наполовину активированную установку.
  4. Восстановить согласованную installation identity, admin state, encrypted credentials и соответствующие key material/role files. Никакого повторного adopt с генерацией нового encryption key. Операторская карта меняет только явно одобренные endpoint/database/network параметры; ключи не попадают в args, shell history или stdout.
  5. Создать новые пустые runtime queues, delivery ledger, worker leases и scheduler outbox. Импортировать definitions, пересчитать future due instants. Держать scheduler paused, delivery выключенной и не запускать background автоматически до принятия.
  6. Проверить только metadata и локальную расшифровку: credentials доступны внутри domain, секретные значения не выводятся и провайдерам не отправляются. Проверить полноценный admin/API путь, источники/категории/расписания, ограничения ролей и пустоту исторических таблиц.
  7. Для запуска на том же VPS использовать существующий Cloak/egress без рестартов. На другом хосте требуется отдельно предоставленный browser endpoint с разрешёнными credentials/networks: News archive не восстанавливает shared browser или Readeck. В изолированной репетиции только synthetic CDP/egress либо HTTP-only fixture — никаких подключений к production browser.
  8. Владелец разрешает первый сбор, проверяет результат, затем отдельно включает доставку и возобновляет расписания с будущими due instants. Исторические выпуски не отправляются. При отказе остаётся исходная установка; недостоверное target-состояние не публикуется.

UI: инструкция вместо панели восстановления

Рекомендация: для managed-профиля /admin/backup становится простой справочной страницей с назначением settings backup и ссылкой на операторскую документацию. Без upload/restore, мнимого расписания автобэкапа и кнопки «полная копия». В мастере первоначального запуска backup настраивать не требуется.

На первом этапе не удалять API/job contracts: существующий application-data export остаётся явно частичным совместимым механизмом, не новым settings bundle. Worker-mode отказы restore/upload/cleanup сохраняются. Не открывать новый публичный recovery API. Удаление старых endpoints/jobs потребует отдельной проверки совместимости и не входит в этот план. Ручной development-профиль не ломать ради managed справки.

Критерии готовности

  • Настройки 8 synthetic источников, категории/mappings, модели, operational settings, channel IDs, admin state и credential metadata восстановлены. Domain может локально расшифровать dummy keys без запросов провайдерам.
  • Articles/editions/jobs/receipts/occurrences пусты. Source cursor/hash-state сброшен; HTTP-only synthetic сбор начинает собирать заново.
  • Scheduler paused, delivery disabled, background не отправляет и не обрабатывает ничего сам при restore. Пропущенные schedules не replay.
  • Corrupt archive, неверный key, missing egress/domain key, другой installation ID, конфликт target и неизвестная schema version отклоняются до activation. Чужая schema и контрольный сосед в fixture сохраняются.
  • Повтор/сбой импорта не приводит к частично доступной установке. Отмена backup или отсутствие места не оставляет исходный web/dispatch остановленным.
  • Проверены PG16 и PG17, применение exact version images и переносимость логических данных между ARM64 и Linux amd64; не копировать PG data directory между архитектурами.
  • Полный тест повторён по инструкции на новом disposable target, затем контейнеры/volumes/открытый staging удалены по точному test prefix. В evidence только versions/counts/hashes/status, без ключей, SQL-текстов и статей.

Хранение, откат и границы

Начальное предложение: один текущий проверенный архив и один предыдущий на backup target; одна зашифрованная off-host копия текущего архива. Destination и recipient выбирает оператор; автоматически ничего не публикуется и не удаляется. RPO — момент последней успешной копии настроек; RTO измеряется репетицией. Периодический backup/retention automation в этот этап не входит.

Сейчас создаётся только этот план. Никаких новых бэкапов/дампов, установок age, live calls, рестартов, смены DB-ролей или лимитов. Браузер и Readeck остаются нетронутыми. Отмена будущей реализации — убрать только собственный diff, сохранив все локальные документы и рабочие настройки. Реальный restore никогда не тестируется поверх единственной production БД.

Фактическая реализация и проверка

Добавлены English operator guide, три psql-рецепта с явным allowlist и managed help page. Архив — плоский набор из 12 файлов settings-recovery-v1, зашифрованный штатным age CLI. Это инструкция и операторские assets; нового runtime CLI, endpoint или backup-сервиса нет. Frozen OpenAPI сохранён; актуальное поведение описано в route ledger.

Изолированные PostgreSQL 16/17: реальные миграции, восемь synthetic источников, категории, ручные extraction rules, AI/provider settings, dummy credentials; импорт в отдельную пустую news_restore_* БД. Проверены typed operational settings, локальная расшифровка, reset cursor/history/queues, sequences и неизменность sentinel соседней схемы. Неполный operational set дополняется согласованным background manifest и штатными defaults; некорректный set откатывается.

Реальные tar/age CLI проверены на macOS ARM64 и Linux ARM64, вместе с отказами при повреждении, другом ключе, unsafe tar и checksum mismatch. Scheduler definitions восстановлены через существующий API: глобально paused, future due, пустой outbox, повтор конфликтует. Добавлен такой же gate в CI matrix PG16/17 на Linux amd64.

Границы evidence: это синтетическая репетиция SQL/ключей/расписаний, не полный поднятый клон production с HTTPS/Access, CDP и provider credentials. Остановка/возврат исходных процессов, grants/volume rebinding и реальный admin path остаются операторскими acceptance шагами инструкции. Ни реальный production backup, ни восстановление поверх live, ни первый сбор/доставка не выполнялись. Новый Linux amd64 gate требует зелёного CI до merge. Временные fixture-контейнеры и test tools удаляются после проверки.

Review PR #50

По независимому Codex review исправлены три замечания: raw SQL diagnostics больше не попадают в test logs; для ручных extraction rules сохраняются success/failure counters, необходимые существующему eligibility filter, и проверяется реальный learning.Context; расписания при restore создаются disabled, а originally enabled ресурсы включаются с новым future due непосредственно при activation. Проверка имитирует задержку acceptance на 48 часов и отсутствие replay. Также добавлены отказ target с остаточной историей и roundtrip удалённого ключа с null envelope. По CodeRabbit добавлены обязательный script exit trap с заранее определённым original-state recovery callback и очисткой staging/partial, а также отдельные ссылки в UI для HTTP-only и adopted/Cloak. Fault injection проверяет exit, отказ age и конфликт публикации: private staging удаляется, callback вызывается, существующий архив сохраняется. CI и повторный review относятся к актуальному head PR, не к предыдущему коммиту.
