Самостоятельный Go scheduler

23 октября 2026 · Редакция 2 · Пользователь одобрил редакцию 2: «Давай да, аппрув». Реализация на Луне начата; PR/review в scope, production не меняется.

1. Решение и границы

Scheduler — отдельный сервис, binary/container и image, с независимым выкатом, собственной схемой PostgreSQL и внутренним versioned API. Он хранит расписания, рассчитывает occurrences и надёжно передаёт команды исполнителям. Он не импортирует модели Evening News, не читает articles/background_jobs/schedule_settings и не знает Gemini, Telegram или браузер.

Python-worker остаётся исполнителем доменных операций. AI обсуждаем отдельно. Collector/extractor, browser concurrency, Readeck, доставка и правила обработки статей не меняются. Этот этап переносит расписание и dispatch, не весь Python orchestrator. Производительность обработки статей и экономия памяти не обещаются.

Почему меняем редакцию 1: отдельный процесс с прямой записью в таблицы News имел бы независимый запуск, но сохранял бы жёсткую зависимость от схемы и логики News. Для переиспользования выбран сервис со своим хранилищем и небольшим контрактом доставки команд. Новый broker не нужен.

2. Границы данных и поток

News Web/Admin → Scheduler API → scheduler schedules + occurrences/outbox
Scheduler dispatcher → внутренний News adapter → существующая news background_jobs
Python-worker → Go collector/extractor + AI + доставка
  • Scheduler: единственный владелец конфигурации расписаний, revision, next_due и outbox. Собственная PostgreSQL schema/role; допустим тот же PostgreSQL server, но без прав на News и соседние схемы. Собственные additive migrations.
  • News: владелец jobs, статей и результатов исполнения. Только News adapter пишет в очередь News; scheduler не использует её advisory lock, worker lease, ORM или queue SQL.
  • Web: сохраняет прежние пользовательские маршруты расписания как facade; в service mode конфигурация читается и изменяется через Scheduler API. Не вести две изменяемые копии schedule config.
  • Scheduler различает «команда принята исполнителем» и «работа выполнена». Его accepted не отображается как success обработки. News показывает результат своего job; в первом этапе обратный execution callback в scheduler не нужен.

Исходная база: PR #18 head c4c64fe / merge 2782c4a. Сейчас Python DurableBackgroundWorker._enqueue_due_schedules ставит задания и обновляет schedule_settings, затем worker сам выполняет их. Существующая очередь: до 32 ожидающих jobs, payload/result до 4096 bytes. В checkout сохранены посторонние local changes и результаты предыдущего выката в документации; их не сбрасывать.

3. Общий контракт scheduler

Новый API /v1/schedules: list/get, create, update, enable/disable и delete с optimistic revision. Клиент задаёт стабильный schedule_key, календарь, target alias, operation и компактный JSON payload. CRUD idempotent, конфликт revision — 409; неизвестная timezone/некорректный календарь — 422. Опубликованная OpenAPI и JSON fixtures — контракт сервиса, не Python модели News.

Календарь: daily/weekly/hourly/interval, timezone IANA, weekdays 1–7, UTC для хранения, injectable clock. Пропущенные occurrences не вызывают catch-up storm: после простоя одна pending occurrence и переход к следующему будущему времени. На переносе сохранить реально поддерживаемое поведение calculate_next_run; DST особенности зафиксировать golden fixtures до runtime-кода, не менять их молча.

Команда доставки v1: version, occurrence_id, schedule_key, schedule_revision, scheduled_for, operation, payload. occurrence_id — стабильный UUID, scheduled_for — UTC RFC3339, revision — целое. Повтор HTTP сохраняет идентичный envelope и idempotency key. Числовые IDs статей, валидность operation и бизнес-ограничения проверяет News adapter; generic scheduler только ограничивает размер/структуру. Никаких URL, prompts или credentials в логах.

Targets — статическая серверная allowlist alias → endpoint + credential. Клиент расписания не может задавать произвольные URL/headers: исключить SSRF. Никаких плагинов или выполнения shell. Переиспользование доказывается вторым fake consumer, который понимает другой operation и не имеет News schema.

4. Надёжная доставка и адаптер News

  • Scheduler атомарно записывает occurrence + outbox и advance next_due в своей БД. Сетевой HTTP только после commit. Неуспешная доставка не теряется, даже если next_due уже изменён: она остаётся в outbox.
  • Несколько dispatcher используют короткие DB claims, bounded HTTP deadline и leases. Не держать транзакцию во время сети. Устаревший claim не может записать ack после нового владельца; одинаковый occurrence при retry всегда сохраняет ID.
  • 2xx с валидным receipt означает durable acceptance. 429/503/network/timeout повторяются с bounded exponential backoff+jitter, учитывается Retry-After; 401/403/невалидный envelope переводятся в видимую blocked state, не бесконечный быстрый retry. Один неисправный target не блокирует остальные. Задать лимиты outbox/in-flight и retention только для acked entries; pending не удалять по TTL.
  • News adapter — новый внутренний маршрут POST /api/v1/internal/scheduled-jobs, со scoped service token и проверкой версии/размера/kind/payload. Не использовать admin password, не доверять identity headers от scheduler. Token остаётся server config, никогда не в расписании. Direct internal request проходит service auth; публичный доступ проверяется отдельно, обход существующего Cloudflare/admin auth недопустим.
  • Adapter проверяет worker availability и queue cap, ставит job транзакционно через существующий enqueue API. Ключ scheduler:v1:{occurrence_id}; duplicate идентичной команды возвращает тот же job receipt, conflicting content — 409. Проверка receipt должна исключать подтверждение незафиксированной транзакции. Потеря HTTP-ответа после commit не порождает второй job.
  • Добавить source metadata для News job (schedule_key/revision/occurrence_id) отдельной additive migration и validate contract. Python-worker продолжает claims, fencing, article recovery и delivery_unknown. В service mode его completion не пишет конфигурацию старого schedule_settings. Admin UI объединяет scheduler config с последним соответствующим News job result, не выдавая delivery accepted за execution succeeded.
  • Для новых job metadata сохранить существующие operational failure/recovery alerts Python-worker. Scheduler не создаёт вторую Telegram доставку. Его dispatch health/errors доступны через status, агрегированные logs и метрики.

5. Миграция, конфигурация и откат

Новый SCHEDULE_DISPATCH_MODE=python|service, default python для совместимости; не является конечной целью постоянно поддерживать два scheduler. В service mode Python отключает только schedule loop; manual jobs и consumer работают. Web facade обращается к scheduler. Scheduler имеет собственный enable switch; выключение планирования не удаляет outbox. Общий emergency pause должен останавливать новые occurrences и отправку pending, сохраняя данные.

Однократный import/export bridge в News, без прямого доступа Go к News DB. После drain активных scheduled jobs экспортировать календарь, enabled и исходный next_run; stable schedule_key news:{legacy_id}. Import idempotent. Сначала проверить offline snapshot, затем при отдельно одобренном выкате отключить Python dispatch и переключить facade/Go. Локальные фикстуры доказывают сохранность первого due occurrence и отсутствие двойного запуска. Legacy таблица остаётся архивом, а не вторым source of truth.

Откат: остановить новые occurrences и dispatch, инвентаризировать pending/acked occurrences и News jobs; экспортировать актуальные Go расписания в News через bridge с сохранением next_due и execution state, затем включить Python dispatcher. Не возвращать старую конфигурацию вслепую. Не удалять очередь, outbox или article stages. Браузер, Go extractor, egress и Readeck не рестартуются.

Service auth, import и права на отдельную schema — изменения контрактов; нужен review до merge. Реальные токены/DDL/production переключения в текущий плановый этап не входят.

7. Проверки

  • Calendar golden parity: Belgrade/UTC, DST, все schedule types, weekdays, invalid config, disable/enable, missed occurrence, edits/revisions.
  • Настоящий изолированный PostgreSQL с разными roles/schema: scheduler не может читать/писать News; Python не пишет scheduler tables. Один повтор occurrence даёт один News job. API compatibility и UI показывают исполнение, а не только ack.
  • Crash до outbox commit, до/после HTTP, после News commit до receipt; lost DB/HTTP, duplicate dispatchers, stale lease/ack, backpressure32, invalid auth/target/payload и malformed receipt; нет потери pending и duplicate jobs.
  • Import → первый due occurrence → success, restart каждого процесса, admin edit race и проверенный rollback с pending/acked jobs. Существующие article attempts/stages, busy-refund и delivery_unknown не меняются.
  • Docker internal-only: scheduler + web adapter + Python worker + PostgreSQL + fake sources/Gemini/Telegram + второй generic fake consumer. Никаких реальных сайтов, AI, Telegram, browser или production DB. Fixture acceptance с actual Go binary, а не mock scheduler.
  • Новые Go unit/race tests в go-scheduler/, Python suite с loopback TEST_DATABASE_URL и выключенными внешними providers, Linux amd64 build и ARM64 build. Конкретные CI commands оформлены в отдельном workflow; локальные результаты указаны ниже.
  • Измерить idle/active CPU, memory каждого процесса и сумму; записать результат без обещаний ускорения заранее. Healthcheck доказывает DB readiness и свежесть dispatcher, а не только открытый порт.
