Отдельный Python worker для фоновой обработки

23 октября 2026 · Редакция 2 · Направление выбрано пользователем: сначала отделить worker, сохранить Python для AI. План одобрен, реализация на Luna проверена локально и на Docker-стенде. PR #18 проходит внешнее review; исправления проверены локально и на точном Docker image; итоговые CI/review отслеживаются в PR #18. Актуальная сводка и ограничения — в разделе 9.

1. Цель и границы

Разделить жизненный цикл веб-приложения и фоновой обработки. Web обслуживает UI/API, CRUD и постановку заданий; отдельный Python worker выполняет расписание, сбор через Go, обработку статей, AI, сводки и существующую доставку. Worker запускается отдельным entrypoint из того же Python image. Go collector/extractor сохраняет свой контракт и лимит двух браузерных операций. PostgreSQL остаётся общим; это первый разрез по исполнению, с явной общей схемой данных.

В этап входят durable очередь заданий в существующем PostgreSQL, координация процессов, worker runtime, адаптация API/админки/CLI и изолированные проверки. Перенос scheduler/AI на Go, отдельный Delivery-сервис, новый брокер, изменение категорий/AI-промптов/правил извлечения и расширение браузерного параллелизма сюда не входят.

Production, browser, egress, Readeck и реальные отправки не меняются. Выкат потребует отдельного решения после PR/review и изолированной приёмки. Снижение общей памяти не обещается: два Python-процесса имеют отдельные базовые расходы; измеряем web, worker и их сумму.

2. Что установлено по коду

  • news_aggregator/main.py запускает scheduler, process monitor и browser-related cleanup внутри FastAPI lifespan.
  • services/scheduler.py создаёт NewsOrchestrator, планирует и выполняет задачи в этом же процессе.
  • orchestrator.py последовательно выполняет сбор → сохранение → AI → сохранение результатов. Защита reserve_processing_cycle() основана на process-local global token.
  • services/database_queue.py содержит локальные asyncio-semaphores. Это менеджер DB-доступа, а не межпроцессная очередь заданий.
  • api/processing_router.py запускает FastAPI BackgroundTasks; articles_router.py, summaries_router.py, telegram_router.py выполняют тяжёлую работу прямо в HTTP-запросах. stats_router.py создаёт orchestrator для статистики; CLI и StatsCollector также вызывают его напрямую.
  • Текущая миграционная точка входа находится в web startup. Worker должен ждать совместимую схему, а не конкурировать с web за миграцию.

3. Предлагаемая схема и режимы

Admin / API ── enqueue / job status ── PostgreSQL jobs
                                          │
Python worker: scheduler ── enqueue ────────┘
              consumer → existing Python orchestrator
                       → private Go collector / extractor → Cloak / egress
                       → Gemini → PostgreSQL results
                       → existing digest delivery

Public web → PostgreSQL read models / persisted worker status

Новый явный режим конфигурации BACKGROUND_EXECUTION_MODE=embedded|worker — предлагаемый контракт. Default embedded сохраняет нынешнее поведение для существующих установок. В режиме worker web не запускает scheduler/orchestrator, browser monitor и browser cleanup; отсутствие worker не включает скрытый embedded fallback. Команды остаются в durable очереди, UI показывает отсутствие worker heartbeat. Worker не поднимает публичный HTTP-порт.

Предлагаемый entrypoint: python -m news_aggregator.worker. Он инициализирует DB access, проверяет миграцию, получает singleton ownership, запускает scheduler/consumer и необходимые фоновые наблюдатели. Python AI, обогащение Telegram и selector learning переиспользуются. Один worker выполняет одно pipeline-задание за раз; Go по-прежнему может обрабатывать до пяти source jobs и двух renders. Масштабирование AI-workers не входит в этот этап.

4. Очередь, владение и восстановление

Новая additive migration создаёт background_jobs и persisted worker heartbeat/ownership. В job храним UUID, конечный набор видов задач, ограниченный JSON payload с ID/флагами, idempotency key, status, timestamps, owner generation и ограниченный результат/error code. Текст статей, секреты и произвольные URL в job payload не копируем. Состояния: queued → running → succeeded|failed|interrupted|delivery_unknown. Сохраняем задания после сбоя; не выдаём enqueue за завершённую обработку.

Scheduler фиксирует due occurrence и enqueue в одной короткой транзакции; уникальный ключ schedule ID + due time исключает повторную постановку одного срабатывания. Manual enqueue поддерживает idempotency key и возвращает прежний job при повторе того же запроса. Глобальная граница конфликтующих pipeline-операций сохраняется в БД; process-local token остаётся только локальной дополнительной защитой. Синхронные DB-only действия вроде selected retry также проверяют общую границу.

Один активный worker подтверждается PostgreSQL advisory lock на выделенном соединении. Потеря владения останавливает приём и отменяет текущую работу. Owner generation проверяется в транзакции сохранения результата: потерявший владение процесс не должен записывать поздний результат после восстановления задания другим worker. AI и сеть остаются вне DB write transactions. Heartbeat живёт отдельно от продолжительности отдельного AI-запроса.

На shutdown worker прекращает claim, даёт ограниченное время на drain, затем сохраняет interrupted state. Восстановление processing-задач использует существующие persisted article stages/retry state, не обнуляет попытки и готовые результаты. Падение web не отменяет уже принятое задание. Повторный worker не создаёт второй scheduler и второй обработчик.

Внешние отправки имеют отдельную границу: если процесс упал после возможной отправки, но до фиксации результата, job становится delivery_unknown и автоматически не отправляется заново. Exactly-once отправка Telegram не обещается. Для нового повтора требуется явное действие пользователя. Этот этап не превращается в переписывание всей доставки/outbox.

При реализации зафиксировать и протестировать ограничение queued backlog, payload/result размеров и срок хранения завершённых job. Предлагаемый стартовый предел очереди — 32 ожидающих задания; при переполнении возвращать retryable queue_full без потери уже принятых работ. Никаких неограниченных in-memory goroutines или списков результатов.

Обновить first-party UI и документацию; embedded-режим сохраняет совместимость. Polling прекращается на terminal status, ошибке авторизации или уходе со страницы.

7. Проверки и критерии приёмки

  • Новые PostgreSQL tests (proposed tests/test_background_jobs_postgres.py): конкурентные enqueue, два workers, повтор scheduled due occurrence, backlog limit, crash/reclaim, старый owner не фиксирует результат. SQLite не считается доказательством этих гарантий.
  • Runtime tests (proposed tests/test_background_worker.py): SIGTERM/drain, DB disconnect, отсутствие миграции, worker down, web restart, heartbeat stale. Ни один queued job не исчезает; errors не превращаются в success.
  • API/UI tests: 202 → polling → реальный terminal result, повтор нажатия, недоступный worker, queue full, права доступа. В worker-режиме web не создаёт orchestrator и не делает AI/CDP/digest вызовы; manual и scheduled задания выполняет один consumer.
  • Обработка статей сохраняет ready stages, bounded attempts и refunds при native busy; interrupted delivery не повторяется автоматически. Изолированные fake receivers считают внешние вызовы; реальные invites/notifications/sends отключены.
  • Планируемые команды: .venv/bin/python -m pytest tests -q с изолированным PostgreSQL TEST_DATABASE_URL; отдельные новые tests запускать повторно после lifecycle findings. Go не меняется; его race suite нужен при изменении Go wiring/контрактов, а не как формальность для Python-only patch.
  • Изолированный Compose: web+worker отдельные процессы, настоящая БД, реальный private Go wire contract на fixture origins; fake Gemini и fake delivery. Проверить restart каждого процесса, сохранение UI-статуса/результатов, source persistence и расписание.
  • Измерить idle и active memory web, worker и их сумму; короткий fixture-тест не выдавать за production sizing или обещание ускорения. Browser concurrency=2, существующие SSRF/event/resource ограничения и 256-MiB Go worker cap сохраняются.

Исторический baseline до одобрения: выполнены чтение исходников и исходные проверки. Результаты последующей реализации, PostgreSQL/JavaScript suite и Docker acceptance приведены в разделе 9; эта исходная проверка не заменяет итоговую приёмку.

8. Риски, восстановление и решения

Основные риски: скрытые обходные вызовы orchestrator, процессные caches/selector state, взаимные блокировки migration/job fencing и неоднозначность внешней отправки. Первым шагом исполнитель уточняет все persistent mounts и direct-commit paths на уровне транзакций; при невозможности обеспечить ownership в сохранении результата интеграция блокируется до исправления контракта.

Rollback разработки: вернуть execution mode embedded только после остановки/дренирования worker; pending jobs сначала инвентаризировать и явно перенести либо оставить для следующего worker. Нельзя одновременно включить два scheduler или молча забыть queued jobs. Additive таблицы и сохранённые статьи не удалять. Переключение в production и rollback не авторизованы этим этапом.

Открытых выборов, требующих второго продуктового решения до начала, нет: выбран Python worker, PostgreSQL queue, один активный pipeline worker и адаптация тяжёлых операций к job status. Точные heartbeat/drain/retention значения и bounded payload limits исполнитель фиксирует в config/documentation и проверяет тестами до review. Существенное расширение API, доставки или доступа к production возвращается отдельным изменением плана.
