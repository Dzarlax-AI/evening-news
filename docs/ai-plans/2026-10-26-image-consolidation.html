Меньше контейнеров, сохранённые компоненты

26 октября 2026 · Редакция 3 · Одобрено пользователем · Реализация в процессе

Цель: четыре продуктовых сервиса — web/API, background, private executor, extractor. Scheduler, worker, ingestion и processing работают компонентами одного background runtime. Один build graph выпускает минимальные образы web, background и executor; extractor и browser сохраняют самостоятельные сборки. Это план кода и изолированных проверок, без изменений production.

1. Целевая схема

Web/APIИнтерфейс, auth, управление, durable acceptance.
BackgroundОдин процесс: scheduler + queue worker + ingestion + processing. Раздельные внутренние модули, pools, contexts и admission limits.
Private executorСуществующие domain/AI/selector callbacks, summaries и delivery. Перенос этих обязанностей сейчас не делаем.
ExtractorПереиспользуемый API и самостоятельный image; browser отдельно.

В production Compose News сегодня 8 постоянных контейнеров. Цель будущего rollout — 5: три контейнера основного приложения, extractor и его защитный egress. Это четыре продуктовых сервиса плюс один инфраструктурный egress; общий браузер и PostgreSQL сюда не считаются. Миграции — временный one-shot, не постоянный контейнер.

Для основного приложения один Dockerfile и один Buildx Bake graph выпускают три минимальных runtime-images. «Одна сборка» здесь означает согласованный build graph и pipeline с общим cache, а не одинаковый image для всех процессов. Каждый target содержит только необходимые ему runtime-файлы; компиляторы и build tools остаются в build stages.

Полные имена находятся в ghcr.io/dzarlax-ai/. Release manifest связывает отдельные digests с одним source commit и target. Образы остаются отдельно адресуемыми: смена одной роли не требует перезапуска остальных, прежние совместимые digests можно сохранять. Тестировать нужно допустимую совместимость API; одинаковый commit не заменяет contract tests.

Общие build stages/cache и подходящие runtime base layers переиспользуются без принуждения всех targets к одинаковому base. Выбор runtime определяется необходимыми зависимостями, а не названием языка. Extractor и egress остаются на своём rss-extractor, browser image — отдельно. Не запускаем четыре демона под shell/supervisor внутри одного контейнера: background — один runtime с компонентами. Самостоятельные CLI и API boundaries сохраняют возможность повторного выделения. Архитектурные имена не привязаны к языку.

2. Основание и изменение редакции

База: 458a64de1e65b2350e49b85f46904a6ace849995, codex/docs-mermaid-20261026. Прочитаны main/config четырёх фоновых модулей, Dockerfile, Compose, workflows и fixture harness. Не затрагиваем существующие dirty/untracked планы и AGENTS.md.

Редакция1 объединяла только images и оставляла все процессы отдельными контейнерами. Пользователь уточнил, что контейнеров тоже слишком много, и сказал «давай» на пересмотр. Редакция2 сохраняла единый image и заменяла четыре фоновых контейнера одним. После проверки рекомендаций Docker/Microsoft пользователь прямо запросил минимальные образы из одной сборки: редакция3 сохраняет сокращение контейнеров, но заменяет универсальный runtime-image тремя final targets. Реализация предыдущих редакций не начиналась.

Текущие entrypoints самостоятельно читают environment, создают pools/contexts и местами вызывают log.Fatal/os.Exit. Их нельзя просто вызвать как goroutines. Worker при потере heartbeat возвращает ErrLeaseLost; текущий executor в example Compose ждёт ingestion/scheduler, а worker ждёт executor — после объединения это стало бы dependency cycle.

Локальный безопасный snapshot прошлого выката использован только для инвентаризации ресурсов и контейнеров; это не новый live audit VPS. Сборки и runtime-тесты этой редакции пока не запускались. Сверка подхода: Docker building best practices рекомендует минимальные runtime-зависимости, multi-stage и reusable stages; Microsoft service boundaries — связанность обязанностей и независимый deploy. Background — осознанное укрупнение приложения с внутренними модулями, а не четыре независимо выкатываемых микросервиса.

3. Runtime-контракты

  • Композиция. Новый go-background/ с cmd/news-background (новые пути) собирает четыре существующих модуля через узкие публичные bootstrap/runner-пакеты. Их internal реализации не копируются и не открываются целиком; самостоятельные cmd/* становятся тонкими обёртками тех же runners. Модули остаются раздельными; межмодульные зависимости собираются явными локальными replace, без зависимости от неопубликованной версии main.
  • HTTP boundaries. Сохраняем private scheduler API8080, ingestion8093 и processing8094 на одном background hostname. Тела запросов, tokens, receipts и DB fences прежние; Python executor по-прежнему вызывает эти API. Не переделываем одновременно все вызовы в in-process API. Web/executor URLs в Compose указывают на background с нужным портом; host ports не добавляются.
  • Конфигурация. В merged runtime отдельные новые DSN-поля WORKER_DATABASE_URL, INGESTION_DATABASE_URL, PROCESSING_DATABASE_URL; scheduler использует существующий SCHEDULER_DATABASE_URL. Не подставляем универсальную привилегированную DATABASE_URL. У каждого компонента свой typed config, pool и прежний DB user/connection limit. Standalone CLI продолжают читать свои прежние env-контракты. Никакого временного os.Setenv между goroutines.
  • Старт без циклов. News migrate завершён; extractor и executor могут стать ready без background. Executor зависит от migrate/extractor, но не ждёт healthy background. Background поднимает свои DB/listeners, затем worker с recovery handshake к готовому executor. Web не нужен для readiness background: scheduler сохраняет outbox и штатно повторяет dispatch, пока web запускается. Ревизии, enabled/paused и due instants расписаний не сбрасываются.
  • Lease/recovery. Singleton lease, owner/generation, attempt fencing, receipt replay, delivery_unknown и retry policy сохраняются. Обработанный ErrLeaseLost прекращает claims и прежнее исполнение, выполняет существующий release/drain и bounded-backoff повторный запуск только worker-компонента с новой lease/generation. Scheduler/listeners не перезапускаются. Не стартуем второй worker до завершения старого. Конфигурационные/неисправимые init errors не прячем бесконечным retry.
  • Готовность. Новый приватный health endpoint runtime на8095 и команда /news-background healthcheck. Liveness и readiness различаются; readiness показывает состояние каждого компонента и свежесть lease. Во время worker recovery общая readiness false, но живые компоненты продолжают работать. Нельзя показывать healthy только потому, что HTTP-порт открыт. Не добавляем health restart/watchdog, перезапускающий весь runtime при ожидаемом lease recovery.
  • Остановка. Сначала прекращаются новые schedule dispatch/claims, затем bounded drain активных jobs при ещё доступных ingestion/processing listeners. После этого закрываются handlers и раздельные pools. Общий SIGTERM приходит одному runtime; каждый компонент не регистрирует собственный signal handler. Drain deadline не должен разрешить stale write или повторную доставку.
  • Секреты и ресурсы. Web не получает фоновые/provider credentials; AI/provider secrets остаются executor. Background неизбежно видит credentials объединённых четырёх ролей: логические DB permissions сохраняются, но прежней межконтейнерной изоляции этих ролей больше нет. Read-only rootfs, непривилегированный user, cap_drop и no-new-privileges сохраняются. Не вводим общий write/heartbeat mutex. Concurrency/pool budgets компонентов остаются ограниченными; общий лимит будущего container не увеличивает суммарный прежний бюджет и выбирается по измерениям, отдельно перед rollout.

4. Объём изменений

  • go-worker/, go-scheduler/, go-ingestion/, go-processing/: публичные runner/config entrypoints, единый caller-owned context, возврат ошибок вместо process exit внутри переиспользуемого пути. Business logic, запросы/схемы, quality/retry policy и HTTP schemas не меняем.
  • go-background/ — новый composition root, lifecycle/readiness/recovery и интеграционные тесты. В docker/Dockerfile одна multi-stage схема с final targets web, background, executor; docker-bake.hcl — новый build graph трёх targets. Общие stages/cache, отдельные минимальные runtime-contents из раздела1. У каждого target свои explicit command/workdir/user/healthcheck; migrate переиспользует executor target. Не наследовать чужой ENTRYPOINT и не расширять права существующих непривилегированных ролей.
  • docker-compose.example.yml, docker-compose.dev.yml: background заменяет четыре старых service entries по умолчанию, env/URL/depends_on обновлены; web/background/executor выбирают соответствующий build target и image, migrate использует executor image. Один container не запускается из универсального superset-image. Не оставляем два параллельно работающих scheduler или worker. Переход не требует новой БД или нового хранилища очередей.
  • Core workflows docker-build-push.yml, web-api.yml, go-scheduler.yml, go-article-ingestion.yml, go-article-processing.yml: сохранить проверки модулей, объединить core assembly/full-pipeline/publication в один согласованный pipeline с Bake graph трёх targets. Остальные workflows не пересобирают/не публикуют core runtime-images независимо; прежние worker/scheduler/ingestion/processing publications выключаются. scripts/check_ghcr_tag_absent.py и его тесты защищают SHA tags всех трёх targets, allowlist включает новый rss-background и существующий rss-summarizer. Artifact release-images.json (новый) хранит source commit, platform, target→repository/digest/image ID; ни один общий digest для разных targets не предполагается. Только явно разрешённая ручная публикация reviewed main после gates. Extractor/browser release paths сохраняются.
  • scripts/run_go_web_fixture_gate.py, run_go_ingestion_fixture_gate.py, run_go_job_worker_fixture_gate.py, run_go_scheduler_fixture_gate.py и их базовые harness/tests: новый consolidated acceptance запускает ровно один background container; проверяется реальный PID/container ID, а не четыре alias/tag. Standalone component tests остаются для регрессий; лишние core Dockerfile удаляются после перевода всех активных ссылок на новый multi-target build graph. В full fixture реальные web/background/executor запускаются из соответствующих targets; один background container обслуживает все четыре роли. Проверка не должна ошибочно требовать одинаковый image ID разных targets.
  • README и docs/web-api-components.md: четыре продуктовых сервиса, отдельные внутренние компоненты, единый build graph и три минимальных core images, команды локального запуска. Не описывать background-модули как независимо выкатываемые сервисы. README — только английские technical guides, без описания Readeck.

Не меняем AI, summaries/delivery composition, reusable extractor, browser/CDP/egress/nft, Readeck, production Compose/env, volumes и DB permissions. Существующая причина heartbeat UPDATE timeouts не объявляется устранённой этим рефакторингом.

5. Выполнение на Луне, один PR

  1. Ведущий: свежая ветка от origin/main, отдельный baseline посторонних изменений. Зафиксировать новые config/runner контракты и dependency graph из раздела3. Создана feature-ветка; component runners реализованы на Луне, затем проверяются ведущим. Составной runtime и ingestion drain выполняются раздельными Luna-агентами с непересекающимися файлами после фиксации публичных runner-контрактов.
  2. Луна, шаг1: извлечь bootstrap четырёх модулей и добавить composition/lifecycle с regression tests. Один последовательный исполнитель gpt-6-luna, поскольку shared lifecycle/config тесно связаны. Старые CLI должны использовать тот же код и проходить прежние проверки.
  3. Промежуточная приёмка ведущим: реальный diff и PG16/17 тесты, старт/drain, loss-of-lease и отсутствие перезапуска scheduler/HTTP handlers. Только после этого Луна переводит multi-target сборку, Compose, harness и CI на готовый runtime.
  4. Луна, шаг2: три минимальных final targets из одного Bake graph, общий cache, Compose, единый consolidated fixture, CI guards и документация. Запрет на production, реальные сайты/AI/доставку, публикацию images и посторонние файлы. Возвратить actual changes, выполненные/неисполненные проверки и ограничения.
  5. Ведущий: независимое review фактических изменений, интеграционная приёмка единого состояния; конкретные исправления исполнителю. После двух неудачных коррекций — самостоятельный разбор и изменение brief. Один PR после локальных gates, затем CI/review. Merge, публикация и выкат отдельно; дополнительных approval на каждую обычную локальную команду не нужно.

6. Проверки — запланированы

  • Go race/vet всех затронутых модулей и нового background. Существующие PG integration tests на16/17; никакой shared/production DB. Все три runtime targets собираются/запускаются для ARM64 локально и Linux amd64 в CI. Предлагаемые новые команды: docker buildx bake -f docker-bake.hcl --set '*.platform=linux/arm64' --load локально и соответствующий linux/amd64 в CI; HCL/fixture tags добавляются при реализации, сейчас этих targets ещё нет.
  • Lifecycle: старт без web и временно недоступного executor без deadlock/busy-loop; readiness по компонентам. Executor после старта доступен; worker выполняет recovery handshake. Повторный bootstrap не дублирует loops/listeners.
  • Fault injection: PostgreSQL worker heartbeat UPDATE lock/timeout во время активной обработки. Старые writes/delivery fences отклоняются, worker восстанавливается с новой generation; PID runtime, scheduler state и другие listeners сохраняются. Не допускается whole-container restart storm. Это воспроизведение отказа и проверка восстановления, не доказательство устранения production-причины timeout.
  • SIGTERM при idle и активном job, bounded drain и повторный старт: существующие receipts/recovery/delivery_unknown правила, отсутствие дублей и stale commits. Длительный processing не блокирует heartbeat или scheduler tick.
  • Полный synthetic gate на одном background container: all8sources (4RSS/1Telegram/3PageMonitor), ingestion/processing succeeded receipts, сохранение статей, private callback и one-shot News migrate. Проверить фактическое число containers и processes, а также target/revision/image ID каждого; четыре отдельных background daemons в одном container не принимаются.
  • Реальный встроенный scheduler: API/readiness, pause/resume, точные revisions/due instants, duplicate occurrence accepted once, outbox retry при недоступном web, один schedule loop и одна worker lease. Fake scheduler из web gate этого не заменяет.
  • Compose manifest: три role-specific image references из одного release manifest; migrate и executor используют один executor target. Явные commands/workdirs/users, верные private URLs, role-specific DSNs, env boundaries, отсутствие host-публикации private ports и dependency cycle. Общие resource caps/пулы измеряются; не обещаем экономию RAM по одному снимку.
  • Affected Python executor/contract/fixture/registry-guard tests и локальный UI на fixture: reader/article/search, admin auth, source/category/settings/schedule/backup paths и безопасные fixture mutations с повторным чтением. Реальные провайдеры/сообщения запрещены.
  • CI guards: PR/обычные проверки не публикуют images, нет параллельных старых core publications; extractor/browser независимы. Все три targets проходят acceptance и имеют верный OCI source revision. Публикуются те же проверенные image contents; после gates не пересобираем silently новый непроверенный artifact. Ошибка любого target блокирует release manifest/publication этой согласованной версии; неудачная registry-публикация не разрешает перезаписать immutable tag.
  • Минимальность проверяется по фактическому содержимому/layers и inventory пакетов и файлов: в web/background нет Python/provider packages, compiler/build tools, domain source и PG backup CLI; у background нет web templates/static. В executor отсутствуют Go binaries/public admin templates, а необходимые backup/migration/provider файлы сохранены. Не удалять существующий файл только по имени: его необходимость проверяется actual operations/fixtures. Совпадение base layers само по себе не доказывает минимальность.
  • Сохранить image size по каждому target, общий shared/unique disk footprint, build/cache time, idle/load working set и startup time. Не складывать sizes образов с общими слоями как фактический disk usage. Отдельная совместимая замена одной роли в fixture не перезапускает другие; новые versions/API не объявлять совместимыми без проверки.

7. Риски и будущий rollout

Один процесс — общая память, GC, CPU quota и область panic/OOM для четырёх компонентов; это цена сокращения контейнеров. Потерю worker lease обрабатываем локально, но фатальное падение всего runtime всё равно затронет все четыре части. Поэтому merged load/recovery tests обязательны, а отдельные модули и standalone commands сохраняются для обратного выделения.

Будущий rollout затронет worker/scheduler/ingestion/processing и адреса private clients, поэтому прежнее разрешение обновить только web/executor его не покрывает. Перед выкатом нужен свежий baseline, pause/drain, проверка network aliases/ACL и новых IP без расширения доступа к CDP или origin egress. Если потребуются изменения browser/nft/egress, отдельно согласовать delta; молча их не включать.

Три targets связывает общий commit/build pipeline, но каждый имеет собственный digest и runtime-зависимости. Не навязываем одновременный restart всех ролей при смене одной; release manifest — проверяемый набор артефактов, а не гарантия отсутствия API coupling. Изменения зависимостей вне необходимой сборки не включаем. Не обещаем заранее меньший суммарный disk footprint или более короткую сборку.

Production на этом этапе не меняется, старые immutable images/config остаются для возврата к прежним четырём контейнерам. Не удаляем backups, volumes, образы или данные. Scheduler DB и News DB не объединяются; schema migrations не добавляются. Автоматического rollback/restart production нет. После будущего отдельного одобрения rollout — штатный8-source проход, память, heartbeat/рестарты и fingerprints browser/Readeck/PG/Traefik.
