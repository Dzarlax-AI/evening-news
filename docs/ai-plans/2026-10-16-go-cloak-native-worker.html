Go/Cloak worker: нативная загрузка и честное сравнение памяти

Следующий отдельный этап: batch shadow на реальных production URL — конкретный план подготовлен; live запуск пока не одобрен этим документом.

Долгосрочное продолжение: план миграции всего бэкенда на Go — отдельное предложение, не расширяющее одобренный scope этого worker.

16 октября 2026. Статус: план одобрен, реализация и изолированные проверки выполняются. Пользователь явно разрешил начало реализации и проверок, запретив изменения production. Экономия RAM пока не доказана.

1. Цель и проверенная исходная точка

Вынести управление браузерной экстракцией в Go, сохранив загрузку страницы самим CloakBrowser. Проверить, уменьшает ли это память всей системы относительно существующего Python, и установить, где остаётся расход: контроллер, CDP wrapper, renderer, другие процессы Chromium, кеши или незакрытые ресурсы.

Проверено в текущем рабочем дереве prototype/go-extraction-parity: Python использует nodriver и общий browser_pool.py с глобальным semaphore на одну вкладку, bounded operation/cleanup и собственными счетчиками. Ранние заметки о Playwright не используются как описание нынешней реализации. Текущий Go BrowserFetchPublic загружает ответы Go HTTP transport и выполняет CDP fulfill; это не нативный сетевой путь Cloak. Одобренный HTTP-only пилот пока оставляет браузер Python.

Предыдущий изолированный Cloak preflight: один повторный public-adapter тест прошел, пять из шести завершились ошибками CDP/discovery; OOM не установлен как причина. Новый worker обязан воспроизвести и исследовать эти случаи. Успех на обычном Chrome не принимается вместо Cloak.

Версию перепроверяем: прежний production-preflight записал Cloak 0.5.2, Chromium 146 и digest sha256:2c0d257802f54c4f86c9ccae336864baf63e118612732127cb96df35756a57a4; локальные docker-compose.cloak.yml и docker-compose.infra-cloak.yml содержат другой digest sha256:61dee1b490ee8f74b040bc02c3d5384c7f64420b87ccaa26a33f213d07df3f73. До тестов read-only сверка фактического image ID/digest, wrapper/browser version, args и ресурсных лимитов. Измерение не подменяет production-образ локальным.

3. Архитектура и сетевой контракт

Python caller → private extraction API → Go controller → CDP → выделенный Cloak
Cloak → ограниченный CONNECT gateway → публичный HTTPS origin
HTML/metadata → существующие Go extractors → bounded response → Python outcome/learning

CDP используется для navigate, ожидания, извлечения DOM и lifecycle. HTML, JS и XHR получает сам браузер; не выполнять Go HTTP download + Fetch.fulfillRequest для browser-задач. Не подменять UA/Client Hints/TLS, viewport или browser identity без явно записанного одинакового профиля теста. Критерий native path: контрольный origin видит запрос и TLS handshake браузера, включая JS/subresource/cookie/redirect цепочку; Go не получает origin-body для fulfill.

HTTPS egress gateway проверяет hostname/порт, запрещает private/link-local/metadata/mixed DNS, выбирает разрешенный IP и подключается к нему; далее передает TLS-байты без расшифровки и без MITM CA. Проверять каждый CONNECT, включая редиректы и подресурсы. HTTP/2 coalescing и уже открытые туннели входят в тесты origin/IP boundary. Gateway не равнозначен прежнему прямому browser egress: QUIC/HTTP3 и маршрут могут отличаться. Python с тем же gateway — обязательный контроль; идентичность всех антибот-сигналов не обещается.

Cloak размещается в отдельной сети без прямого Internet/LAN egress: gateway доступен для исходящего трафика, CDP — только для входящего controller connection. Страница не получает исходящий доступ к controller/CDP через «разрешенную control plane». Правила на уровне сети блокируют bypass proxy, UDP/QUIC/WebRTC, прямой DNS и private destinations, включая IPv6 и loopback attack surface. Отсутствие внешнего трафика проверяется отказными тестами/счетчиками; CDP URL-фильтр и CSP сами по себе недостаточны. Shared infra с доступом к БД для такого браузера не используется.

Первый native scope — публичные HTTPS article/web URL. Native HTTP, WebSocket origin traffic, downloads, внешние popup, учетные записи и долгоживущие production cookies первоначально не поддерживаются; возвращается явный unsupported/policy outcome. Никакого автоматического обхода через менее ограниченный Python transport. Gateway допускает методы внутри HTTPS-туннеля, необходимые обычной странице, но origin HTTP-level byte/status семантика не считается проверенной одним CONNECT.

Шифрованный туннель позволяет ограничить объем TLS-трафика и время, но не строго decoded response bytes. Отдельно ограничиваем DOM transfer и отслеживаем CDP encoded bytes; cgroup memory/CPU/pids — последний предел. При hard native decoded-body requirement текущий дизайн не проходит gate: нельзя выдавать приблизительный счетчик за точный лимит распаковки.

4. Жизненный цикл и ошибки

  1. Bounded admission, первоначально concurrency 1. Переполненная очередь дает busy; ожидание включено в общий caller budget. Идентификаторы endpoint, proxy и режима не принимаются из article payload.
  2. Discovery проверяется на закрепленном Cloak. Проверить, какие context/session операции действительно поддерживает wrapper и как он привязывает контексты к websocket. Не предполагать совместимость по одному /json/version.
  3. На job — owned disposable browser context, about:blank target и session; регистрировать ownership сразу после создания. Сначала подключить наблюдение и egress policy, затем navigate. Cookies/cache между разными jobs изолированы. Нужные cookies внутри одной цепочки не сбрасываются между navigation/JS запросами.
  4. Ожидание bounded: navigation + содержательная готовность DOM/нужного селектора, без бесконечного network-idle. Не вводить фиксированный долгий sleep. Для huge DOM сначала cheap size guard, затем bounded чтение; не выгружать дерево DOM до guard. Результат: исходный/final URL, main-document status, текст, metadata/media, provenance, timing и truncation.
  5. При success, timeout, cancellation или ошибке — отдельный короткий cleanup deadline, не отмененный caller context: stop loading, detach/close owned resources, dispose context. Квота не освобождается как «чистая», пока cleanup не подтвержден. Не затрагивать чужие targets и не отправлять global Browser.close.
  6. При потере websocket/generation — fail всех связанных jobs, не replay автоматически после возможной навигации. Ресурсы с потерянным create-response считаются неизвестными; dispose-on-detach проверяется тестом, не принимается на веру. Если cleanup/ownership нельзя доказать — worker not-ready, drain, restart только выделенного тестового/worker Cloak через supervisor. Перезапуск не считается успешной очисткой без отметки в отчете.
  7. 429/Retry-After → durable retry Python, без повторной browser/HTTP попытки; 401/407, policy/resource/cancel → типизированный отказ. DNS/CDP временная недоступность → retryable failure с cooldown и bounded reconnect; без fallback, обходящего policy. Learning, AI, DB и отправку выполняет только авторитетный Python caller.

Browser deadline первоначально сохраняет текущий максимум API 30 секунд, в пределах общего Python budget. Cleanup имеет отдельное измеряемое ограничение. Если реальные стратегии требуют больше, это отдельное согласованное изменение контракта, а не скрытое увеличение таймаута.

6. Протокол сравнения памяти

Одна Linux/amd64 машина, закрепленные digest приложения/worker/Cloak/gateway, одинаковые CPU/RAM/shm/pids, browser flags, concurrency 1, URL/order/caps/readiness и объем результатов. Каждый прогон получает свежий выделенный Cloak и профиль. Никаких production cookies, env, DB, scheduler, AI-ключей или отправок. Synthetic HTTPS origin и разрешенный test CA — только fixture stand; live origin использует обычное доверие сертификатам.

ВеткаЧто отделяет
A — текущий Python/nodriver + native CloakРеальная существующая политика lifecycle; controlled fixture network без доступа к LAN/Internet. Записать фактический reuse cookies/cache, а не объявлять их одинаковыми.
B — Python controller + тот же gateway и disposable context policyСтоимость новой изоляции/egress относительно A. Браузерная библиотека остается текущей; если wrapper не поддерживает нужный isolation mode, это блокер, не повод незаметно заменить библиотеку.
C — Go controller + точно те же gateway/context policyЭффект языка/CDP controller при равных условиях B/C. Сравнение A/C показывает совокупный эффект реального изменения.
D — полная будущая связка app Python + Go worker + Cloak + gatewayПроверка эксплуатационной экономии: Python app после выноса не исчезает. Суммируем все обязательные контейнеры и сравниваем с app Python + Cloak при том же потоке jobs.

Два вида corpus: (1) детерминированные native-loaded fixtures, одинаковые ответы на server side, включая JS/fetch/cookies/redirect/slow/huge DOM/iframe/worker; (2) ограниченный список публичных live URL как отдельная совместимость, без непрерывного publisher load. Доступ к частному synthetic origin задается только отдельной test-only gateway конфигурацией с точным allowlist origin/IP; она не поставляется в production и не выбирается через API. Другие private destinations остаются запрещены. Контрольный origin сохраняет доказательства native request/TLS; секреты, bodies и полные URL не попадают в обычный отчет.

Протокол: cold baseline → одинаковый warm-up → минимум шесть циклов смешанных jobs → idle baseline после каждого цикла → завершение. Три независимых повторения с чередованием A/B/C; отчет содержит значения и разброс каждого повтора. Для механики lifecycle отдельно использовать общий DOM snapshot и тот же extraction algorithm, затем выполнить end-to-end native navigation + extraction: различия parser/качества не смешивать с расходом controller.

  • Основные показатели: синхронные memory.current по всем контейнерам, максимум суммы во времени, anon/file/shmem, CPU, latency p50/p95, throughput, errors/timeouts/429, количество реальных navigation и browser attempts, OOM/restarts. Сумма независимых container peaks — только верхняя оценка, не фактический пик системы. Указать accounting /dev/shm и host memory, не суммировать одни страницы дважды.
  • Разбивка: Python RSS/PSS и tracemalloc; Go RSS/PSS, live heap и goroutines; Cloak wrapper, browser, renderer/GPU/utility process tree, FD/socket/CDP sessions/targets/contexts. PSS — диагностическая атрибуция, cgroup total — эксплуатационная метрика. Profiling отдельно, одинаковая частота сбора 1 секунда; cgroup peak дополняет пропущенные короткие пики.
  • Baseline: до первого job, после warm-up, после каждого цикла на фиксированных idle точках 5/30/60 секунд. Показывать удержание кеша, slope и возврат ресурсов; отсутствие падения RSS само по себе не доказывает утечку. Не вызывать GC только у одного языка; forced-GC диагностика отдельно.
  • Concurrency 2 — отдельный stress run после concurrency 1, одинаково для B/C. Нельзя выдать уменьшение параллелизма или браузерных загрузок за выигрыш от Go.
  • После короткого lifecycle gate — минимум 24 часа изолированного soak на fixture corpus с тем же расписанием и idle окнами. Перезапуски не обнуляют видимый граф: lifetime и recovery budget сохраняются в отчете.

Решение: перенос ради RAM принимается только при воспроизводимом улучшении всей связки D относительно baseline при равном качестве, числе jobs, browser attempts и приемлемой latency. Целевую экономию в MiB и допустимое ухудшение p95 утверждаем по замеренному baseline до canary. Если выигрывает только controller heap, а суммарная память не снижается — так и фиксируем; следующий шаг выбираем по browser process breakdown.

7. Этапы, файлы и проверки

  1. Baseline и capability probe. Read-only сверка digest, controlled воспроизведение EOF/large DOM/cancel, provenance ledger и A baseline. Если pinned Cloak нестабилен уже с native Python или не поддерживает ownership — сначала разбор этого блокера, без выдачи миграции за исправление.
  2. Изолированный native skeleton. Новый transport и lifecycle, policy gateway, отказные network tests, Python B adapter. Без переключения API/production. Сначала короткая серия lifecycle/ownership, затем profiling.
  3. Article integration. Bounded native DOM → existing Go extractor; явный experimental server switch, private capability/readiness, typed errors; Python retry/learning/cache/force tests. HTTP-only по умолчанию сохраняется.
  4. A/B/C/D measurement и soak. Скрипт воспроизводимого запуска, pinned artifacts, независимая проверка методики и source differences. Отчет с графиками всей памяти, controller/browser breakdown, latency и failure ledger.
  5. Release decision. Только после gates — отдельный rollout diff, CI build immutable digest, отдельное разрешение на production. Не собирать production Docker image на VPS.

8. Acceptance, ручная QA, риски и откат

  • Native proof: контролируемый origin получает browser TLS/JS/cookies/subresources, без origin fulfill через Go. Надежность pinned Cloak проверена повторениями, а не единичным успехом.
  • Security: закрытые DNS/mixed answers/rebind/private redirect/IPv6/WebRTC/worker/iframe/download/popup обходы не достигают запрещенных destinations. Разрешенные fixtures завершаются. Политика одинакова B/C; не отключать CSP/egress без замены проверенной защитой.
  • Lifecycle: success/cancel/timeout/EOF/reconnect/crash/SIGTERM, потерянный create-response и late replies не оставляют owned contexts/sessions/targets; чужой sentinel target не тронут. Проверить cookie isolation между jobs и сохранение внутри job. Browser.close допустим только supervisor для своего выделенного контейнера.
  • Quality: разные методы и negative fixtures имеют source-backed expectations; metadata/media/relative links/final URL и truncation сохранены. Force refresh не запускает повторный AI/learning/delivery. Проверить одной статьей полный isolated processing path без реальной отправки.
  • Performance: A/B/C/D и 24-hour soak опубликованы как проверяемые artifacts, нет необъясненного роста объектов/FD/targets, OOM и restart не скрыты. Failed/short runs не исключаются из статистики успешных задач.

Основные риски: native crash вне Go heap; wrapper context semantics; новый egress меняет доступность сайтов и стоимость; page-native запросы могут тратить память до CDP событий; cache/cookie isolation меняет нагрузку; перенос controller не уменьшает renderer heap. Все они проверяются отдельными measurements/gates.

Откат: эксперимент по умолчанию выключен. На стенде остановить только свои worker/Cloak/gateway, сохранить логи, вернуть прежний Python route; production не затрагивается. При будущем canary — mode python и сохраненный app digest, закрытие новой admission и bounded drain; ошибки новой policy не превращать в per-job обход. БД не восстанавливается и jobs не переотправляются. Shared infra-chrome, Traefik и другие потребители не перезапускаются.

9. Предположения, открытые вопросы и approval gate

Предлагаемые defaults: dedicated browser, concurrency 1, публичный HTTPS article/web scope, disposable context/job, existing API budget до 30 секунд, controlled-first benchmark. Существующие production authenticated profiles не переносим. Native HTTP/WebSocket и коллекторами займемся отдельным scope только при подтвержденной необходимости.

До реализации неизвестны: актуальный фактический digest/args; причина прошлых native EOF; возможности wrapper для scoped contexts/proxy/dispose; доля browser RAM и требуемая экономия; достаточно ли существующего времени для native методов; нужен ли строгий decoded-body cap. Эти вопросы имеют конкретные probes выше. Отрицательный ответ может остановить соответствующий gate и потребовать пересмотра, а не ослабления защиты.

Approval gate пройден: пользователь одобрил план и начало реализации с изолированными проверками. Публикация образа, commit/push/PR, secrets и включение production не выполняются. Нового подтверждения на уже одобренные этапы не требуется.

Опорные материалы: Cloak preflight, HTTP-only pilot evidence, method ledger. Проверенные первичные CDP источники: Target lifecycle, Fetch interception, Network telemetry. Tip-of-tree документация описывает возможности протокола, но их наличие в pinned Cloak подтверждается только capability tests.

10. Фактическое выполнение и открытые gates

Добавлены отдельный native Go transport, server-only выбор backend, typed native failures без автоматического обхода через Python, bounded readiness с проверкой browser generation, CONNECT gateway, синтетический HTTPS origin и A/B/C/D measurement runner. HTTP-only остается режимом по умолчанию.

Подтверждено на отдельном закрепленном Cloak: сбой cleanup воспроизводится минимальным Python CDP при closeTarget → disposeContext; atomic context disposal дал 12/12 успешных Go capability циклов. Настоящая browser HTTPS загрузка, JS и cookie через CONNECT прошли 6/6. Это короткие проверки, не soak и не доказательство полной совместимости сайтов.

Свежий полный Python regression: 487 passed, 5 явных real-browser/soak skips; выделенный PostgreSQL остановлен после тестов. Go test/vet/mod verify и Linux race всех восьми пакетов прошли. Независимое ревью потребовало и получило исправления resource/error semantics, selector learning, frame identity, auth bounds и readiness; benchmark дополнительно проходит отдельную integration-проверку.

На VPS kernel 5.15 нет cgroup memory.peak. Его отсутствие отмечается как недоступный показатель, а не нулевое значение; синхронные memory.current samples остаются отдельной доступной метрикой. Не сравнивать sampled maximum с ненаблюдаемым истинным пиком. Три одинаковых независимых повтора, D с реальным processing, network egress bypass gate, sizing и завершенный 24-hour soak остаются открытыми.

Три короткие серии дали 210 успешных measured jobs без расхождений/OOM: A/B/C, B/C с одинаковой readiness и B/C с одинаковой readiness и controller limit 384 MiB. Последняя серия: synchronized sampled maximum Python+Cloak+gateway 445,7 MiB, Go+Cloak+gateway 310,3 MiB; controller maximum 100,0 и 8,1 MiB, p95 1,527 и 1,480 s. Это сравнение выделенных контроллеров: Python app после выноса останется, а память Cloak меняется между прогонами. Общая экономия сервиса не доказана.

Драйвер soak прошел 42 focused benchmark/soak tests и реальный 180-second smoke: 33 одно-кейсовых batch, затем 4 idle samples, без OOM/ошибок. Safe HTTP-only API smoke текущего бинарника прошел. Свежий непрерывный C-only soak стартовал 2026-10-16 10:28:54 UTC на 86400 s, начальный статус running. Результат 24 часов пока не получен. На каждом batch — все 5 synthetic cases × 6 cycles, idle gates 5/30/60 s; нет retries/restart и смешивания прежних artifacts. Контейнеры выделенные, без внешней сети; cleanup/outer timeout удаляют только их. Production не менялся.

Уточнение длительности от 16 октября: по просьбе пользователя первичное наблюдение сокращено до 4 часов от исходного старта, до 2026-10-16 14:28:54 UTC (16:28:54 по Белграду). Сохраняются тот же прогон и накопленные artifacts. Отдельный bounded supervisor остановит только его driver через SIGTERM; исходный суточный driver честно запишет interrupted, а изменение цели и его результат сохраняются отдельно. Незавершенный batch не считается успешным. Затем требуется оценить результаты, тренд памяти/PID, idle, OOM и restarts. Суточный тест отложен; сейчас ожидаем 4 часа наблюдения, без утверждения об исключении медленных утечек.

Конфигурация, evidence и ограничения: native worker implementation. Production, shared browser, конфиги/секреты infra, схема БД, AI и доставка не изменены.
