Результат и границы

Go владеет жизненным циклом попытки задания и порядком шагов новостного цикла. Python перестаёт принимать и исполнять задания очереди и управлять полным циклом; он предоставляет ограниченные предметные операции. Основная реализация — Luna, один PR и review. Пять постоянных контейнеров и три core-образа сохраняются: новые компоненты включаются в существующий background runtime, отдельные контейнеры и образы не создаются.

На Go переходят admission/idempotency, timeout policy, execution receipts, cancel/drain/recovery, применение результатов к совместимым schedule/stats полям и оркестрация ingestion → processing → необходимые сводки → публикация. Компоненты executor, orchestration и domain client разделены интерфейсами по обязанностям.

Python сохраняет Gemini, промпты и AI-поведение, обучение селекторов, форматирование/доставку Telegram/Telegraph, бэкапы, миграции и существующие административные предметные операции. Это конечные операции, а не вложенный запуск прежнего NewsOrchestrator. Перенос внутренних алгоритмов публикации, бэкапов и AI в этот этап не входит. Публичные UI/API/auth, настройки и расписания не меняются. Production, публикация образов, browser, extractor, egress и Readeck вне применения этого этапа.

Проверенная исходная схема

  • Текущий checkout: codex/env-runtime-cleanup, HEAD c10cb0d; PR34 уже merged в main1443a32. Сохранены локальные журналы двух планов, AGENTS.md и три пользовательских untracked production-плана. Перед реализацией — свежая ветка от проверенного origin/main, без reset или перезаписи этих файлов.
  • news_aggregator/executor.py содержит PythonJobExecutor, singleton guard, envelope validation, receipts, callbacks, private web backend и recovery. Go worker уже общается с ним через go-worker/internal/executor/client.go; очередь и lease не надо переносить повторно.
  • news_aggregator/orchestrator.py вызывает Go ingestion и Go processing, собирает статистику, отдельно генерирует дневные сводки и отправляет дайджест. Обычный news_processing сам по себе не отправляет Telegram; news_digest и telegram_digest имеют другие условия.
  • services/background_execution.py всё ещё выбирает исполнение восьми типов заданий и вычисляет timeouts. Некоторые части старого DurableBackgroundWorker используются активными обработчиками: удалять файл целиком до переноса этих вызовов нельзя.
  • Ingestion selector client и worker используют один JOB_EXECUTOR_URL. Processing использует отдельный ARTICLE_AI_URL. Python callbacks проверяют локальные _ACTIVE_FENCES и текущий executor instance — после переноса эту привязку необходимо заменить проверкой Go execution authority.
  • По завершённой live-приёмке PR34 действует один.env с явными role mappings; web/background не получают provider secrets. Последний production heartbeat timeout произошёл до этого переноса на COMMIT около5s; причина не доказана. Данный этап не является исправлением этой отдельной проблемы.

Целевая схема без новых контейнеров

Background: scheduler → queue worker → execution component → orchestration. Execution component вызывает существующие ingestion/processing API; те продолжают хранить собственные run receipts. Для AI/selector и конечных операций используется приватный domain API существующего Python-сервиса.

Предлагаемые новые пути: модуль go-execution/ с runner/ и отдельными пакетами internal/executor, internal/orchestration, internal/domainclient, internal/store, internal/policy. Он подключается к go-background через runner, как уже подключены worker, scheduler, ingestion и processing. Самостоятельный Docker image или второй процесс внутри контейнера не нужен.

Go execution listener — приватный :8101 внутри background, без host ports. Python domain API остаётся на :8100; web backend и ARTICLE_AI_URL продолжают обращаться туда. Worker получает JOB_EXECUTOR_URL на Go execution endpoint. Для selector client вводится отдельный SELECTOR_SERVICE_URL, явно заданный в Compose; нельзя глобально переопределить один общий URL и направить selector в неправильный сервис.

Readiness не образует цикл: Python domain health проверяет собственную готовность, а не наличие активного Go задания; execution readiness проверяет singleton guard и доступность domain API; worker начинает dispatch после готовности execution, ingestion и processing. Потеря worker lease или execution guard отменяет связанные шаги и запрещает новые записи. Startup/shutdown входят в общий bounded drain.

Контракты и сохранение безопасности

  1. Worker ↔ execution. Сохранить существующий private contract: status, timeout policy, accept202 с duplicate, read receipt, cancel, finalized и recovered events. Тот же versioned envelope, job/owner/generation/attempt/deadline, проверка backend PID по lease, тот же bounded result и safe error codes. Повтор того же тела возвращает прежнюю попытку; изменённое тело того же ключа отвергается. Только существующие восемь job kinds.
  2. Durable authority. Использовать существующие background_jobs/background_job_executions и текущие ingestion/processing receipts. Не вводить новую очередь, event bus или обязательную таблицу checkpoints. Go владеет execution receipt и новым instance ID; in-memory registry служит отмене, но не заменяет PostgreSQL fences. Отдельный singleton guard execution не должен конфликтовать с worker lease или оставшимся guard предметного Python-сервиса.
  3. Domain API — новый внутренний контракт. Явные допустимые операции для сводок, подготовки/отправки дайджеста, бэкапа, media refresh, stats/operational alerts. Запрос содержит version, operation, execution envelope/instance, ограниченный типизированный input и fingerprint. Нельзя передавать имя Python-метода, произвольный SQL или произвольный URL. Перед реализацией клиента зафиксировать схемы и ограничения размеров в contract fixtures.
  4. Callbacks и поздние ответы. Python проверяет актуальную Go execution identity, состояние попытки и deadline; перед публикацией DB/cache-результата повторяет transactional fence. Локальный _ACTIVE_FENCES прежнего PythonJobExecutor перестаёт быть источником authority. Ни одна транзакция/queue mutex не удерживается во время AI/HTTP. Несовпавшие instance/attempt/generation и изменившиеся source/item fingerprints отвергаются.
  5. Повторы и доставка. Lost acknowledgement сначала сверяется с receipt той же операции. Ограниченный cache ответов внутри domain instance не даёт оснований повторять отправку после его рестарта. При неизвестном внешнем исходе сохраняется delivery_unknown; автоматического повторного Telegram/Telegraph send нет. Не обещать exactly-once для внешнего API. Cancel не равен доказанному прекращению внешней операции; поздний ответ не переводит старую попытку в succeeded.
  6. Настройки и ресурсы. Сохранить timeout precedence/defaults, schedule revisions/due instants, article retries и error vocabulary. Один.env, явные per-component mappings. Для execution — явный EXECUTION_DATABASE_URL с проверкой необходимых текущих прав; не расширять worker role и не передавать provider credentials в background. Для локальных fixtures возможен отдельный least-privilege runtime role. Production credentials/grants не изменять. Пулы/конкурентность ограничены и укладываются в текущий бюджет; проверки должны выявить увеличение connections/working set, а не скрыть его поднятием лимитов.

Реализация на Луне и порядок

  1. Контракты и characterization — Luna, high. В новой ветке зафиксировать существующие execution API и поведение всех8job kinds, timeout policy, result aggregation и schedule completion. Owned: новые fixtures/tests и проект contract files. Не менять runtime. Ведущий проверяет схемы, receipts и delivery cases; это разблокирует последующие шаги.
  2. Execution core — Luna, high. Owned: новый go-execution модуль, его PG store/policy/HTTP lifecycle и tests. Сначала fake domain handlers. Acceptance: idempotency, строгая валидация, fencing, deadlines/cancel/drain, recovery и ограниченные результаты. Не менять provider code и production.
  3. Domain boundary — Luna, high, последовательно. Owned: Python domain API и перенос вызовов из executor.py в явные leaf services, callbacks/job_fence и tests. После фиксации контрактов. Удаление старого PythonJobExecutor — только после совместимой интеграции. Python предметная логика не переписывается ради этой границы.
  4. Orchestration и интеграция — Luna, high. Owned: Go orchestration/domain clients, go-background startup/probes/drain, scoped config, Compose examples, Docker/Bake/CI и combined fixtures. Разделить JOB_EXECUTOR_URL/selector URL. Старый Python полный цикл исключить из активного runtime; удалить недостижимые части после import/call-graph проверки, сохранив используемые leaf операции и CLI.
  5. Приёмка — ведущий. Проверить фактический combined diff, concurrency/auth/data contracts, наблюдаемые tests и Docker gates. Независимый Luna review дополняет проверку ведущего; Sol/Astra автоматически не запускаются. Review findings возвращаются исполнителю. Один PR, CI и review; без merge, publication или deployment на этом этапе.

Общие файлы принадлежат одному исполнителю в каждый момент; параллельные правки executor.py или runtime.go запрещены. Новые агенты/модель реально указываются в журнале после запуска. Не создавать worktree только для планирования. Если исходный checkout нельзя безопасно продолжить с сохранением dirty файлов, при реализации использовать управляемую изоляцию.

Проверки и приёмка

Ниже запланированные проверки; в ходе подготовки плана они не запускались.

  • Contract/golden parity Python reference ↔ Go: валидный/повторный/конфликтующий envelope, duplicate JSON keys, bool вместо integer, UUID/deadline bounds, unknown kind, token failures и result overflow. Отдельно все8job kinds и payload flags.
  • PG16/17 integration и Go race/vet: concurrent accept, две execution instances, lease loss, старые callbacks/instance после рестарта, stale finalize, cancel race, deadline во время AI, пропавший ACK. Нет DB lock во время сетевого запроса; никаких writes после fence loss.
  • Fake providers: AI/selector callback из Go execution, Python domain restart до/после send, частичная доставка, receipt lost, backup boundary и source changes. Внешнее unknown не повторяется автоматически. news_processing не отправляет сообщения; news_digest уважает оба флага.
  • Существующие executor/backup/background/web-backend tests адаптируются к новой границе, а не просто удаляются. Функциональная full Python suite и затронутые Go suites; команды go test -race -count=1 ./... и go vet ./... в новом модуле и затронутых модулях; python -m pytest tests/ -q.
  • Расширить scripts/run_go_background_fixture_gate.py: штатный цикл8synthetic sources через Go execution/orchestration, selected processing, AI и selector callbacks, publication ambiguity, worker/execution/domain restarts, startup без dependency cycle, bounded shutdown и отсутствие OOM. Новый gate сохраняет прежние инварианты71-check набора; число новых checks заранее не обещается.
  • Final images: три core targets из одной сборки, background содержит execution/orchestration, Python image не запускает очередь/полный цикл. Linux/amd64 CI и Mac/ARM64 local smoke по доступному месту. Disk preflight, без массового prune. UI/public contract paths остаются прежними; admin backup/settings и cookie/JWT/Basic bridge regression покрыты.
  • Secrets/permissions: один.env, provider secrets только в domain service; pool/resource bounds не подняты; состав контейнеров не вырос. Сеть fake-only, исходящие Telegram/Telegraph/AI/site запросы исключены. Production и реальные источники не участвуют в локальной приёмке.

Риски и возврат

Главные риски — потеря fencing при передаче authority, повтор внешней доставки, startup cycle, прежняя Python orchestration за новым Go фасадом и смешение scoped URLs/DSNs. До исполнения существенного кода контрактные fixtures должны фиксировать текущую семантику, включая странности legacy result handling; изменение поведения требует отдельного решения, а не молчаливого улучшения.

Без production выкатки возврат — не применять новый PR/образ; исходные данные и настройки не меняются. Нельзя сбрасывать пользовательские файлы или восстанавливать production из этого плана. Будущий rollout потребует отдельного одобрения с pause/drain, согласованной заменой background/domain image и конфигурации, без двух активных исполнителей. Если реализация докажет необходимость новых production grants/schema, перед применением потребуется отдельный конкретный план; сама миграция authority не является разрешением менять VPS.

Go execution и orchestration включены в существующий background runtime; Python worker, NewsOrchestrator и приём заданий старым executor удалены. Python сохраняет typed domain operations и callbacks. Старые parser/receipt oracle перенесены в tests, selector PostgreSQL tests используют действующий RemoteDomainFence и оба advisory guard.

Независимый локальный прогон: Python + PostgreSQL16 — 1051 passed, 28 subtests; Go race tests с PostgreSQL17 — worker, scheduler, ingestion, processing, execution и background; go vet и module verification этих модулей прошли.
