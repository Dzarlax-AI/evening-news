Go/Cloak: падение одной вкладки не останавливает очередь

2026-10-21 · Редакция 2 · Одобрено пользователем: «Го». Ограниченный контракт реализован и принят; production не изменён.

Основание

Асинхронный CDP coordinator устранил прежнюю остановку на The Verge: теперь C возвращает resource_limit и переходит дальше. Последний диагностический live-прогон подтвердил Inspector.targetCrashed на case-0034. C выполнил 3 из 5 попыток; B — 5 из 5, причём case-0034 в B завершился таймаутом. Причина падения renderer не установлена. Тот же класс Inspector.targetCrashed воспроизведён без реальных сайтов на фиксированном paced6МиБ HTMLfixture. Удаление background:true не помогло; эксперимент отменён. Новая строгая native regression остаётся красной. Считать его ошибкой только Go оснований нет. Relay подключился 14 из 14 раз без ошибок, OOM не было; production и очистка независимо проверены.

Текущее поведение NativeBrowser.Fetch: Inspector.targetCrashed своей сессии немедленно taint-ит worker; ошибка ownership loss останавливает всю серию. Каждый Fetch уже создаёт отдельный BrowserContext, а cleanup проверяет отсутствие своего контекста и targets. Изменение params.sessionId не устранило этот renderer crash.

Предлагаемый контракт

  1. Различать подтверждённый Inspector.targetCrashed своей сессии и неизвестную потерю ownership. При падении своей вкладки немедленно отменить задание, завершить pending RPC и удалить только свой контекст.
  2. Восстановить доступность для следующего задания только после успешного disposal, подтверждения отсутствия своих context/targets, отсутствия event overflow, совпадения поколения браузера и успешной ограниченной проверки его доступности.
  3. Текущая статья возвращает пустой результат и отдельную конечную ошибку native_browser_target_crashed. Автоматически повторять её запрещено. Следующая независимая статья получает новый контекст.
  4. При любой неопределённости, неуспешном cleanup, malformed/owned detach, закрытии CDP-соединения, смене поколения или overflow worker остаётся tainted, следующая попытка отклоняется без allocation. Очередь256, pending RPC32, requests128, wire5МиБ, concurrency1 и все таймауты/лимиты сохраняются.

Это изоляция сбоя задания; она не устраняет причину падения Chromium. Перезапуск браузера, повышение лимитов и изменение фонового режима вкладки в этот объём не входят.

Риски, неизвестные и откат

Главный риск — ошибочно принять повреждение всего browser process за падение одной страницы. Поэтому восстановление допускается только при всех перечисленных receipts; сомнение означает отказ. Причина конкретного renderer crash и прежнего редкого TCP connect timeout остаётся неизвестной. Если synthetic не подтвердит контракт, реализацию не принимать. Откатить только новый обработчик восстановления и API mapping отдельным обратным patch, сохранив накопленные изменения и evidence; никаких reset/checkout поверх пользовательской работы.
