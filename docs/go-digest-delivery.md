# Native digest workflow and delivery

The background execution component retains job ownership and calls the private domain operations API. The Go domain process validates the request envelope and executes the four digest operations directly. Accept and status receipts use the job, attempt, operation and operation ID; a lost accept acknowledgement is reconciled by reading the same receipt. A changed request conflicts with the existing receipt. Prepared handles are opaque UUIDs bound to the job attempt, domain instance and deadline.

The domain process reads the UTC-day snapshot under the worker and execution fence, generates an edition using the existing editorial library, then persists the edition under a fresh fence. Provider calls do not hold a database transaction. The editorial model receives prepared summaries as evidence, not original article content. Historical editions remain in `editorial_digest_editions`; preparation checks their stored snapshot and render before use. The workflow calls the editorial library directly.

Migration `015_digest_delivery` adds `digest_delivery_intents` and `digest_delivery_parts`. It is applied by the existing explicit migration command, not at runtime startup. Before a future rollout, verify the domain database role has only the required privileges on these tables. Keep receipt history during rollback; the previous image cannot consult these receipts, so resolve any unknown delivery before restarting publication with that image. The intent is keyed by edition, destination fingerprint and publication purpose. It records the originating job, attempt and domain instance until completion. A different attempt or instance may take over only when there are no parts that are sending, sent or unknown. An incomplete intent with any such part cannot be continued automatically; a completed intent returns its saved result without another POST. A 429 is terminal for the current call. Its persisted Retry-After applies to the whole intent, including a later switch between rich and plain delivery; a later owner may retry only after the period has elapsed. A part records its immutable payload hash and state, without message text or bot credentials. The native sender shares the existing POST admission limit with AI and other domain consumers and performs one POST per reserved part.

A part is committed as `sending` before the network request. An explicit valid Telegram `ok=true` response permits `sent`; definite 4xx rejection permits a bounded rich-to-plain fallback, except that 429 ends the current attempt. A timeout, disconnect, 5xx, malformed or empty response, lost commit acknowledgement, or an unfinished `sending` receipt represents an unknown outcome. The workflow does not resend a confirmed or possibly accepted part automatically. Telegram and PostgreSQL do not form a single transaction, so this is not an exactly-once guarantee.

Main and service destinations use the configured defaults and existing `settings` overrides. The digest fixes the selected destination for its delivery intent. Operational alerts and admin tests use the shared transport and the selected logical destination. The domain process receives the Telegram token and defaults explicitly; background and web do not need them. Fixture-only endpoint routing is separate from ordinary operation inputs and defaults to the official Telegram endpoint outside fixture mode.

The Go integration tests require an explicitly configured loopback PostgreSQL fixture. The CI matrix exercises PostgreSQL 16 and 17. The synthetic image gate has separately exercised default digest publication, ambiguous delivery after lease loss, a definite 429 receipt, and partial delivery without replay in its PostgreSQL 16 run; complete image acceptance and PostgreSQL 17 remain open. Provider and Telegram endpoints in these tests are synthetic.
